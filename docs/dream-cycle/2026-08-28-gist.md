# security-adversarial SOTA Report — 2026-08-28

**TL;DR**: 2025–2026's biggest npm supply-chain incidents (the Shai-Hulud
self-propagating worm, Sept–Nov 2025; the May 2026 node-ipc compromise,
which exfiltrated 78,330 secrets from 2,186 organizations' CI/CD pipelines
in five days) were all *devDependency*-tier compromises that executed
during `npm ci`/`npm install`/`npm test`/`npm run build` — never shipped to
a production artifact, but very much live on a build/CI machine. Tonight's
security-adversarial deep dive tested MetaHarness's own supply-chain
tooling (`harness audit`, `harness sbom`) against that exact blind spot,
using the metaharness repo itself as the target. Both commands default to
excluding devDependencies (industry-standard, matches the documented
two-tier CI pattern), but neither said so: `harness audit` printed
`PASS: 0 advisories at high+` and `harness sbom` silently emitted a
smaller SPDX document, with **no signal in either output** that anything
was excluded — even though this repo's own dev dependency tree right now
carries 1 critical (Vitest ≤3.2.5, arbitrary file read/execute via the
Vitest UI server) and 4 high advisories. A reviewer trusting the default
output would see a clean bill of health that isn't the whole picture. Fixed
both commands to disclose the suppressed/excluded count by default without
changing default pass/fail gating; independent self-critique caught a
real, adjacent double-counting bug in the pre-existing `total` field
arithmetic (`Object.values()` summing npm's own precomputed `total` key a
second time), fixed in the same diff since my own new disclosure line would
otherwise have shipped a wrong number.

## Hypothesis

Given a harness (or this repo) audited via `harness audit` (default, no
`--include-dev`) and `harness sbom` (default, no `--include-dev`), when a
disclosure patch is applied — `audit` runs one additional best-effort,
non-gating `npm audit` call (no `--omit=dev`) to report a suppressed
advisory count, `sbom` counts excluded dev-scope packages and adds an SPDX
`creationInfo.comment` plus a matching CLI line — then a reviewer reading
only the default-mode output should be able to tell, without re-running
with extra flags, that N advisories / M packages were excluded by
dev-scope filtering, relative to baseline (today's commands, which give no
such signal even when devDependencies carry a critical advisory), subject
to: (a) default PASS/FAIL gating semantics for `audit` are unchanged — the
disclosure is additive, never gating; (b) no new dependency, no new
external destination (same npm registry already contacted); (c) 0
regressions in the existing 467-test `create-agent-harness` suite; (d) new
tests must fail against the pre-patch code (red/green), not just pass
against the patch.

## Adversarial Critique

Self-critique (same session — no second model/critic available tonight;
disclosed, not hidden, per ADR-250). Checked: did the candidate weaken any
existing test or threshold? No — only additive tests, no existing

tonight (kept the diff bounded). **Found and fixed one real bug during my
own adversarial pass**: `npm audit`'s `metadata.vulnerabilities` object

the unpatched code) summed `Object.values(counts)`, double-counting that
`total` key — invisible in the old code only because the default
(`--omit=dev`) scope on this repo happens to be all-zero. My own new
"devDependencies not counted: 16 advisories" line surfaced it immediately
against real npm output; fixed both the new and the pre-existing
occurrence to sum only the five known severity keys, added a regression
test (`auditJson()` test helper now includes a realistic `total` key) so
it can't silently reappear.
