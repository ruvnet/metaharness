# security-adversarial SOTA Report — 2026-10-13

TL;DR: `harness threat-model`'s top-level `verdict`/`exitCode` — the one number a PR reviewer or CI gate would actually read — is computed from a hand-picked boolean grid that never consults the severity rollup (`scan.worst`) its own internal `scanMcp()` call already produces. A harness with an MCP server registered but **zero** governing policy file gets `verdict: 'clean', exitCode: 0` in the same report that lists `no-policy` as a HIGH finding and sets `worst: 'high'`. This was disclosed-but-deliberately-deferred by this repo's own 2026-09-03 run (#276) and never revisited. Fixed tonight by folding `scan.worst` into both verdict thresholds. This is not a MetaHarness-specific embarrassment: a September 2026 audit found five commercial/OSS MCP scanners (Cisco, Snyk, NVIDIA among them) returning clean verdicts against MCP servers that were live-stealing credentials.

## MetaHarness Current Capability

`harness mcp-scan` (ADR-022, "npm audit for agent tools") already computes a correct per-finding severity rollup (`ScanReport.worst`) over policy/permission/dependency checks. `harness threat-model` (iter 112) wraps it for PR/compliance review but recomputes its own `verdict`/`exitCode` from an independent boolean grid (`shellAccess`, `policyDefaultDeny === false`, `secretsReachable`, `networkAccess`, `fileWrite`, `auditLog === false`) that has no term for "no policy file exists at all" (`policyDefaultDeny` is `null`, and `null === false` is `false` in JS) or for scan-only findings like an unscoped interpreter allow-rule (`risky-bash-allow`) or a settings-side `unrestricted-bash-allow`. Net effect, confirmed live against this repo's own committed `kimi-k3-harness` fixture tonight: `verdict: clean, exitCode: 0` printed in the same JSON as `worst: high`.

**Bottom line:** nobody in this list ships a mature "findings list + separate verdict" report comparable to `threat-model.ts` — MetaHarness is ahead of the pack in even having the surface. The specific failure (a prose/JSON verdict that can read safer than the structured findings underneath it) isn't publicly documented anywhere in the MCP-security niche specifically, but it's a named instance of the general SAST/SCA "fail-on-threshold" anti-pattern class, and the Sept 2026 Pluto Security audit shows real, shipped commercial scanners making the identical class of mistake this month.

## Hypothesis

Given a scaffolded harness directory with an MCP server registered (via `.harness/mcp-policy.json`, `.mcp.json`, or `.claude/settings.json`'s `mcpServers`), when `buildThreatModel()` computes its top-level `verdict`/`exitCode`, then the verdict should never read better than `scanMcp()`'s own `worst` severity rollup over the same directory — subject to: (a) zero change to `mcpInUse`/`findings`/`worst`/every other `ThreatModel` field; (b) the `!mcpInUse` early-"off" path stays byte-identical (verified: `scan.worst` is always `'info'` when MCP isn't in use); (c) every currently-correct `'clean'` verdict for a findings set whose worst severity is `'low'`/`'info'` stays unchanged; (d) the exit-code scheme (high=2, medium=1, clean=0) is preserved, just correctly triggered.

## Evaluation

**Candidate**: `packages/create-agent-harness/src/threat-model.ts` — add `|| scan.worst === 'high'` to the HIGH branch and `|| scan.worst === 'medium'` to the MEDIUM branch of `buildThreatModel()`'s verdict grid. `scan` is already in scope (no new import, no circular dependency; confirmed `mcp-scan.ts` does not import from `threat-model.ts`).

**Landmine found and fixed in the same diff**: root-level `__tests__/harness-threat-model.test.ts`'s `makeSafePolicyRepo()` fixture omitted `requireApprovalForDangerous`, which `mcp-scan.ts` already independently flags as a MEDIUM finding (`no-approval-gate`) — the fixture was never actually fully compliant, just silently uncaught by the old verdict grid. Corrected by adding the missing field (a legitimate tightening — the fixture now earns its "safe" label for real — not a weakened assertion).

- **Baseline** (`git stash` the source fix): 4/4 new package-level assertions + 3/3 root-level assertions fail non-vacuously — `clean`/`0` where `high`/`2` or `medium`/`1` is now expected.
- **Candidate**: `packages/create-agent-harness` 623→627/629 tests (+4, 0 regressions, 2 pre-existing skips). Root `__tests__/harness-threat-model.test.ts` 8/8 (0 regressions, 1 fixture corrected). Downstream `packages/agntcy` 82/84 (2 pre-existing skips, 0 regressions — confirmed it reads `ThreatModel`'s boolean shape, never `.verdict`/`.exitCode`). `tsc --noEmit` clean. Full monorepo `npm run build`: clean (JS-only; wasm/NAPI crates live in a separate `cargo`-only workspace never touched by `npm run build`, not a degradation tonight).
- **Live CLI smoke test**: `harness threat-model` against this repo's own committed `kimi-k3-harness` fixture: `clean/exit 0` → `high/exit 2`, matching `worst: high`.
- **Blast radius** (independently confirmed twice, by two research passes): the only production call site is `subcommands.ts`'s CLI dispatch (forwards `{code, lines}` verbatim); no `.github/workflows/*.yml` shells out to `harness threat-model` and checks its exit code; `packages/agntcy/src/identity/from-mcp-scan.ts` duck-types the boolean triplet, never `.verdict`/`.exitCode`.
