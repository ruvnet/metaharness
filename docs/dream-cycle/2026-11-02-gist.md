# Darwin-Evolution SOTA Report — 2026-11-02

TL;DR: `@metaharness/weight-eft`'s deterministic reward-hacking monitor (ADR-198) — the sole defense
keeping a trajectory that secretly read a withheld gold/test file, or tampered with the verification
harness, out of weight-eft's SFT/DPO training-data export — gated its `gold-read` detection on a
`READ_TOOLS`/`WRITE_TOOLS` tool-name allowlist copied from a *different* harness's naming convention
(`read_file`, `edit_file`, `cat`, `view`, ...). This repo's own actual agentic tool surface
(`ls`, `read`, `grep`, `edit`, `line_edit`, `run_tests`, `submit` — `bench/swebench/agentic-loop.mjs`'s
`buildAgenticToolsSchema`, mirrored in `gepa/genome.ts`'s `TOOL_ORDER`) was never in either set, and
none of `read`/`ls`/`edit`/`line_edit` match the branch's regex fallback (`/file|path|patch/i`) either
— so an agent calling its own primary file-reading tool (`read`) to open `test_patch.py` or
`gold_patch` sailed through undetected. Closed by adding the real tool names to the two sets; 0
regressions, 2 new tests fail non-vacuously pre-fix (exactly the predicted gap; the `edit`/`line_edit`
verification-tamper case was already covered by an existing regex fallback and is now covered via the
allowlist too, for defense-in-depth).

## MetaHarness Current Capability
`detectRewardHack()` (`packages/weight-eft/src/reward-hack.ts`) is a pure function over a
`DarwinTrajectory`'s messages, called by `export.ts`'s `exportTrainingData` on every gold-resolved
trajectory before it can enter SFT or on-policy DPO data. It has 4 detection branches: (a) gold-read
via an outgoing tool call, (b) verification-harness tamper, (c) sandbox escape, (d) gold content
leaking back through a tool *response* (added 2026-09-07, PR #293). Branches (a)/(b) gate partly on a
hardcoded tool-name allowlist (`READ_TOOLS`/`WRITE_TOOLS`) plus a generic regex fallback on the tool
name itself.

## Hypothesis
> Given a `DarwinTrajectory` whose assistant turn calls this repo's own agentic tool surface (`read`,
> `ls`, `edit`, or `line_edit` — not a different harness's `read_file`/`edit_file` convention), when
> that tool call's arguments contain a gold-read pattern (e.g. `test_patch`, `gold_patch`) or a
> verification-tamper pattern (e.g. `conftest.py`), then `detectRewardHack()` should flag it
> (`gold-read` / `verification-tamper` respectively) — matching its already-correct behavior for the
> generic `read_file`/`edit_file` tool names — subject to: (a) the existing `read_file`/`cat`/
> `edit_file`/... coverage and all 4 pre-existing detection branches stay byte-identical; (b) an
> honest trajectory calling `read`/`edit` on a path with no gold/verification pattern in it is **not**
> flagged (no new false positives); (c) the fix stays inside `reward-hack.ts`'s documented "pure
> function, no I/O" contract; (d) zero regression on weight-eft's existing 48 tests.

Frozen before implementation, not modified after.

## Adversarial Critique

Independent fresh-subagent critic (cold-read, own reproduction, not taken on faith): read the full
post-fix `reward-hack.ts`, independently confirmed `ls`/`read`/`edit`/`line_edit` are this repo's own
tool names (`agentic-loop.mjs`, `genome.ts`), independently confirmed the gap via direct code reading
— and sharpened it: pre-fix, branch (a) (gold-read) was **dead code for every trajectory this repo's
own harness actually produces**, not just a partial gap, since the harness's sole read/list tools
(`read`/`ls`) matched neither the sets nor the regex fallback. Ran `git log --all -p` over ~140 refs
independently and confirmed `READ_TOOLS`/`WRITE_TOOLS` were untouched since file creation — genuinely
fresh. Confirmed the diff is purely additive (no pattern/threshold weakened, no test deleted) and
blast radius is exactly `export.ts` (the only real caller). Independently ran both suites (weight-eft
52/52, darwin-mode 840/854 unaffected) and `tsc --noEmit` clean.

**Verdict: ACCEPT-WITH-CAVEATS.** One real caveat, correctly flagged: `GOLD_READ_PATTERNS` applies a
loose bare `/test_patch/i` (and `/expected[_-]?(output|patch|result)/i`) match to call *arguments* —
unlike the tool-RESPONSE-content patterns (branch d, added 2026-09-07), which were deliberately
narrowed to a `test_patch:` key specifically to avoid false-positiving on a legitimate
`def test_patch(self)`-style test name. Because `read`/`edit` are now the harness's dominant
production tool names, an honest trajectory calling `read(path=".../test_patch_something.py")` on a
real library file (e.g. testing an HTTP PATCH method) would now get flagged, where that risk was
previously dormant (nothing matched `read`). This is a pre-existing design choice already accepted for
`cat`/`edit_file` (the same loose pattern applies there too) — tonight's fix *activates* it for the
harness's real trajectories rather than introducing it. Not fixed tonight (narrowing the pattern is a
separate, independent change with its own false-negative-risk tradeoff to evaluate on its own); flagged
below as a follow-up.
