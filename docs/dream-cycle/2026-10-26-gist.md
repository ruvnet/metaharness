# Flywheel-Promotion SOTA Report — 2026-10-26

TL;DR: `@metaharness/avo`'s and `@metaharness/turn-credit`'s `canon()` — both documented "exact
mirrors" of `@metaharness/flywheel`'s receipt canonicalizer — still had the same two bugs
`flywheel/receipts.ts` was hardened against on 2026-10-16 (stack-exhaustion on deep nesting) and
2026-10-21 (NaN/Infinity/-Infinity collapsing to the same signed byte string as `null`). Ported both
hardenings verbatim. An independent critic's adversarial review surfaced a **third, previously
undisclosed** copy of the same bug in AVO's own core receipt chain (`crypto.ts::canonical()`) —
deliberately not fixed tonight, filed as the next finding instead of scope-creeping this diff.

## MetaHarness Current Capability

`canon()` in `packages/flywheel/src/receipts.ts` is the package's single canonicalization choke
point (signing, replay, multi-generation proof, review-context digest). It was hardened on
2026-10-16 (`MAX_CANON_DEPTH=64`, PR #406) and 2026-10-21 (non-finite rejection + `canonEquals()`
fail-closed helper, PR #423) — both ACCEPTed and **confirmed merged to `main`** (via the
2026-10-21 integration PR #426, verified directly: `git log` shows `review-dream406`/
`review-dream423` as ancestors of the current main tip, and `packages/flywheel/src/receipts.ts`
on `main` already has the hardened code). The same logic was independently copy-pasted into two
other packages (disclosed 2026-10-21) for cross-repo/dependency-free reasons, and — as of tonight's
independent review — into a **third** place no prior night had named.

mature), just not an *adopted* one — none of these frameworks treat "may this candidate replace the
running one" as an adversarial security boundary, because none of them yet have an agent proposing
its own next version the way this repo's flywheel/Darwin loop does. The gap is a genuine
architectural-maturity gap, not a solved-but-unpublished one. Best non-default comparison found:
the x402 canonicalization draft above, for its version-pinning idea.

## Hypothesis

> Given a receipt/manifest payload containing a non-finite number or pathological nesting, when the
> already-ACCEPTed `canon()` hardening from `flywheel/receipts.ts` is ported byte-for-byte into its
> two disclosed sibling duplicates, both packages' signature/hash-binding checks should reject the
> crafted input cleanly instead of colliding or stack-overflowing, with zero behavior change on all
> existing finite inputs and all existing tests green.

**Result: CONFIRMED.**

## Evaluation

- Non-vacuous baseline repro (pre-fix, against built `dist`): `canon({x:NaN}) === canon({x:null})`
  → `true` in both `avo` and `turn-credit`; deep nesting (200k) → native `RangeError`.
- Post-fix: both now throw a clean, named error (`non-finite`, `exceeds max nesting depth`); normal
  finite/shallow inputs byte-identical to before.
- `packages/avo/__tests__/flywheelGate.test.ts`: 11→18/18 (+7, 0 regressions).
- `packages/turn-credit/__tests__/turn-credit.test.ts`: 20→25/25 (+5, 0 regressions).
- Downstream sweep (flywheel+avo+turn-credit+create-agent-harness): 874 passed / 2 pre-existing
  skipped / 1 failed — the 1 failure is a live-OpenRouter model-deprecation 404, confirmed identical
  on the unmodified baseline (environmental, not caused by this candidate).
- `tsc --noEmit` clean on both touched packages. `npm audit --omit=dev --audit-level=high`: 2
  pre-existing high advisories (`body-parser`, `zod`), unrelated to this diff, disclosed not fixed.
