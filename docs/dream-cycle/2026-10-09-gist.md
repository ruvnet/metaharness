# host-adapters (kernel) SOTA Report — 2026-10-09

TL;DR: `@metaharness/kernel`'s `SessionLog.append()`/`fork()` had a disclosed-but-unfixed (2026-09-19, #332) TOCTOU race — two concurrent, unawaited calls on the same log could read the same pre-increment index, corrupting the on-disk JSONL and making the *entire* session unrecoverable on reopen (not just the racing events). The identical bug was independently duplicated into the `--sessions` scaffold-template copy of `SessionLog` emitted into every new generated harness (`packages/create-agent-harness/src/index.ts`). Both are fixed tonight with a per-log async operation queue that changes only append-time *ordering*, never the wire format. A major competitor SDK (OpenAI Agents SDK) has the exact same bug class, reproduced with a 646,802-error stress test in a real, currently-unmerged PR — this is an active, unsolved problem industry-wide, not a solved one MetaHarness was behind on.

## MetaHarness Current Capability

`packages/kernel-js/src/session.ts`'s `SessionLog` (ADR-246 §2.3): append-only JSONL, per-branch monotonic index, fork-not-edit branching, SHA-256 hash-chained replay, byte-for-byte wire parity with a Rust mirror (`crates/kernel/src/session.rs`). The Rust mirror is a pure, stateless validate/replay/fork function library with no persistent mutable append state — it structurally cannot have this race; only the TS side's convenience mutable `LogState` could.

| Framework | Concurrent-write approach | Grade |
|---|---|---|
| OpenAI Agents SDK | Per-file `threading.Lock`, but the lock-per-call bug made it a no-op; fix unmerged | A (known, currently unfixed gap) |

| DSPy/GEPA | No append-only log; batch/offline snapshots with transactional (copy-then-commit) load | B/C (different problem class) |

**Bottom line:** this exact race is either unaddressed, known-and-still-broken in a major actively-maintained SDK, or avoided by restricting to single-writer models — not solved under true multi-writer contention anywhere but an alpha side project. MetaHarness's kernel already had the right format-level invariants (monotonic index, hash-chained replay, fork-not-edit); tonight's fix closes the one remaining write-arbitration gap, putting it ahead of the two named competitors that have looked at this specific property in public.

## Hypothesis

Given a `SessionLog` instance (kernel-js) or its scaffold-template duplicate (create-agent-harness), when two or more `append()`/`fork()` calls are issued without awaiting the previous call, then each call should be assigned a distinct, monotonic index and the log should remain reopenable (reopen must not throw a duplicate/non-monotonic validation error) — subject to: (a) the wire format (`serializeEvent`/`canonicalJson`/`stateHash` fold) stays byte-identical for any sequential use (verified by the existing, unmodified fixture test continuing to pass); (b) zero new dependency; (c) `fork()`'s identical one-level-up race (two concurrent forks to the same new branch name) closes as the same mechanism; (d) both the kernel-js source and the scaffold-template copy get the identical fix shape.
