## OBSERVATION

- `packages/flywheel/src/sequential.ts`'s `withSequentialEvidence()` reads
  `evidence.pairedOutcomes` and early-returns the base rule's decision only
  when `!outcomes` is true. `![]` is `false` in JS — an empty array is
  truthy — so `pairedOutcomes: []` does NOT hit the early return.
- The function's own doc comment states the intended contract: "When absent
  the rule degrades to `baseRule` alone rather than silently blocking every
  promotion — a caller that has not wired up per-item outcomes yet should
  get the old behavior, not a permanently closed gate."
- `sequentialEvidence([])` starts at `eValue = 1`, accumulates nothing (loop
  body never executes on an empty array), and `1 >= threshold` (default 20)
  is false — so `significant` is always `false` for `[]`, regardless of
  `alpha`/`lambda`.
- `packages/flywheel/__tests__/sequential.test.ts` (pre-tonight) tested the
  `undefined` case (`degrades to the base rule when no paired outcomes are
  supplied`) but never tested `pairedOutcomes: []` explicitly — the gap was
  untested, not just unfixed.
- No current production code path in this repo passes `pairedOutcomes` to
  any `PromotionRule` — `withSequentialEvidence` is reachable only from its
  own unit tests today (confirmed via `grep -rln pairedOutcomes` across
  every package `src/` in the repo). Open PR #288 (2026-09-06, unmerged as
  of tonight) is the one change that would make this reachable from
  `runFlywheelGenerations`/`verifyReplayBundle` in production.

## INFERENCE

- The empty-array case is a real, plausible integration hazard, not a
  contrived one: JS/TS callers commonly default an optional array field
  with `?? []` rather than leaving it `undefined` (e.g. an `Evaluator`
  or an adapter that has not yet wired real per-item outcomes, or one
  whose holdout suite legitimately scored zero items on a given run). Any
  such caller would have every candidate permanently rejected by
  `insufficient_sequential_evidence`, silently, with no distinguishing
  signal from "real data was checked and found weak."
- This is the same underlying bug SHAPE as tonight's slot has repeatedly
  found in this package (a strict/edge-case comparison in a promotion-gate
  clause failing closed or open in an unintended way — see 2026-08-16
  #205, 2026-08-26 #231, 2026-08-31 #255, 2026-09-01 #258, 2026-09-11
  #307's `noopRate` ceiling-lockout) but is a DIFFERENT function
  (`withSequentialEvidence`, not `verifyReplayBundle`/`gateReExecutes` or
  `meetsPromotionRule`'s `noopRate` clause) and a different trigger
  (falsy-but-not-absent input, not a strict-inequality ceiling).
- Per STEP 1.1's duplicate-direction rule, the `verifyReplayBundle`/
  `gateReExecutes` replay-trust family has now been the subject of ≥3
  substantially-identical prior-night findings (08-16, 08-26, 08-31/09-01)
  — that specific direction was deliberately NOT revisited tonight even
  though `replay.ts` was re-read in full as part of research.
