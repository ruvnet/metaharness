# security-adversarial SOTA Report — 2026-08-18

**TL;DR**: `harness mcp-scan` ("npm audit for agent tools", ADR-022) checks a scaffolded harness's
`.claude/settings.json` allow-list for risky `Bash(...)` grants via a regex whose binary alternation
was `rm|curl|wget|sudo|chmod|ssh` and a wildcard check matching only `*`/`mcp__*`/`mcp__*__*`. Neither
matched a fully unscoped `Bash(*)`/bare `Bash` rule, nor an unscoped interpreter rule. The second gap is
live today: the `vertical:ai` template's own `.claude/settings.json.tmpl` ships `Bash(python *)`, and a
real `metaharness --template vertical:ai` scaffold carries it in unflagged — `mcp-scan` reports "clean"
on the exact grant it exists to catch. Fixed both gaps in a small change to the same check loop,
disclosing which half is live and which is defense-in-depth (an independent critic caught me
overstating the first half's reachability before this shipped — see Adversarial Critique).

## MetaHarness Current Capability

`harness mcp-scan` (`packages/create-agent-harness/src/mcp-scan.ts`) statically inspects
`.harness/mcp-policy.json` + `.claude/settings.json` + `package.json` and flags: no policy,
not-default-deny, shell/network/file-write grants, missing approval gate/audit log/timeout/call-budget,
wildcard tool permissions, risky `Bash(...)` allow-rules, unguarded secret reads, unpinned deps. Exit 1
on any HIGH. A sibling tool, `harness threat-model`, independently re-derives a similar verdict from
`.harness/mcp-policy.json` alone and never consults `mcp-scan`'s findings — see Recommended Next Steps.

## Hypothesis

Given `scanMcp`'s host-permission-check loop, which flags only exact wildcard strings (`*`, `mcp__*`,
`mcp__*__*`) and a regex over a fixed binary list (`rm|curl|wget|sudo|chmod|ssh`), when the regex's
binary alternation is extended to include arbitrary-code interpreters (`python`, `python3`, `node`,
`ruby`, `perl`, `bash`, `sh`) and a new exact-match branch flags fully unscoped `Bash`/`Bash(*)` as a
separate HIGH finding, then a real `metaharness --template vertical:ai` scaffold's shipped
`Bash(python *)` allow-rule should be flagged `risky-bash-allow` (MEDIUM) where it previously scanned
clean, subject to: (a) zero regression in the package's 455-test baseline, (b) no existing test
modified, (c) the new check must not fire on any narrower, legitimately-scoped `Bash(...)` rule, (d)
diff materially under 300 lines.

  `Bash(git *)` remain unflagged, as they should.

## Adversarial Critique

Independent critic (no authorship context) reviewed the diff — verdict **ACCEPT-WITH-CAVEATS**, and
caught a real problem before this shipped: my first draft's comments claimed
`host-config.ts:45` (`if (cfg.allowShell) allow.push('Bash(*)')`) was *the* live mechanism putting
`Bash(*)` into a scaffolded harness's `.claude/settings.json`. The critic traced the call graph and
found that line unreachable for that outcome: the CLI's `scaffold()` never passes `allowShell` into
`hostConfigFiles()`, and the web-ui's `claudeSettings()` (the actual `.claude/settings.json` writer)
hardcodes a scoped `Bash(npx <name>*)`, never calling the function with the analogous push at all. I
independently re-verified by reading both call sites directly — confirmed. Rewrote the framing before
shipping: `Bash(*)`/bare `Bash` is disclosed as defense-in-depth against the *config shape*, not a
second live generator bug; `Bash(python *)` is the finding with confirmed real-world reachability
(proven via the actual CLI). Critic separately confirmed: no existing test/fixture modified, no
false-positive risk on scoped rules, severities consistent with siblings, diff scope exactly the 2
stated files, not a duplicate of any prior Dream Cycle finding.

## Recommended Next Steps

1. **Wire `mcp-scan`'s findings into `threat-model`'s verdict.** `buildThreatModel()` re-derives its own
   booleans from `.harness/mcp-policy.json` only, never consulting `scanMcp()`'s `findings[]`/`worst` —
   a harness can be `mcp-scan` HIGH/exit 1 on its `.claude/settings.json` allow-list while `threat-model`
   reports "clean"/exit 0 on the same harness. Same root-cause class as tonight's fix.
2. **Extend `sbom-cmd.ts` to Cargo, not just npm.** `harness --with-wasm <crate>` wires a real Rust crate
   into a scaffolded harness, but `harness sbom` reads only `package.json`/`package-lock.json` — an SBOM
   that looks complete but omits Rust deps. The unshipped top-level `scripts/sbom.mjs` already reads
   `Cargo.lock`; port that logic in.
3. **Check `Read(*)`/`Write(*)`/`Edit(*)`/`WebFetch(*)`** — tonight's fix covers `Bash(...)`; the same
   wildcard-argument class likely applies to other permission prefixes `mcp-scan` doesn't examine.
   Not attempted tonight to keep this diff single-mechanism.
