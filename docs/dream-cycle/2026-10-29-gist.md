# host-adapters (GitHub Actions heartbeat) SOTA Report — 2026-10-29

TL;DR: `@metaharness/host-github-actions` partially projects `autonomous.heartbeat`
onto GitHub Actions' native `schedule:` cron trigger (cadence only) but silently
dropped the required sibling field `heartbeat.instruction` — so a scheduled
(cron-fired) run's `task` input resolved to the bare literal `github.event_name`
("schedule") instead of any real instruction content, even though the adapter's
own runbook claimed the heartbeat was fully "Projected." Fixed by threading
`instruction` through as a `HEARTBEAT_INSTRUCTION` env var, consumed by the
generated composite action only when `$GITHUB_EVENT_NAME = "schedule"`, and by
disclosing it explicitly in `installRunbook()`. ADR-246 §2.2 ("never silently
drop — project per host or emit an explicit documented no-op") violation, the
same class 2026-09-19 (#332) closed for 8 other hosts' `autonomous` field.

## MetaHarness Current Capability

`packages/host-github-actions/src/index.ts`'s `workflowYaml()` already does
real ADR-246 §2.2 projection for `autonomous.gateCommand` (a pre-flight gating
step) and `autonomous.heartbeat.cadence` (a native `schedule:` cron trigger,
round-2 fix from #332, 2026-09-19). `installRunbook()` discloses every
`autonomous` field as either "Projected onto this host" or (quoting the field
itself) "**Not projected** ... documented no-op." `heartbeat.instruction`
(required whenever `heartbeat` is set — `kernel-js/types.ts:47`) was the one
field that fell through both categories whenever `cadence` parsed as a valid
cron: the `else if (autonomous?.heartbeat)` disclosure branch only runs when
`cronCadence` is falsy, so a *working* cron trigger silently hid the fact that
its own instruction was never used.

## Hypothesis

Given a `HarnessSpec` with `autonomous.heartbeat` set to a valid 5-field-cron
`cadence` and a non-empty `instruction`, when `host-github-actions`'s
`workflowYaml()`/`actionYaml()`/`installRunbook()` thread `instruction` through
as the effective task for schedule-triggered runs, then a cron-fired run
should receive the instruction's text as its task input instead of the
baseline's literal `github.event_name`, and `installRunbook()` should disclose
`heartbeat.instruction` as "Projected onto this host" — subject to: the
existing manual/`issue_comment` trigger resolution stays byte-identical;
YAML/shell injection safety is preserved (JSON.stringify-escaped at the YAML
value position, matching this file's existing cadence/gateCommand/step-name
convention); zero behavior change when `heartbeat` is absent or non-cron.

  This predates tonight's change and is not widened by it.
