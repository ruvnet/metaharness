# Flywheel-Promotion SOTA Report — 2026-11-11

TL;DR: `verifyReplayBundle()` and `verifyMultiGenerationEvidence()` (`@metaharness/flywheel`) are
documented, re-exported entry points for an *independent reviewer with no trust in the producer* — but
only `cli.ts`'s `loadBundle()` ran untrusted bundle JSON through the fail-closed `validateReplayBundle()`
gate before calling them. A caller that imports either function directly (the exact "external reviewer"
use case both functions' own doc comments describe) got no such gate: a non-array `chain`/`all_commits`/
`generations`, or a non-array `parents` on a chain node, reached the functions' own iteration/property
access and threw an uncaught `TypeError` — breaking their own documented "always return a verdict, never
throw" contract. This is the exact gap the 2026-10-21 ledger entry disclosed-but-did-not-fix ("validate-
bundle.ts's fail-closed gate lives only in the CLI path, not in verifyReplayBundle/
verifyMultiGenerationEvidence themselves"). Root cause is distinct from the canon()-family hardening
fixed 10-16/10-21/10-26/10-31 (recursion depth / non-finite encoding inside canonicalization) — this is
top-level/array shape, which canon()'s depth bound never touches — so it is not a duplicate direction
under STEP 1.1. Fixed by wiring `validateReplayBundle()` into `verifyReplayBundle()`, and an equivalent
`Array.isArray` guard into `verifyMultiGenerationEvidence()`, as the first thing each function does.

## MetaHarness Current Capability

`@metaharness/flywheel` ships one promotion gate (`meetsPromotionRule`, already fail-closed on
NaN/Infinity via `isValidScore`) and two independent-replay entry points: `verifyReplayBundle` (lineage +
receipts + gate re-execution) and `verifyMultiGenerationEvidence` (recursive-improver proof). Both are
re-exported from `index.ts` as the package's public API for a reviewer who trusts nothing from the
producer. `validateReplayBundle` (shipped 09-21, hardened against NaN/Infinity/oversized numbers) already
existed and was already wired into the CLI's `replay`/`graph`/`analyze` verbs — but, until tonight, into
neither of the two functions those verbs themselves call for verification.

## Hypothesis

Given a `ReplayBundle` or `MultiGenerationEvidence` JSON object with a structurally malformed top-level
shape (non-array `chain`/`all_commits`/`generations`, or a non-array `parents` on a chain node) passed
*directly* to the exported `verifyReplayBundle()`/`verifyMultiGenerationEvidence()` — bypassing `cli.ts`'s
`loadBundle()` gate — when `validateReplayBundle()` is wired into `verifyReplayBundle()` (and an
equivalent `Array.isArray` guard into `verifyMultiGenerationEvidence()`) as the first thing each function
does, then both should return a clean `{pass:false}` verdict instead of throwing an uncaught `TypeError`,
subject to: (a) zero regressions on the 291 pre-existing flywheel tests; (b) all 7 real committed
`ReplayBundle` files continue to replay PASS byte-identically; (c) no change to any gold data, threshold,
or promotion rule. Frozen before implementation (confirmed via live `node -e` repro against the pre-fix
`dist/cjs` build before writing the fix), not revised after evaluation.
