# darwin-evolution SOTA Report — 2026-10-12

TL;DR: Darwin Mode's Tier-1 "mock" sandbox (`packages/darwin-mode/src/mock-sandbox.ts`, ADR-101/102) is the deterministic, LLM-free evaluator used by the `evolve:dry` script every generated harness ships and by the web-UI's default `sandbox: 'mock'` config. Its `extractSurfaceParams()` reads a `memoryThreshold` value out of a mutated `memory_policy.ts` surface file — and the existing `DeterministicMutator` really does perturb that value in production (its generic numeric-threshold edit rule matches the template's `threshold = 0.5` literal) — but the pre-fix `simulateAgentLoop()` never consumed `memoryThreshold` anywhere. Every memoryPolicy mutation scored byte-identically to its unmutated parent, 100% of the time: Tier-1 evolutionary search was structurally blind to an entire approved mutation surface it was actively generating children for. Fixed tonight with a 34-line, backward-compatible change (baseline `threshold=0.5` is a provable no-op). `toolPolicy`, `reviewer`, and `scorePolicy` remain unextracted in this file — disclosed, not fixed, below.

## MetaHarness Current Capability

`packages/darwin-mode/src/mock-sandbox.ts` (Tier-1, ADR-101/102): `extractSurfaceParams()` text-parses 4 of the 7 ADR-071 surfaces (retryPolicy→maxAttempts, contextBuilder→contextWindow, memoryPolicy→memoryThreshold, planner→planSteps) using the same regexes `DeterministicMutator` writes with. Pre-fix, `simulateAgentLoop()`'s `solved`/`durationMs` depended on only `maxAttempts` and `contextWindow`; `planSteps` only emits cosmetic log lines; `memoryThreshold` was computed and silently dropped. `toolPolicy`, `reviewer`, `scorePolicy` are not extracted at all, despite `safety.ts`'s `FILE_BY_SURFACE` mapping all 7. `pickSurface()` (mutator.ts) samples all 7 surfaces uniformly, so pre-fix, ~5/7 of generated Tier-1 mutations were fitness-invisible — provably no-ops from the selector's point of view, independent of mutation content. `--sandbox real` is the raw CLI default, but `create-agent-harness` hardcodes its generated `evolve:dry` script to `--sandbox mock`, and the web-UI's `DarwinSandbox` config defaults to `'mock'` too — so this is the path most users actually exercise first.

ADR history: ADR-101 names `toolPolicy` ordering as outcome-driving; ADR-102 (as-built) silently swapped it for `memoryPolicy` — tonight's fix closes that gap, not a new design call. At least the 4th "signal computed then discarded" instance in this family (ADR-249 08-17; Tier-2 gate 09-02; traceQuality 09-22; Tier-2 toolPolicy 10-07/#379).

## Hypothesis

Given a Tier-1 (mock) Darwin-mode evolution run — the default sandbox for `create-agent-harness`'s generated `evolve:dry` script and the web-UI's default config — when a child variant mutates only the `memoryPolicy` surface (one of the 7 ADR-071-approved surfaces), then `simulateAgentLoop()`'s `solved`/`durationMs`, and therefore `scoreBenchmark()`'s `finalScore`, should change relative to the parent when the mutated `memoryThreshold` crosses 0.5 in either direction (pre-fix: provably byte-identical 100% of the time, regardless of mutation content), subject to: (a) the baseline template's `threshold=0.5` stays a byte-for-byte no-op for every variant not touching this surface (backward compatibility); (b) zero new dependency, zero LLM calls (Tier-1 stays deterministic per ADR-102); (c) the existing `mock-sandbox.test.ts` suite and all dependent darwin-mode suites stay 100% green with only additive new assertions.

## Evaluation

`evaluated: accepted`.

- **Baseline** (reproduced via `git stash` on the source file only, keeping the new tests): 2 of 4 new tests fail non-vacuously (the other 2 are compatibility/saturation checks that correctly pass either way) — a strict-vs-lenient `memoryThreshold` at otherwise-identical params produced byte-identical `solved`/`attemptsUsed` (pre-fix: `strict.solved` expected `false`, received `true`; `lenient.attemptsUsed` expected `2`, received `3`).
- **Candidate**: `mock-sandbox.test.ts` 8→12/12 (+4, 0 regressions). Full `@metaharness/darwin` suite: 669 passed, 14 pre-existing skips (683 total), 0 regressions across 74 test files. `tsc --noEmit` clean. Full monorepo `npm run build` clean (JS workspaces; wasm/NAPI steps not exercised in this sandbox, an unrelated environmental degradation — confirmed irrelevant since `mock-sandbox.ts` has zero wasm/native dependency). No cross-package consumer of `mock-sandbox.ts`'s exports exists outside its own test file (grep-confirmed) — blast radius contained to `@metaharness/darwin`.
- Design is backward-compatible by construction: `memoryPenalty(0.5) = 0`, and the base template's literal default is `threshold = 0.5` — every pre-existing test (none of which varies `memoryThreshold`) is a provable no-op under the new code.
- **Independent critic (round 1): ACCEPT-WITH-CAVEATS** — one concrete defect: a 4th new test claimed to exercise a `Math.max(0, …)` floor clamp but used a strict (never-negative) penalty, so the clamp never engaged. Deeper look: `attempt` only ranges over `0,1,2,…`, so `attempt >= requiredAttempts` behaves identically whether `requiredAttempts` is `0` or negative — the clamp was fully inert for *any* input, not just under-tested. **Round 2 (same night):** removed the dead clamp, rewrote the test for the real saturation behavior, re-ran the full suite (669/683, unchanged), reconfirmed via a fresh `git stash` repro. Critic's other finding stands and is carried into Recommended Next Steps: the mechanism is a 2-plateau step function, not a continuous gradient — a partial, not complete, fix to the fitness-blind-surface problem; toolPolicy/reviewer/scorePolicy remain honestly disclosed as unaddressed.
