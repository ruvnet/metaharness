# host-adapters SOTA Report — 2026-08-14

**TL;DR**: 2026 harness-evaluation literature (Zhang et al., arXiv:2605.23950;
Epoch AI's SWE-bench Verified tracker) has now formally shown that scaffold
identity — not just the model — can swing agent benchmark scores by 10+
points, which sharpens the stakes of MetaHarness's own claim that its 10
host adapters are "emission-only" and never change measured behavior
(ADR-247, ADR-027). Auditing that claim tonight surfaced a real, reachable
defect: `AgentSpec.name`/`HarnessSpec.name` were interpolated unescaped into
YAML **mapping-key** position for Hermes, so a name containing `:` silently
corrupts the emitted `cli-config.yaml`. The bug turned out to be triplicated
— ADR-046 requires this Hermes logic stay byte-for-byte identical across
all **three** codegen paths (`@metaharness/host-hermes`, CLI scaffold's
`host-config.ts`, web-UI's `scaffold.ts`), and all three had it. Fixed in
all three, tested (19+15+18/18 green, additive only), independently
critiqued — the critic
caught a residual reserved-word hazard in the fix itself (closed before
shipping) and two comparably-shaped sibling gaps this diff does **not**
close (disclosed below, not hidden).

(`packages/host-*`) turning one typed `HarnessSpec` into host-native config

exists for only 8 of 10 today (missing `rvm`, `copilot` — filed below, not

## Hypothesis

Given the three Hermes YAML-emitting codegen paths (`@metaharness/host-hermes`,
`host-config.ts`'s hermes case, `scaffold.ts`'s hermes case — kept
byte-for-byte in parity by ADR-027/ADR-046), each interpolating a
harness/agent name directly into YAML mapping-key position while already
escaping same-function scalar *values* via `JSON.stringify`, when a
`yamlKey()` helper (quote unless bare-identifier-shaped AND not a
YAML-1.1-reserved scalar) is applied at every key-position site in lockstep
across all three, then a name with YAML-significant characters should no
longer corrupt any of the three documents, subject to: (a) byte-identical
output for existing conventional names, (b) each suite green with only
additive tests, (c) no new dependency, (d) the three paths stay in parity.

## Adversarial Critique

Independent critic (no authorship context) reviewed the
`@metaharness/host-hermes` adapter fix specifically (the first-drafted,
narrowest form) — verdict **ACCEPT-WITH-CAVEATS**. Confirmed all 3 claimed
key-position sites fixed, confirmed the new tests fail pre-fix (not
vacuous), confirmed no test weakened. It found one real problem —
`yamlKey()`'s identifier regex bare-emitted YAML-1.1-reserved scalars
(`true`, `null`, `123`, …), which Hermes' PyYAML-family loader would
silently mistype from string to bool/null/int — **fixed before shipping**
(`YAML_RESERVED_BARE` check added, 19/19 green). It also surfaced two
**comparable, still-open** sibling gaps not closed tonight (see Recommended
Next Steps): (1) the top-of-file YAML *comment* line also embeds the name
raw — a newline can break out of the comment and inject arbitrary top-level
YAML (worse than tonight's bug: whole-document injection), present in all
three codegen paths; (2) `optionalMcpYaml`'s `name`/`command`/`url`
**value** positions are also unescaped (adapter only). A *third* finding
came from my own re-read afterward: ADR-046/ADR-027 require this Hermes
logic stay byte-for-byte identical across `host-config.ts` and
`scaffold.ts` too — both had the same unfixed bug. That 2-file expansion
was **not** separately critiqued; instead each new test was verified by
direct revert-and-fail (restore the pre-fix line, confirm the predicted
corrupted output, restore the fix — shown in Benchmarks). Disclosed rung:
the 3-path fix is evidence-backed by direct reproduction, not a second
critic pass.
