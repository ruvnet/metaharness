## Hypothesis

Given a Darwin Mode variant surface file (one of ADR-071's seven approved mutation files) containing ordinary optional-chaining syntax around a blocked capability identifier (`process?.env`, `fetch?.(`, `eval?.(`, `require?.(`, generic `exec?.(`, `Reflect?.get(process,...)`), when `BLOCKED_CONTENT_PATTERNS` in `packages/darwin-mode/src/safety.ts` is updated to tolerate an optional `?.` between the identifier and its separator, then `inspectVariant()` and `validateGeneratedCode()` should both flag the content as blocked, subject to: (a) every previously-blocked non-optional-chaining payload remains blocked byte-identically, (b) zero existing test regresses, (c) diff confined to `safety.ts` + its two security test files + `SECURITY.md`.

## Benchmarks / Evaluation

**Round 1**: Baseline (pre-fix, new tests present) 16/16 new tests fail non-vacuously (`expected 0 to be greater than 0` for every BYPASS #4 case). Candidate (post-fix): full `packages/darwin-mode` suite **665→681/695** (+16, 0 regressions). `import(` and `new Function` deliberately left unpatched — confirmed via the TS compiler API that `?.` on either is a genuine syntax error (`new Function` is additionally a bare-word match with no trailing-separator requirement, so it is unaffected by this bypass class at all).

**Independent critic verdict: REJECT.** A fresh, cold-read subagent critic reproduced the round-1 red→green proof itself, then found and demonstrated end-to-end (real `inspectVariant()` call, crafted `planner.ts`) a residual bypass round 1 missed entirely: the non-null assertion operator `!` (`fetch!(`, `process!.env`, `eval!(`, `require!(`, `exec!(`, `Reflect!.get(process,…)`) — valid TypeScript, same mechanism as `?.`, completely unconsidered in round 1. It also found a false-positive regression: round 1's `process.env`/`process.binding` fix made every separator character independently optional, so "process" immediately followed by "env"/"binding" with **no separator at all** also matched — flagging ordinary identifiers (`processEnvVar`, `NodeJS.ProcessEnv`, `processEnvironment`, `processEnvelope`, `processBindingConfig`).

**Round 2** (same night): redesigned the `process.env`/`process.binding` patterns as an alternation of whole separator forms (`.`|`?.`|`!.` before a bare property, or optional `?.`/`!` before a mandatory `[`) instead of independently-optional pieces — closing the false positive while still requiring a real separator. Added `(?:\?\.|!)?` (covering both `?.` and `!`) to the five call-form patterns (`exec`/`eval`/`fetch`/`require`/`Reflect.get`), which carry no equivalent false-positive risk since their trailing `(` stays mandatory. Independently re-verified: all 9 of the critic's exact payloads (including the end-to-end `fetch!(...)`+`process!.env` exfiltration string) now blocked; all 5 false-positive identifiers stay clean; full `packages/darwin-mode` suite **665→709/723** (+44 total: 16 round-1 + 28 round-2, 0 regressions, 14 pre-existing skips unchanged), `tsc` clean, zero downstream importers of `safety.ts` repo-wide.
