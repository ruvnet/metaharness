# Darwin-Evolution / Weight-EFT SOTA Report — 2026-11-01

TL;DR: In 2026, the Dream Cycle's own history shows a bug class — a comparison-based numeric
safety gate (`x < MIN || x > MAX`) that silently lets `NaN` through, because every IEEE-754
comparison against `NaN` evaluates `false` — has now surfaced twice in this repo (`learn`'s
`--max-cost` spend cap, fixed 2026-10-17) and once in the wild as a tracked 2026 CVE (vLLM's
temperature validation, CVE-2026-54235, fixed June 2026). A third, disclosed-but-never-fixed
instance has sat open in `@metaharness/weight-eft` since 2026-09-22: `train.ts`'s
`assertTunableSize()` — the gate that's supposed to refuse any base model outside the vetted
1–14B "tunable" band before spending real GPU training time — passes silently when the CLI's
`--params-b` flag parses to `NaN`. Tonight's DEEP surface moved from the originally-rotated
`flywheel-promotion` to `darwin-evolution`/`weight-eft` because flywheel-promotion's
`canon()`/`canonical()` sibling-porting family has now run 4 consecutive nights (10-16/21/26/31)
and 10-31's own PR pre-committed this as the night to switch (STEP 1.1).

## MetaHarness Current Capability

`@metaharness/weight-eft` (ADR-198) is the $0-by-default LoRA SFT/DPO pipeline: `export` builds
JSONL from a Darwin archive, `train` plans (and, behind `--train` + a detected GPU/endpoint,
runs) training, `eval` folds outcomes into a cost-Pareto delta. `assertTunableSize()` is the one
place that enforces "stay in the 7-14B class model band, don't train a 32B model that spills a
16GB GPU." It is called unconditionally from both `sftConfig()` and `dpoConfig()`, reachable even
on the default dry-run path, not just behind `--train`.

**Why this isn't "None across the board" by default:** the interesting fact isn't absence, it's
that the *exact mechanism* was a live, cross-vendor-confirmed production CVE in the single
closest adjacent project 4.5 months ago, with a public fix (`Number.isFinite` before the range
check) that transfers directly here.

## Hypothesis

> Given `weight-eft train --params-b <value> --sft <path> ...`, when `--params-b` parses to
> `NaN` (malformed/non-numeric flag value), then `assertTunableSize()` should reject the
> configuration with an explicit error — before a plan is built or `runTraining` runs, on both
> the SFT-only and SFT+DPO paths — matching its documented 1–14B band contract,
> subject to: the 3 existing boundary tests (7B/9B accept, 32B reject) stay byte-identical; the
> `[1,14]` constants are untouched; the fix is a pure additive `Number.isFinite` guard; zero
> regression across weight-eft's suite.

Frozen before implementation; not modified after evaluation begins.

## Benchmarks

Corpus: `packages/weight-eft/__tests__/train.test.ts`'s existing size-gate `describe` block (3
pre-existing cases: 7B accept, 9B accept, 32B reject) plus 2 new non-vacuous cases added tonight
(NaN reject, ±Infinity reject). No synthetic benchmark corpus was created — the existing unit
suite is itself the real, committed oracle for this gate; it has not been modified beyond adding
cases.

## Evaluation

`evaluated: accepted`.

- **Baseline** (`git stash` isolating only `packages/weight-eft/src/train.ts`, new test file kept):
  2/11 new-file tests fail, but only 1 is a true gate bypass — `assertTunableSize({paramsB: NaN})`
  returns without throwing (`NaN < MIN` and `NaN > MAX` both observed `false` under IEEE-754,
  the exact CVE-2026-54235 mechanism). The `±Infinity` case is **not** a bypass: `Infinity > MAX`
  is `true`, so the pre-existing range check already threw pre-fix — that test failed only
  because the thrown message didn't match `/non-finite/i` yet. Caught and corrected by tonight's
  independent critic; disclosed here rather than left as an overclaim.
- **Candidate**: `train.test.ts` 11/11 (9 pre-existing + 2 new); full `@metaharness/weight-eft`
  suite 48→50/50 (+2, 0 regressions). `npx tsc --noEmit` clean.
- **Downstream sweep** (repo-root `npx vitest run`, all workspaces): 3632 passed / 60 skipped / 1
  failed — the 1 failure is `packages/avo/__tests__/openrouter-live.test.ts` (OpenRouter 404 on a
  model deprecated 2026-10-09), an environmental flake documented in multiple prior nights'
  PRs (10-11/10-16/10-26/10-31), unrelated to this diff (touches no `avo` file).
- `npm audit --omit=dev --audit-level=high`: 0 high/critical (10 pre-existing moderate transitive
  advisories — `minimatch`/`tuf-js`/`sigstore` via `agntcy-dir` — unrelated, no manifest/lockfile
  touched).
- Live CLI smoke test: `node packages/create-agent-harness/dist/bin.js weight-eft train
  --params-b notanumber --sft <path> --adapter test` now exits 1 with an explicit non-finite
  error instead of silently emitting a dry-run plan for a nonsensical model size.
- **Independent adversarial critic** (fresh cold-read subagent, own reproduction): verdict
  **ACCEPT-WITH-CAVEATS**. Confirmed the fix is correct, minimal, additive, and the sole choke
  point (`assertTunableSize` gates all 3 production call sites; the only untrusted-input
  constructor, `cli.ts`'s `--params-b` flag, always flows through it — no bypass path). Caught
  the counting/framing errors corrected above. Disclosed, not fixed: `weight-eft/src/cli.ts`'s
  `exportCmd --max-tokens` has the identical unguarded `Number(...)` idiom (already named in the
  2026-09-22 gist as a separate, lower-severity, data-quality-only finding — correctly left out
  of this narrowly-scoped fix); no test exercises `trainCmd`'s CLI dispatch directly, only the
  `train.ts` unit.
