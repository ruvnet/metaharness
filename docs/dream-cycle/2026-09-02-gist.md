# darwin-evolution SOTA Report — 2026-09-02

TL;DR: 2026 field evidence (Meta-Harness, arXiv 2603.28052; Agentic Harness
Engineering, arXiv 2604.25850; a field survey flagging that self-modifying
harnesses have been caught disabling their own scoring visibility, e.g. STOP
and DGM) converges tightly on Darwin Mode's own "freeze the model, evolve the
harness" thesis, and specifically flags **verifier-honesty / containment**
against a mutating agent as a live, practical risk — not a theoretical one.
Auditing Darwin Mode's own containment layer against that risk tonight found
a real instance of exactly that class of gap: the **Tier-2 `agent` sandbox
(ADR-106) never called the ADR-071 safety gate** before executing a variant's
real, generated TypeScript surface code in a child process. `tier2-sandbox.ts`
carried a module-doc claim ("the gate has already cleared the variant before
any execution") that was false — and had already been caught and explicitly
left open ("out of scope to fix here") in yesterday's ADR-273. Tonight closes
it: `inspectVariant` now runs first, mirroring the two sibling sandboxes that
already do this correctly (`sandbox.ts`, `llm-agent-sandbox.ts`). A new
adversarial regression test proves non-vacuously that unpatched code lets an
injected module-level side effect (a marker file write) actually fire, and
that the patched code prevents it — before any exitCode/metadata check.

(7 mutation surfaces + a numeric-genome kind as of ADR-272) with a frozen

constituent. This is a codebase that audits its own headline claims harshly;
tonight applies that same discipline to the containment layer rather than to
another benchmark number.

## Hypothesis

Given a Darwin-mode evolutionary run configured with `sandboxMode: 'agent'`
(Tier-2, ADR-106) evaluating a mutated variant whose generated surface file(s)
would be flagged by `inspectVariant` (ADR-071 safety gate) — e.g. blocked
filesystem-capability content in an approved surface file — when the variant
is dispatched through `runVariantTaskAgent`/`runVariantTasksAgent`, then the
safety gate must run and disqualify the variant (exitCode 99, matching
`sandbox.ts`/`llm-agent-sandbox.ts`'s existing convention) BEFORE
`tier2-driver.ts` imports/executes its surface files, subject to: (a) zero
behavioral change for any variant that already passes the gate; (b) zero
existing test weakened; (c) full darwin-mode suite stays green.

## Benchmarks

Deterministic, $0, no LLM/GPU calls. Corpus: a hand-built adversarial variant
directory (one approved surface file poisoned with a `node:fs` top-level
import + `writeFileSync` side effect — both individually confirmed to trip
`BLOCKED_CONTENT_PATTERNS`) plus the full existing 74-file / 671-test
darwin-mode suite as the regression corpus.

## Evaluation

- **Baseline (unpatched `tier2-sandbox.ts`)**: `inspectVariant` correctly
  flags the poisoned variant when called directly (control), but
  `runVariantTaskAgent` still executes it — `exitCode: 1` (not 99, i.e. never
  gated), and, decisively, the injected marker file **is created**
  (`existsSync === true`): the malicious module's code ran for real.
- **Candidate (patched)**: same variant now returns `exitCode: 99`,
  non-empty `blockedActions`, and the marker file is **never created**
  across both `runVariantTaskAgent` and `runVariantTasksAgent` (all tasks
  disqualified, not just the first).
- **Regression**: full darwin-mode suite 657 passed / 14 pre-existing skips
  (74 files), 0 failures, before vs. after identical pass count outside the
  2 new tests. Full monorepo build (4 phases) clean.
