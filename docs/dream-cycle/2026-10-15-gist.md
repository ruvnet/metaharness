# generator-genome SOTA Report — 2026-10-15

TL;DR: `repo-scorecard.ts`'s `compileConfidence` dimension (the `metaharness
score` command, ADR-041) was the last scorer in its own family still trusting
manifest-inferred `testCommands` instead of real test-file evidence — a
zero-test Python repo with only a `pyproject.toml` scored a full 90/100
"will build/run cleanly" confidence. Fixed to require real evidence
(`hasVerifiedTestFiles`, or an authored `npm test` script), matching the
precedent `genome-scorers.ts::scoreTestConfidence` already set on 2026-08-25
(#229). 2026 external research on agent-harness evolution (HarnessDev,
arXiv:2609.01437) and the LangGraph/CrewAI/AutoGen landscape both ground why
this class of "manifest implies readiness" shortcut matters.

The "no competitor does this" row is a genuine gap, not solved-but-unpublished:
repo-readiness/genome scoring is a narrow, MetaHarness-specific idea (score a
*target* repo for harness-fit before scaffolding) that doesn't map onto what
LangGraph/CrewAI/AutoGen/DSPy ship (they configure/orchestrate agents, not
score arbitrary host repos for harness-worthiness). HarnessDev is the closer
match — it scores *generated harnesses themselves* on downstream task
performance, a complementary, heavier-weight signal to this repo's cheap
static scorer.

## MetaHarness Current Capability

`metaharness score <repo>` (ADR-041, `repo-scorecard.ts`) emits 6 dimensions:
harnessFit, compileConfidence, taskCoverage, toolSafety, memoryUsefulness,
estCostPerRunUsd + recommendedMode/archetype. All derived from
`analyze-repo.ts`'s no-exec file inventory. Capability-discovery correction
for tonight's session: the scheduler prompt's STEP 0.5 checklist names
`doctor`/`diag`/`audit`/`mcp-scan`/`threat-model`/`sbom`/`secrets`/`validate`/
`compare` as if they were `metaharness` (generator) subcommands — they are
not. This package ships **two separate bins**: `metaharness` (`dist/bin.js`:
new/analyze/genome/score/learn/redblue/flywheel/turn-credit/avo/proxy) and
`harness` (`dist/harness-bin.js`: doctor/diag/audit/sbom/mcp-scan/
threat-model/secrets/validate/compare/sign/verify/…, intended to run against
a *scaffolded* harness, though it also runs cleanly against this monorepo
itself). Running `node bin.js doctor` against the wrong bin silently
scaffolds a new harness literally named "doctor" (confirmed, then cleaned up
this session) instead of erroring — a real, if minor, UX footgun worth a
future night's attention, not fixed tonight (out of scope for a
generator-genome *scoring* candidate).

## Hypothesis

Given a target repository with a test-capable manifest (e.g. `pyproject.toml`,
`go.mod`, or `package.json` with no `scripts.test`) but **zero** real test
files on disk, when `metaharness score <repo>` computes `compileConfidence`,
then the test-signal term of that score should require real evidence
(`profile.hasVerifiedTestFiles`, a `tests/`/`__tests__`/`test` directory scan,
or an authored `npm test` script) rather than crediting the manifest-inferred
`testCommands` list directly — subject to: (a) a repo with real verified
tests, or a human-authored `npm test` script, is unaffected (full credit
unchanged); (b) `taskCoverage`'s separate, pre-existing `testCommands.length`
term is untouched (different dimension, different semantics — "coverable
work surface" vs. "will build cleanly"); (c) 0 regressions elsewhere. Frozen
before implementation, not modified after evaluation began.

## Scan Findings — router

- `train.ts:120-141`'s `looFor()` adds `rows[h].scores[pickId]` into a
  leave-one-out total without checking the picked candidate id actually has
  a score in that held-out row; `Router.fromExamples` (index.ts:122-135)
  explicitly supports sparse per-candidate rows, so a real sparse dataset can
  silently inject `NaN` into the LOO comparison with no error. Same block has
  two vestigial `void`-ed dead variables (`pickPred`, `pickCost`, line 127/140).
- `calibration.ts:56-59`'s `round6` doesn't normalize `-0` to `0`, unlike
  `turn-credit/belief.ts:18-23`'s sibling `round6` (which explicitly does, for
  exactly the "byte-stable digest" reason `calibration.ts`'s own doc comment
  at line 141-144 claims for itself) — a `gap` of exactly 0 from the negative
  side can leak a signed zero into a digested calibration report.

## Scan Findings — turn-credit

- `cli.ts:51`'s `usesPairs` check uses `.some()` then casts the *whole*
