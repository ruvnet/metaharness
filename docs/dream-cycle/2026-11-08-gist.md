# Security-Adversarial SOTA Report — 2026-11-08

**TL;DR:** `harness threat-model`, MetaHarness's security/compliance artifact for MCP tool
surfaces, reports a headline "Allowed tools: 0 / Denied tools: 0" for any harness whose
MCP tool surface is declared only via the repo's own host-agnostic `.harness/mcp-policy.json`
schema — which is 8 of the 10 hosts this generator supports. It silently fabricates a
confident-looking "nothing is allowed" fact instead of surfacing the real tool grants. This
is exactly the named anti-pattern CWE-636 ("Not Failing Securely") and the MCP spec's own
"scope inflation blindness" risk, measured at scale by arXiv:2507.06250 (1,438/2,562 real
MCP servers carry unreviewed network/system privileges). Fixed by making the counters
`number | null` and printing an explicit "N/A — role-scoped policy" line instead of a
fabricated `0` for hosts that don't use flat allow/deny lists. Independent critic: pending
(see Evaluation).

## MetaHarness Current Capability

`packages/create-agent-harness/src/threat-model.ts`'s `buildThreatModel()` computes its
headline `allowedTools`/`deniedTools` counters *only* from `.claude/settings.json`'s
`permissions.allow`/`.deny` string arrays (lines 78-82). The dangerous-capability booleans
(`allowNetwork`/`allowShell`/`allowFileWrite`/`secretsReachable`) are read correctly from
the host-agnostic `.harness/mcp-policy.json` via `mcp-scan.ts`'s `scanMcp()` — so the tool
is only half-blind. Confirmed live: `packages/arc-agi-3-chatgpt` (a real, shipped example
targeting ChatGPT, not Claude Code) declares a 17-unique-tool, 3-role MCP surface entirely via
`.harness/mcp-policy.json`'s `allowedTools` map and `mcp-capabilities.json`'s `tools` field
— `harness threat-model packages/arc-agi-3-chatgpt` reports "Allowed tools: 0, Denied
tools: 0" for it today, with no warning. An independent architecture-review pass confirmed
(`host-config.ts` lines 109-266) that 7 of the other 9 hosts (codex, hermes, openclaw,
copilot, opencode, github-actions, prime-agent) have **no flat per-tool allow/deny concept
on disk at all** — `.harness/mcp-policy.json`'s role-keyed `allowedTools` is the *only*
place such scoping exists for them, and it is read by zero files in the package (confirmed
via repo-wide grep). `mcp-capabilities.json` — ADR-022's own "capability manifest hosts can
inspect" — is likewise read by zero files.

Genuine gap, not solved-and-unpublished for peer *frameworks* (LangGraph/AutoGen/CrewAI
don't solve this either) — but a cluster of dedicated third-party MCP scanners already
demonstrates host-agnostic multi-format scanning as a working pattern. MetaHarness already
owns a host-agnostic policy schema (`.harness/mcp-policy.json`) that its own security tool
doesn't read — it has less excuse than the peer frameworks that have no such schema at all.

## Hypothesis

Given a generated harness directory whose MCP tool surface is declared only via
`.harness/mcp-policy.json`'s role-keyed `allowedTools` map (true for 7 of 9 non-Claude-Code
hosts) with no `.claude/settings.json` `permissions` block present, when
`buildThreatModel()`'s `allowedTools`/`deniedTools` fields are changed from `number` to
`number | null` — set to `null`, with `formatThreatModel` printing an explicit "N/A —
role-scoped `mcp-policy.json`, not flat allow/deny" line, whenever no flat permission data
exists but a non-empty role-scoped `allowedTools` map is present — then `harness
threat-model` stops fabricating a `0` for those hosts, relative to the current
unconditional-`0` baseline, subject to: (a) Claude Code's existing settings.json-based
counting and its genuine `0` semantics stay byte-identical; (b) `secretsReachable` /
`dangerousPermissions` / `verdict` / `exitCode` (already correct) are untouched; (c) zero
regression in the existing `threat-model`/`mcp-scan` suites; (d) the live CLI smoke test
against the real `packages/arc-agi-3-chatgpt` fixture flips from `0/0` to the new `N/A`
line.
