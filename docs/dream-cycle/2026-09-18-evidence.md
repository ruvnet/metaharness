## OBSERVATION

`packages/create-agent-harness/src/mcp-scan.ts`'s `no-secret-guard` finding
and `packages/create-agent-harness/src/threat-model.ts`'s
`secretsReachable`/verdict computation both independently used an
unanchored regex, `deny.some((d) => /\.env/.test(d))`, to decide whether a
`.claude/settings.json` `permissions.deny` entry actually blocks the real
`.env` secrets file. Because `.test()` matches anywhere in the string, a
deny rule that targets only the harmless, commonly-committed
`.env.example` template (`Read(./.env.example)`) satisfied the check —
producing a false "guarded" verdict even when a broad `Read(*)` allow-rule
leaves the real `.env`/`.env.local` fully readable.

Confirmed live before any fix: a hand-built fixture directory
(`allow: ["Read(*)"]`, `deny: ["Read(./.env.example)"]`, otherwise
compliant default-deny policy) produced, via the real built CLI
(`dist/harness-bin.js`), `Secrets reachable: no` and `Verdict: clean
(exit 0)` for `harness threat-model`, and no `no-secret-guard` finding
from `harness mcp-scan` — a clean bill of health for a harness whose real
credentials are fully exposed to any tool with read access.

This is CWE-777 ("Regular Expression without Anchors") in a live
security-verdict path — the same underlying weakness class OWASP's Top 10
for Agentic Applications 2026 motivates as "Excessive Agency" (risen to
#3), and the same class 2026 fixes to gitleaks-adjacent allowlist regexes
(`uinaf/ffss` PR #141, `uinaf/agent-skills` PR #80) independently confirm
is still live in agent-tooling repos this year, not a solved problem.

## MEASUREMENT

- **Fix**: extracted a single, exported `envSecretGuarded(deny: string[])`
  helper in `mcp-scan.ts` with a left- and right-anchored regex,
  `/(?:^|[(/])\.env(?:$|[)/*]|\.\*)/`, requiring `.env` to start at a
  string/path boundary (`^`, `/`, or `(`) and to be followed by end-of-
  string, `)`, `/`, `*`, or a literal `.*` wildcard — matching exactly the
  two shapes the repo's own generator (`host-config.ts`) emits
  (`Read(./.env)`, `Read(./.env.*)`) plus bare `.env`/`**/.env` for
  hand-edited configs. `threat-model.ts` now imports and reuses this
  helper instead of keeping its own independently-drifting copy of the
  same regex — same consolidation pattern PR #276 (2026-09-03) applied to
  `mcpEnabled` detection.
- **Red proof**: `git stash` on the 2 `src/*.ts` files only (new tests
  kept) → 3 new assertions fail: 2 direct `expect().toBe()` failures
  reproducing the false "clean"/"guarded" verdict on the `.env.example`
  fixture, 1 `envSecretGuarded is not a function` (no such export
  pre-fix). 26 pre-existing tests in the same 2 files unaffected.
- **Green**: restored → all pass. Full `create-agent-harness` suite:
  **572→575/577** passed (+3 assertions inside existing/new `it` blocks,
  2 pre-existing skips unchanged, 0 regressions across all 45 test
  files). `tsc --noEmit -p packages/create-agent-harness/tsconfig.json`
  clean both before and after.
- **Live CLI smoke test** (real rebuilt `dist/harness-bin.js`, not mocks,
  against the same fixture): post-fix, `harness mcp-scan` reports
  `[MED ] Secrets not denied`; `harness threat-model` reports `Secrets
  reachable: yes` / `Verdict: high (exit 2)`.
- `npm audit --omit=dev --audit-level=high`: 1 pre-existing moderate
  advisory, unchanged — no dependency touched by this fix.
- Repo-wide grep for other call sites of the same detection pattern
  (`score.ts`, `oia-manifest.ts`, `audit-cmd.ts`, `genome-scorers.ts`):
  none reference `.env` at all. One unrelated `.env`-substring pattern in
  `packages/darwin-mode/src/repo_profiler.ts` (`RISK_PATTERN`) flags files
  for human review — over-inclusive by design, the safe direction, not the
  same bug class — no action taken there.

### Independent adversarial critique (2 rounds, same night)

- **Round 1**: a separate subagent, no shared session context, was handed
  only the diff and the claimed bug/fix description and told to be
  adversarial. It independently re-derived the bug by reading the pre-fix
  code, tested the new regex against realistic deny-list strings itself,
  ran the full test suite and `tsc` itself rather than trusting the
  numbers it was given, confirmed no reward-hacking (`git diff` on both
  test files is pure addition, no assertion weakened, no gold data
  touched), and confirmed the `.env.local`-only design choice (narrower,
  unverifiable guards don't count) is a defensible conservative default.
  It then found a real residual gap: the round-1 regex was only
  right-anchored, so `Read(./secrets.env)` / `Read(./myapp.env)` —
  unrelated files that merely *end* in `.env` — still counted as
  "guarding" the real harness `.env`, reproducing a narrower version of
  the same false-guard bug. Verdict: **ACCEPT-WITH-CAVEATS**, recommending
  a fast-follow to left-anchor the regex.
- **Round 2 (same night, not deferred)**: left-anchored `ENV_GUARD_RE` per
  the critic's exact finding, added its exact repro cases
  (`Read(./secrets.env)`, `Read(./myapp.env)` → false;
  `Read(.env)` → true) as tests, re-ran the full suite (575/577, 0
  regressions) and `tsc` (clean) against the round-2 fix, and re-verified
  live via the rebuilt CLI. This mirrors PR #276's own round-2-critic
  precedent (a missed `.mcp.json` case, closed same PR) rather than
  shipping the round-1 gap disclosed-not-fixed.

## INFERENCE

This is the same underlying weakness (CWE-777) that PR #276
(2026-09-03) closed for this codebase's *MCP-surface-detection* field
(`mcpEnabled`), recurring one field over in the same two files for
*secret-guard-detection* (`guardsEnv`) — both were independently
duplicated, unanchored regex checks feeding a live security verdict. The
2026 external evidence (OWASP's Excessive Agency risk climbing to #3;
real 2026 gitleaks-allowlist-anchoring fixes in agent-tooling repos)
converges on the same principle: regex-based permission/secret-detection
logic in agent tooling is an active, currently-being-patched risk
category industry-wide in 2026, not a one-off local bug. The
consolidation-into-one-helper fix (rather than patching both files'
copies independently) is deliberately chosen to close the *drift* vector
that let the same bug class recur here twice already (#276, then
tonight) — a future third recurrence would need to independently
reintroduce a second unanchored copy of `envSecretGuarded`'s logic rather
than just missing one call site.
