# Dream Cycle 2026-09-03 — Flywheel Evidence Record

Not a flywheel-domain candidate (CLI security-tooling correctness fix, not

## OBSERVATION

`packages/create-agent-harness/src/threat-model.ts`'s `buildThreatModel()`
computed `mcpInUse` from only `.harness/mcp-policy.json`/`.mcp.json`,
while the sibling function it calls internally, `scanMcp()`
(`mcp-scan.ts`), additionally checked `.claude/settings.json`'s
`mcpServers` key. A harness registering MCP only via `.claude/settings.json`
therefore got `mcpInUse: false`, and `formatThreatModel()`'s early return
("mcp surface: off ... MCP is not in use") silently discarded the real
findings `scanMcp()` had already computed one line above. This exact gap
was flagged, not fixed, by the 2026-08-28 security-adversarial night
(PR #243's Recommended Next Steps #4). Confirmed live by direct source
inspection (`grep -n "mcpServers" packages/create-agent-harness/src/threat-model.ts`
returned zero matches pre-fix) and by a new test suite (`threat-model.test.ts`,
previously nonexistent for this file) that fails non-vacuously against the
pre-fix code.

An architecture-review subagent (no shared authorship context) additionally
found a live downstream consumer: `packages/agntcy/src/identity/from-mcp-scan.ts`
(ADR-240) derives AGNTCY verifiable-credential badges directly from
`ThreatModel.mcpInUse` — a `settings.json`-only harness was silently
under-issued its `mcp.read` badge, extending the bug's blast radius beyond
`harness threat-model`'s CLI output.

## MEASUREMENT

- **Round 1 fix**: `mcpInUse = scan.mcpEnabled` (reuse `scanMcp()`'s own
  check). Red/green: 3/6 new tests fail pre-patch, 6/6 pass post-patch;
  full `create-agent-harness` suite 560/560 (2 skipped), 0 regressions,
  `tsc --noEmit` clean.
- **Independent adversarial critic** (fresh sub-agent, no authorship
  context) reviewed Round 1 cold and returned REJECT: `scanMcp()` itself
  never read `.mcp.json`, so the wholesale swap silently dropped
  `.mcp.json`-only registrations — verified empirically by the critic
  (built a `.mcp.json`-only fixture, confirmed `mcpInUse: false`
  post-Round-1) — and flagged one new test as tautological
  (`tm.mcpInUse === scan.mcpEnabled`, comparing the implementation to
  itself).
- **Round 2 fix**: moved the third detection signal (`.mcp.json`) into
  `scanMcp()` itself, so `mcpEnabled` ORs all three surfaces in the one
  place downstream callers rely on. Replaced the tautological test with an
  explicit expected-value table (5 cases, each surface independently) and
  added a dedicated non-tautological `.mcp.json`-only regression test,
  plus 2 new isolation tests directly in `mcp-scan.test.ts`.
  `threat-model.test.ts`: 7/7 (was 6). `mcp-scan.test.ts`: 17/17 (was 15).
  Full `create-agent-harness` suite: 563/563 (2 skipped), 0 regressions.
  `tsc --noEmit`: clean. Downstream consumer `packages/agntcy` suite: 82/82
  passed, unaffected.
- **Second critic pass**: dispatched with Round 2's fix applied, instructed
  to re-verify from scratch (fresh read of both files, re-run the suite
  itself) rather than trust a summary. Final verdict recorded in the PR's
  Adversarial Critique / Witness sections.

## INFERENCE

The bug is a concrete instance of a known-shape security-tooling failure —
two components answering the same "is X in use?" question from different,
independently-maintained subsets of the same config surface (2026 research
frames this as adjacent to "parser differentials" and SAST
detection-coverage gaps, though no source names this exact intra-codebase,
same-tool variant). Fixing it by collapsing to one authoritative check
(rather than adding a second OR-branch in `threat-model.ts`) is the
correct SOTA-aligned mitigation implied by that research: single source of
truth, not two independently-drifting ones. The critic's Round 1 rejection
demonstrates the fix genuinely needed adversarial pressure to reach that
state — the first "obvious" fix reintroduced the same bug class from a
different angle.
