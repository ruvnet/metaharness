# flywheel-promotion SOTA Report — 2026-08-26

**TL;DR**: `@metaharness/flywheel`'s `verifyReplayBundle()` — the function an
external reviewer uses to trust a promoted policy lineage with *zero trust in
the producer* — re-executes the promotion gate on each PROMOTED commit's
sealed scores (ADR-235), but **never supplied the anti-Goodhart anchor clause**
to that re-run. A promotion that regressed the frozen, never-optimized-against
anchor suite replayed clean. This exact gap was disclosed-not-fixed by the
last flywheel-promotion night (2026-08-16, PR #205, still unmerged). 2026
research confirms replayable anti-Goodhart guards are a genuinely
under-addressed seam even in academic verifiable-ML-pipeline work (not a
solved-but-unpublished problem) — closest analog: SLSA/in-toto provenance
verifies *artifact* authenticity, not *re-execution of a guard predicate*
over sealed scores. Fixed: `gateReExecutes` now reads the root commit's
sealed `anchorScore` and re-checks the anchor clause. 2 files, 52
insertions / 2 deletions. Independent adversarial critic: **ACCEPT**.

## MetaHarness Current Capability

`meetsPromotionRule` (gate.ts) is a 5-clause conjunctive gate: primary
non-regression, strict no-op improvement, cost/win non-worsening, no safety
regression, and an **anchor** clause — a frozen, never-optimized-against
suite a winner must not regress (the anti-Goodhart guard). `run.ts` computes
and enforces this live via a `rootAnchor` closure var. `verifyReplayBundle`
(replay.ts) lets a third party re-derive trust from a `ReplayBundle` alone:
receipts verify, lineage reaches root contiguously, every promoted node is
actually PROMOTED, the gate fingerprint is unchanged, and — the ADR-235
step — every PROMOTED commit's *sealed* `baselineScore`/`candidateScore`
must **re-pass** the rule. That re-run never built `PromotionEvidence.anchor`
— `LineageCommit.anchorScore` (already carried, already sealed on the root
and every promoted node) was simply never read by replay. Confirmed via
direct inspection (run.ts:92-193, replay.ts pre-fix) and via a real bundle
(`packages/radio/.radio-flywheel/replay-bundle.json`) whose root carries a
sealed `anchorScore` that replay never consulted.

Six of six named agent frameworks show "No" for a genuinely-replayable
anti-Goodhart anchor — not because the field solved this quietly elsewhere,
but because none of them ship an autonomous self-improvement *promotion*
loop at all (orchestration frameworks, or human-in-the-loop diff review).
The one adjacent discipline that does sign+replay (SLSA) verifies a
different thing (artifact build provenance, not a multi-clause gate
decision). Given the SWE-bench leaderboard-integrity crisis above, this is a
genuine, current differentiator, not table stakes.

## Hypothesis

Given `verifyReplayBundle`'s `gateReExecutes` step, which re-runs
`meetsPromotionRule` on each PROMOTED commit's sealed `baselineScore`/
`candidateScore` but never supplies `evidence.anchor`, when the re-run is
extended to read the root commit's sealed `anchorScore` (the run's frozen
anti-Goodhart bar, already present on every real bundle) and each promoted
commit's own sealed `anchorScore`, constructing `evidence.anchor` before
re-gating, then a bundle whose promotion regressed the frozen anchor should
FAIL replay (`gateReExecutes: false`) where it previously passed silently,
while every honestly-produced bundle continues to PASS unchanged, subject
to: (a) zero regression in the existing 47-test suite, (b) purely additive
to `ReplayVerdict`/no new required bundle fields, (c) `meetsPromotionRule`
itself untouched, (d) diff materially under 150 lines, (e) the fix matches
the anchor axis to the SAME sealed-field trust tier as the pre-existing
primary/noopRate/costPerWin re-execution (not new signature coverage —
that remains a disclosed, separate, larger future gap).
