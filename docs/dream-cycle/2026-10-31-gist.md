# Flywheel-Promotion SOTA Report — 2026-10-31

TL;DR: `@metaharness/avo`'s own independent canonicalization primitive
(`packages/avo/src/crypto.ts`'s `canonical()`) — which feeds `sha256()`/
`transitionHash()`/`checkpointHash()`/`verifyReceipt()`/
`verifyVariationCheckpoint()`, i.e. the Ed25519-signed `ActionReceipt`/
`VariationCheckpoint` trust chain `GovernedVariationOperator` signs on every
action of a real self-evolution run — was still carrying both gaps that
`@metaharness/flywheel`'s `canon()` was hardened against on 2026-10-16
(unbounded recursion depth) and 2026-10-21 (NaN/Infinity/-Infinity collapsing
to the same `"null"` token `JSON.stringify` gives real `null`, letting a
tampered non-finite value swap for `null` in a signed field undetected).
These two gaps were disclosed-but-deliberately-unfixed in #438 (2026-10-26,
open/unmerged), which ported the same hardening to two *other* sibling
duplicates (`avo/flywheelGate.ts`, `turn-credit/receipt.ts`) and flagged
`crypto.ts` as the next, more central target — it feeds the actual live
AVO self-evolution loop, not an additive/unused gate mirror. Fixed tonight:
ported both mitigations verbatim, plus fail-closed try/catch on the two
`verify*` boolean predicates so a now-uncanonicalizable value fails the check
cleanly instead of throwing out of a `.every(verifyReceipt)` call.

**On "None across the board":** none of LangGraph, AutoGen, CrewAI, OpenAI
Agents SDK/Codex, Claude Agent SDK, or DSPy/GEPA has published anything on
receipt canonicalization or numeric-encoding safety in 2026 — a genuine open
gap, not solved-but-unpublished. Orchestration-framework governance reviews
score audit-trail *presence*, never byte-level signing hygiene; that work is
happening one layer down, in narrow standards drafts (x402, agent-audit-trail)
and small single-maintainer trust-layer projects (titan-gate, eval-conductor,
OpenFlyWheel, FIPSign), not in the frameworks themselves — consistent with
treating canonicalization as serialization plumbing beneath the framework's
abstraction level, exactly MetaHarness's own situation with (as of tonight)
**four** independently-duplicated `canon()`/`canonical()` implementations.

**Synthesis:** MetaHarness's Ed25519 + canonical-JSON + replay design is at or
slightly ahead of the published niche field (no competitor documents
NaN/Infinity/depth edge cases) but behind DSSE's PAE approach, which avoids
the canonicalization-ambiguity class of bug altogether by construction.
Hardening canonicalization edge cases is a well-known best practice elsewhere
(RFC 8785 mandates rejecting non-finite numbers) — not a MetaHarness-specific
catch-up item, but a known-correct pattern MetaHarness is still finishing
rolling out internally.

## Hypothesis

Given `packages/avo/src/crypto.ts`'s `canonical()` (feeding the live
Ed25519-signed `ActionReceipt`/`VariationCheckpoint` trust chain), when it is
hardened with the same two mitigations already ACCEPTed and merged to main in
`@metaharness/flywheel`'s `canon()` (`MAX_CANON_DEPTH=64`; distinct-rejection
of NaN/Infinity/-Infinity instead of collapsing to `JSON.stringify`'s
`"null"`), then `canonical()`/`sha256()`/`transitionHash()`/`checkpointHash()`
detect a crafted deeply-nested payload or a non-finite-for-null substitution
that previously collided or crashed silently, subject to: byte-identical
output for every existing finite/string/bool/null/array/object value (0
regressions); the change stays additive/narrowing only; a new dedicated
`crypto.test.ts` non-vacuously proves the fix (red before, green after)
rather than relying on indirect coverage via operator/claim-gate tests.

## Independent Adversarial Critique

Fresh subagent, no visibility into this session's reasoning, own repro.
**Verdict: ACCEPT-WITH-CAVEATS.**

- Confirmed the diff is correct (depth-bound/non-finite checks fire in the
  right order, `depth+1` threaded through both array/object recursion) and
  complete within `packages/avo` (grepped every `canonical`/`sha256`/
  `transitionHash`/`checkpointHash` call site — all route through the
  hardened function, no bypass).
- Independently reproduced red→green itself (own stash/pop cycle, own test
  run) — not taken on faith.
- **Caveat 1 (disclosed, not fixed)**: `operator.ts`'s live hot-path call
  sites (`sha256(this.options.invariants)` in the constructor/loop,
  `transitionHash(...)` inside `transition()`) are **not** wrapped in
  try/catch, unlike the two `verify*` predicates — a non-finite value
  reaching them now **throws and aborts a real run**, where before it would
  have silently signed a corrupted/ambiguous receipt. The critic checked
  every realistic source of such a value (`ProtectedInvariants` is static
  config; `archive.ts`/`repository.ts`/`supervisor.ts`'s divisions are all
  guarded; the one unguarded division, `swebench.ts:116`, feeds a benchmark
  report, not a signed receipt) and judged real-world likelihood low — but
  it is a genuine, undisclosed fail-loud-vs-fail-silent behavior change,
  deliberately left as-is to keep tonight's diff to one conceptual change
  (hardening the primitive + the two predicate call sites whose documented
  contract is "never throw"), not extended into `operator.ts`'s own
  run-loop error handling.
- **Caveat 2 (new disclosure)**: two more sibling duplicates of the identical
  bug exist and were NOT fixed tonight: `packages/horizon/src/checkpoint.ts`
  (`canonical()`, same unguarded shape, feeding `hashCheckpoint`/
  `verifyCheckpoint` for `HorizonCheckpoint.stateHash` — `verifyCheckpoint`
  has **no try/catch at all**, worse than avo's pre-fix state) and
  `packages/harness/src/receipts.ts` (`canonical`/`sortKeys`, no depth bound,
  NaN/Infinity still collapse to `null`, used in the ADR-047 hash-chained
  receipt log). Both are real, live, uncaught instances outside the four
  files already known tonight — flagged below as next candidates.
