# MetaHarness Security-Adversarial SOTA Report — 2026-10-28

## TL;DR

MetaHarness ships two SPDX-2.3 SBOM generators — `harness sbom` (per-scaffolded-harness)
and `scripts/sbom.mjs` (meta-repo level). Neither correctly populated **Component Hash**,
a field the 2026-07-29 CISA/NSA/FBI "Minimum Elements for a SBOM" baseline (superseding
NTIA's 2021 version) added to its required field set. `sbom-cmd.ts` omitted the field
entirely. `scripts/sbom.mjs` was worse: it emitted a syntactically valid `checksums`
entry that was **fabricated** — a SHA1 hash of the npm `integrity` (SRI) string itself,
or of a placeholder `name@version` string when integrity was missing — never a real
digest of the package's actual content. Both are fixed tonight by decoding the real
SRI digest npm's own `package-lock.json` already carries, with an honest
"component hashes: X/Y" disclosure instead of silent gaps or manufactured data.

## MetaHarness Current Capability (before tonight)

- `packages/create-agent-harness/src/sbom-cmd.ts` (`harness sbom`): read `package-lock.json`'s
  `integrity` field into nothing — the `SpdxPkg` type had no `checksums` field at all.
- `scripts/sbom.mjs` (meta-repo `node scripts/sbom.mjs`): emitted
  `checksums: [{ algorithm: 'SHA1', checksumValue: createHash('sha1').update(p.integrity ?? \`${p.name}@${p.version}\`).digest('hex') }]`
  — a hash *of the SRI string*, not of the artifact. Passes SPDX shape validation; conveys
  zero real provenance; a careless auditor could mistake it for a verifiable checksum.
- Both gaps were disclosed-not-fixed on 2026-10-18 (#413/#414's Security Review) and
  2026-10-23 (#430/#431's Scan Findings) — this is the third night naming the SBOM-hash
  gap but the first to actually implement the fix (prior two were deferred in favor of
  smaller/different candidates that night).

## Hypothesis

Given a scaffolded harness or the meta-repo itself with an npm `package-lock.json`
present, when `harness sbom` and `scripts/sbom.mjs` are extended to decode each
package's real `integrity` (SRI) field into an SPDX `checksums` entry, then every
package with real lockfile integrity data should carry a verifiable hex digest that
reproduces independently from the raw SRI bytes — relative to the pre-fix baseline
(no checksum field, or a SHA1-of-the-SRI-string fabrication) — subject to: (a) a
package with no real integrity data gets no checksum at all, never a fabricated one;
(b) the strongest of multiple space-separated SRI entries is used; (c) 0 regressions
in dev-dependency disclosure, apps/web-ui dedup, or cargo package handling; (d) every
existing SPDX shape/validation test stays green. Frozen before implementation.
