# Generator-Genome SOTA Report — 2026-10-10

TL;DR: `apps/web-ui`'s repo→harness recommender (`recommendPlan()`) could not structurally
recommend `mcp: 'off'` for ANY input repo — every one of its 8 archetypes hardcoded MCP to
`'local'` or `'remote'`. Unlike the identical bug's already-fixed-but-unmerged sibling in the
CLI package, this instance has REAL consequences: it feeds `buildScaffold()`'s file-emission
gate, so every signal-less repo run through the web importer got a full governed MCP server it
never needed. Fixed with the same override pattern as the pending CLI fix (PR #376, unmerged),
ported to this file's array-shaped `requiredSignals`. 2026 empirical research (two new arXiv
papers) shows this is not a local quirk: 15-18% of real agent-harness repos carry a confirmed
over-permission defect of this shape, and tonight's competitor survey found no comparable
framework that forecloses the safe/off state as completely as this one did.

## MetaHarness Current Capability
`apps/web-ui/src/generator/repo.ts` mirrors `packages/create-agent-harness/src/analyze-repo.ts`
(the CLI file's own comment literally reads "mirrors apps/web-ui/src/generator/repo.ts") — both
implement the ADR-023 repo→harness importer with an 8-entry `ARCHETYPES` table and a weighted
scorer. ADR-022 defines `off` as a first-class MCP mode ("off is a first-class mode... a
memory-only or CLI-only harness is valid") and this file's own `McpPolicy` doc comment states
"every field defaults to the safe option; the harness author opts INTO capability, never out of
safety." Neither file's `recommendPlan()` honored that contract: every archetype hardcoded
`policy.mcp`/`a.mcp` to `'local'` or `'remote'`, so `'off'` was structurally unreachable. The
CLI-side half was already found and fixed on 2026-10-05 (issue #374, PR #375/#376) — verified
real against the `dream/2026-10-05-generator-genome` branch diff, but still unmerged — and that
night's critic escalated the `apps/web-ui` sibling as having *real*, not cosmetic, consequences
(the CLI package's scaffold step hardcodes `mcp:'local'` independently, making its instance
reporting-only). Tonight closes that sibling.

Why mostly "None": a genuine, narrow gap, not a solved-but-unpublished problem. These frameworks
treat tool/capability definition as explicitly author-driven by scope; none built a "guess your
capability tier from the repo" step, since a wrong guess is either a broken or an over-privileged
agent. Most real incidents of this shape (CVE-2026-49257, CVE-2025-49596, CVE-2026-55580/55581,
CVE-2026-9680, CVE-2025-64132) occur in deployed MCP *servers*, not generators — the problem has
shifted downstream, not been solved upstream. MetaHarness is the only generator found that
cannot itself reach the safe state.

## Hypothesis
Given a repo-readiness analysis for a target repo with zero real MCP signal, when
`recommendPlan()` (`apps/web-ui/src/generator/repo.ts`) is applied, then `HarnessPlan.mcp`
should be able to report `'off'` — and `buildScaffold()` should emit no `src/mcp/*` surface —
subject to: (a) an archetype requiring MCP signal (`requiredSignals` includes `'hasMcp'`) is
unaffected; (b) a repo with real MCP signal is unaffected regardless of which archetype wins;
(c) all other inputs produce byte-identical output; (d) 0 regressions in `apps/web-ui`'s suite.
Frozen before implementation; not modified after evaluation began.

## Evaluation
**Baseline (pre-fix):** new test `recommends mcp:off for a repo with zero MCP signal` fails
non-vacuously: `AssertionError: expected 'local' to be 'off'`. Independently reproduced by the
adversarial critic via an isolated revert of only `repo.ts` (correctly noting a naive
`git stash` of both files would remove the new test along with the fix and falsely appear to
reproduce nothing).
**Candidate (post-fix):** full `apps/web-ui` suite 72/72 passed (8 test files, 0 regressions),
`npx tsc -b` clean. All 8 `ARCHETYPES` entries manually enumerated: the 7 with
`policy.mcp:'local'` now report `'off'` under zero MCP signal (byte-identical when `hasMcp` is
true); the 1 `policy.mcp:'remote'` entry (`mcp-server-harness`, requires `'hasMcp'`) is
untouched in every case. Critic independently tried an adversarial input not in the existing
fixtures (a zero-MCP-signal Python repo, routing to `data-pipeline-harness`) and confirmed it
also reports `'off'` with zero `src/mcp/*` paths emitted — generalizes, not overfit to one
fixture. `evaluated: accepted`.

## Security Review
Direction is strictly more restrictive (fewer MCP surfaces exposed by default for signal-less
repos); `'off'` was already a first-class, fully-handled value throughout `scaffold.ts`/`mcp.ts`
and every host adapter — simply unreachable from this one function before the fix. No
downstream code assumes `primitives.mcp` is always non-`'off'`; critic found no crash risk.
`HarnessBuilder.tsx`'s manual Off/Local/Remote toggle already existed as a safety valve even
under the bug — a bad-default defect, not an unfixable lock.

## Scan Findings — router

(sparse-row NaN propagation in `trainRouter` via unguarded `r.scores[id]` indexing, unlike

winner after a mutation that should flip it to 0.2. Not fixed tonight — good candidate for a
dedicated router night.
