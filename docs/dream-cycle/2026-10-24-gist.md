# host-adapters (kernel) SOTA Report — 2026-10-24

TL;DR: `kernel-js`'s `SelfEvolvingRouter.ensureLoaded()` (ADR-014's opt-in
self-evolving tier routing) is a lazy-async singleton with no in-flight
guard: two concurrent first-calls both see `this.impl === null` and each
unconditionally constructs its own `LearnedWeights` instance — one
construction (and the WASM-backed cost that went into it) is silently
discarded when the other overwrites `this.impl`. Disclosed, not fixed, on
2026-10-19; confirmed and fixed tonight by caching the in-flight promise
instead of the resolved value — the textbook fix for this bug class.
Investigated and explicitly did **not** confirm a stronger "permanently
lost routing-weight update" claim: under this repo's Node/vitest engine,
both concurrent calls' updates consistently land on whichever instance
survives the race, for the 2-call shape tested. That's reported as a
disclosed theoretical risk, not an independently reproduced one — the
fix removes the duplicate construction regardless of which claim holds.

## MetaHarness Current Capability

`packages/kernel-js/src/self-evolution.ts`'s `SelfEvolvingRouter` wraps
the kernel's 3-tier router with learned, outcome-driven weights (ADR-014,
opt-in). `ensureLoaded()`:

```ts
async ensureLoaded(): Promise<void> {
  if (!this.config.enabled) return;
  if (this.impl) return;
  const emergent = await loadEmergent();
  if (emergent) {
    this.impl = new emergent.LearnedWeights({ tiers: [...] });
  }
}
```

has no re-check after the `await`, and no shared in-flight marker — the
classic "check, await, write, no re-check" shape. `loadEmergent()` itself
has the identical shape at the module level (`_emergent` cache), but its
write is idempotent (same resolved module for every caller) so it isn't
independently harmful; the instance-level `this.impl` write is **not**
idempotent (each caller constructs a *distinct* object), which is where
the real bug lives. **Zero in-repo production call sites** wire
`SelfEvolvingRouter` in today (confirmed via repo-wide grep for
`SelfEvolvingRouter`/`recordOutcome`) — it's an exported, tested, but not
yet production-reachable kernel primitive; a future caller (e.g.
`packages/router`) wiring it in under real concurrent traffic would hit
this race on day one.

Separately, `memory-rvf.ts`'s `ensure(ns)` (per-namespace RVF index
creation) has the identical shape, disclosed 2026-10-19 and re-confirmed
tonight as still unreachable: `@ruvector/rvf` fails to resolve in this
repo's install (`Cannot find package`); only the unrelated
`@ruvector/rvf-node` binary is installed. Not fixed tonight — fixing
dead code gives no real before/after proof.

## Hypothesis

Given a `SelfEvolvingRouter` with `enabled: true`, when two or more
`recordOutcome()` calls race through `ensureLoaded()` before either sets
`this.impl`, then — with the in-flight-promise cache — exactly one
`LearnedWeights` instance should be constructed, matching a single
sequential call, subject to: (a) the EMA fallback path stays provably
non-racy; (b) all pre-existing `self-evolution.test.ts` assertions pass
unchanged; (c) `disabled`-mode pass-through is untouched; (d) zero API
changes to `@ruvector/emergent-time` usage.

## Benchmarks / Evaluation

**Candidate**: `packages/kernel-js/src/self-evolution.ts` — added a
private `implPromise` cache; `ensureLoaded()` now does
`this.implPromise ??= loadEmergent().then(cb).catch(resetAndRethrow)`
and returns it, instead of re-entering the unguarded await every time
(the `.catch()` was added in round 2, see below). **~20 lines changed, 1
file.** New test file `self-evolution-concurrency.test.ts` (**+3
tests**), mocking `@ruvector/emergent-time` via `vi.doMock` so both the
EMA-fallback and real-impl code paths are exercised deterministically
regardless of the real package's installed API shape (which has drifted
— see below).

- **Baseline** (`main`, confirmed via `git stash` on just the source
  file): the "constructs exactly one `LearnedWeights` instance under 2
  concurrent first-calls" test fails non-vacuously — `expected 2 to be
  1` — reproduced 5/5 runs.
- **Candidate**: same test passes; full `kernel-js` suite **62→65/66**
  (3 new, +3, 1 pre-existing unrelated skip, 0 regressions); `tsc
  --noEmit` clean; `npm run build` clean.
- **Downstream sweep**: full monorepo `vitest run` — **3558 passed / 60
  skipped**, 3 failures, all confirmed pre-existing on unpatched `main`
  too (2 real `npm audit` high-severity advisories in unrelated
  dependencies — `body-parser`, `zod` — and 1 live-OpenRouter test
  failing on a deprecated model, `Qwen3 8B` → 404); **0 regressions
  attributable to this candidate**.
- **Investigated and NOT claimed**: a true "permanently lost update"
  (one call's `.update()` surviving on a discarded instance while the
  final `this.impl` never receives it) — tested directly with
  distinguishable, non-default reward values for 2 concurrent calls;
  deterministically, in 5/5 runs, both updates landed on whichever
  instance survived. Reported as a disclosed risk of the same race (a
  3rd concurrent call, or any `async` work inside the constructor, could
  still expose it), not as independently reproduced data loss. Removed
  a draft test that would have falsely implied this was confirmed.

## Adversarial Critique (round 2)

A fresh, cold-context critic independently re-ran the red→green proof
(not trusted from the diff), confirmed zero production call sites for
`SelfEvolvingRouter` (correctness hygiene for unwired ADR-014 "exotic"
code, not a production-incident fix), and hand-traced N=3 concurrent
calls to show a true lost-update is *structurally* unreachable for this
code shape — stronger than the "investigated, not reproduced" claim
above. It caught one real, undisclosed gap: the fix cached `implPromise`
even on a rejected construction, permanently poisoning every future call
with the same error instead of retrying. **Verdict: ACCEPT.** Closed
same night: `.catch()` now clears `implPromise` on failure; added a
regression test (confirmed to fail without the reset, pass with it).
Final: kernel-js suite 62→65/66 (+3, 1 pre-existing unrelated skip, 0
regressions).
