# Dream Cycle Evidence Record — 2026-10-06 (flywheel-promotion)

Durable evidence per STEP 13. No flywheel-gate/receipt production call site applies to this candidate
itself (it changes the *verifier*, not a gated promotion); classified per STEP 13 taxonomy.

## OBSERVATION

`packages/flywheel/src/replay.ts`'s `verifyReplayBundle()` lets an external reviewer establish trust in
a promotion lineage with claimed zero trust in the producer. `receipts.ts`'s `verifyReceipt(r)` checks
`r.signature` against the Ed25519 public key *embedded in `r.publicKey` itself* — it proves the receipt
is internally self-consistent, never that `r.publicKey` belongs to anyone the reviewer actually trusts.
ADR-274 (2026-09-01) disclosed this precisely, as an explicit out-of-scope residual: "an attacker could
in principle self-sign an entirely fabricated bundle with a fresh keypair... a distinct, larger
follow-up... not attempted here." `packages/avo/src/flywheelGate.ts` (ADR-271) already solves this exact
problem one package over, for the AVO→gateway path, via a `FLYWHEEL_TRUSTED_PUBLIC_KEYS_JSON` allowlist.

## MEASUREMENT

Constructed a fresh, unrelated Ed25519 keypair ("the forger") with `makeSigner()`. Fabricated a complete
`ReplayBundle` (root commit + one rejected candidate) self-signed entirely by the forger key.
`verifyReplayBundle(bundle)` with no options returns `pass: true` — confirmed directly, pre-fix and
post-fix alike (this is the *documented, intentional* default-unchanged behavior, not a bug). Pre-fix,
there was no way to make it return anything else: no parameter existed to express "but only if signed by
a key I recognize." Added `opts.trustedPublicKeys?: readonly string[]`; measured 6/6 new unit tests fail
non-vacuously against the pre-fix source (`git stash` on `replay.ts`+`cli.ts` only, tests kept) with
`checks.trustedSigner === undefined`, then pass post-fix. Live CLI proof against the real committed
`experiments/signal-flywheel/bundle.json`: `--trusted-key <real-signer-key>` → PASS; `--trusted-key
<bogus>` → `FAIL (trustedSigner)`, exit 1; no flag → PASS, unchanged. All 7 real committed `ReplayBundle`
files in the repo re-verified unchanged with no flag supplied.

## INFERENCE

The gap was real and exploitable as described, not merely theoretical: a concrete fabricated-bundle
repro produces a clean PASS today with no mechanism to express otherwise. The fix closes it only when a
caller opts in, by design (see Alternatives Considered in ADR-319) — this is a capability addition, not
a default-behavior hardening, which is the correct scope for a backlog-pressured night per STEP 1.1.

## HYPOTHESIS (frozen before the fix, see gist)

Given a `ReplayBundle` signed by a key not on the reviewer's explicit allowlist, when
`verifyReplayBundle` is invoked with `opts.trustedPublicKeys` supplied, then verification must fail with
reason `trustedSigner`, subject to: (a) omitted is byte-identical to today; (b) an allowlisted signer
still passes; (c) an empty array means "not supplied"; (d) a malformed/missing receipt fails closed,
never throws; (e) 0 regressions.

## DECISION

**ACCEPT.** Added the opt-in allowlist + CLI flag. Independent adversarial critic (fresh subagent, cold
read, no access to this session's reasoning) returned **ACCEPT-WITH-CAVEATS** on the first draft:
confirmed the core mechanism is sound (signature validity and signer trust are independently required —
no bypass found by copying a trusted key string without its private key), confirmed `all_commits`
coverage and the empty-array guard both work as claimed, confirmed 0 downstream breakage via an actual
test run — but found a real robustness gap: `c.receipt.publicKey` was dereferenced with no guard, so a
malformed bundle (`c.receipt === undefined`) would *throw* an uncaught `TypeError` the moment
`trustedPublicKeys` was actually supplied, rather than failing closed like every other check in the
file. **Fixed in the same pass**: `c.receipt?.publicKey` (optional chaining) + an `Array.isArray` guard
on `opts.trustedPublicKeys` itself (defensive, since the type is TS-only). Added a 6th regression test
reproducing the exact crash scenario, isolated from an unrelated pre-existing crash in a different loop
(see below) by using a ROOT-verdict commit, which that other loop already skips. Re-verified: 149/149,
tsc clean, live CLI unchanged, critic's caveat resolved.
