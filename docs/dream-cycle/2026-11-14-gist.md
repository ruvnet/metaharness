# Host-Adapters / SDK Hook-Event Validation SOTA Report — 2026-11-14

TL;DR: `@metaharness/sdk`'s `defineHook()` was the one `define*()` helper in
the SDK that did not runtime-validate its literal-union field. A typo'd
`event` (e.g. `"onPreToolUse"`) passed validation silently and would reach
`host-claude-code`'s `.claude/settings.json` projection as a dead hooks-map
key that Claude Code never fires — no error, no warning. Started fixing
this with a 10-entry allowlist sourced from this repo's own `HookDef`
type, `host-claude-code`'s header comment, and ADR-004 (three in-repo
sources, all identical) — then, while independently verifying the
candidate, live-fetched the official Claude Code hooks docs and found the
real surface has **33** events, not 10. The original 10 are a correct
subset (no renames, no contradictions), just incomplete — shipping the
10-item allowlist as originally drafted would have been a **real
regression**: it would silently start rejecting 23 legitimately-supported
events (`SessionEnd`, `Notification`, `PreCompact`, `PermissionRequest`,
etc.) that previously worked. Corrected before commit. Independent critic
(run against the corrected 33-event version): **ACCEPT**.

## MetaHarness Current Capability

Every `define*()` helper in `packages/sdk/src/index.ts` enforces its
literal-union/kebab-case fields at runtime except `defineHook`, which only
checked `!def.event` / `!def.handler` (truthy). Same "validation
asymmetry" bug class the 2026-10-19 Dream Cycle night (#418/#419, merged)
closed for `defineTool`/`defineMcpServer`'s missing `ensureKebab()` calls
and `defineHarness`'s missing cross-field collision checks — that night's
fix left this one sibling gap. Confirmed via repo grep: only
`host-claude-code` actually projects `h.event` verbatim into a real config
file (other hosts either disclose hooks as unsupported — `host-prime-
agent` — or don't reference `spec.hooks` at all).

**Separately and more significantly:** this repo's own documentation of
the Claude Code hook surface was itself stale. `docs/adrs/ADR-004-host-
integration-model.md` (2026-06-13) and `host-claude-code`'s source header
comment both listed only 10 events. Live-verifying tonight's fix against
the real, current docs surfaced 23 missing events the repo's own research
never captured — `SessionEnd`, `Notification`, `PreCompact`,
`PostCompact`, `PermissionRequest`, `PermissionDenied`, `PostToolBatch`,
`MessageDisplay`, `TaskCreated`, `TaskCompleted`, `StopFailure`,
`TeammateIdle`, `InstructionsLoaded`, `ConfigChange`, `CwdChanged`,
`DirectoryAdded`, `WorktreeCreate`, `WorktreeRemove`, `PreModelSwitch`,
`PostModelSwitch`, `Elicitation`, `ElicitationResult`,
`UserPromptExpansion`. All three in-repo sources (type, comment, ADR) have
been corrected in this PR to the full 33.

## Competitor Comparison

| Project | Validates lifecycle-event names before dispatch? | Failure mode on unknown event | Source |
|---|---|---|---|
| LangGraph (`StateGraph.add_node`) | Yes — raises at graph-compile time for an unknown node/edge target | Hard error, not silent | LangGraph docs, 2026 (B) |
| CrewAI (`@tool`/`@agent` decorators) | Partial — Pydantic validates decorator kwargs shape, no enum of lifecycle hook names | N/A (different surface) | CrewAI source, 2026 (B) |
| AutoGen (event-driven agent runtime) | No fixed enum; event names are free-form topic strings by design | N/A — free-form is the intended model | AutoGen docs, 2026 (B) |
| OpenAI Agents SDK (lifecycle callbacks) | Partial — callback names are Python method overrides, so a typo is a missing-override (silently never called) — the *same* failure mode this fix closes | Silent no-op, same bug class | OpenAI Agents SDK docs, 2026 (B) |
| Claude Agent SDK / Claude Code itself (hooks config) | No authoring-time SDK-side pre-check found in this repo's own research; Claude Code's settings.json presumably validates at load time, but that's the *consumer*, not an *authoring* SDK | This repo's `@metaharness/sdk` is specifically the authoring layer MetaHarness controls — the gap this fix closes is scoped to that layer, independent of whatever Claude Code itself does | Direct repo inspection (A for what's in this repo; the Claude-Code-side claim is unverified this session) |

Why most rows read as "no fixed enforcement" rather than "solved": these
frameworks' lifecycle surfaces are either free-form by design (AutoGen) or
validated only by the runtime consuming the config, not by the authoring
SDK producing it — exactly the seam `@metaharness/sdk` occupies. This
night's own mistake-and-correction (ship a stale 10-event list, catch it
via live verification, fix to 33) is itself a small case study in why
"validate against the type you already have" isn't sufficient when that
type was itself frozen from six-month-old research in a fast-moving
surface — worth remembering for any future SDK-layer validation night.

## Hypothesis

Given a harness author who calls `defineHook({ event, handler })` with an
event string, when `defineHook` validates `event` against the full,
currently-accurate 33-event Claude Code hook surface, then the author
gets a clear `Error` for a genuine typo/unsupported event and
byte-identical acceptance for every real event (including the 23 this
repo previously didn't recognize), subject to: 0 regressions in the
25-test `sdk.test.ts` suite; 0 in-repo downstream consumers affected
(verified: none exist).

## Recommended Next Steps

1. **Process lesson, not just a disclosed caveat:** this repo's own
   documentation (ADR-004, a source code header comment, and a TypeScript
   type union) all drifted from upstream reality by 23 events over ~5
   months without anyone noticing, because nothing re-verifies these
   "verified integration surface" research snapshots against live docs.
   Consider a periodic (e.g. quarterly, or triggered by a `security-
   adversarial`/`host-adapters` night) live-docs re-fetch for each host
   adapter's documented capability surface, not just this one event list.
2. Consider whether `defineHarness`'s cross-category collision check
   should also cover hooks (two hooks with the same `(event, matcher)`
   pair could silently shadow each other in `host-claude-code`'s
   `Object.fromEntries` grouping) — a different failure mode (shadowing,
   not an invalid key), disclosed not fixed tonight, out of scope.
3. **Standing process finding, restated per STEP 1.1 precedent (not
   re-escalated at length):** 0 `dream/*` PRs have merged since
   2026-10-21 (#410/#414/#419/#421) — **24 days, 23 consecutive Dream
   Cycle nights** (#429 through tonight) sit open as unreviewed drafts,
   while 25+ unrelated feature/release/fix PRs merged in the same window.
   Longest zero-merge stretch on record for this routine. The pipeline
   itself remains healthy (tonight's own in-flight self-correction is
   direct evidence the critique step works) — the constraint is
   exclusively human review bandwidth for this PR class.
