# Host-Adapters / SDK Validation-Asymmetry SOTA Report — 2026-11-14

TL;DR: `@metaharness/sdk`'s `defineHook()` was the one `define*()` helper in
the SDK that did not runtime-validate its literal-union field. A typo'd
`event` (e.g. `"onPreToolUse"`) passed validation silently and would reach
`host-claude-code`'s `.claude/settings.json` projection as a dead hooks-map
key that Claude Code never fires — no error, no warning, just a hook that
silently never runs. Fixed with a 10-entry allowlist mirroring the type
union, `host-claude-code`'s own documented hook surface, and ADR-004's
host-integration table (three independent in-repo sources, all identical).
Independent critic: **ACCEPT**.

## MetaHarness Current Capability

Every `define*()` helper in `packages/sdk/src/index.ts` enforces its
literal-union/kebab-case fields at runtime except `defineHook`, which only
checked `!def.event` / `!def.handler` (truthy). This is the exact
"validation asymmetry" bug class the 2026-10-19 Dream Cycle night (#418/#419,
merged) closed for `defineTool`/`defineMcpServer`'s missing `ensureKebab()`
calls and `defineHarness`'s missing cross-field collision checks — that
night's fix did not touch `defineHook`'s `event` field, leaving this one
sibling gap. Confirmed via a direct repo grep: only `host-claude-code`
actually projects `h.event` verbatim into a real config file (other hosts
either disclose hooks as unsupported — `host-prime-agent` — or don't
reference `spec.hooks` at all).

## Competitor Comparison

| Project | Validates lifecycle-event names before dispatch? | Failure mode on unknown event | Source |
|---|---|---|---|
| LangGraph (`StateGraph.add_node`) | Yes — raises at graph-compile time for an unknown node/edge target | Hard error, not silent | LangGraph docs, 2026 |
| CrewAI (`@tool`/`@agent` decorators) | Partial — Pydantic validates decorator kwargs shape, not an enum of lifecycle hook names (CrewAI has no hook-event enum analog) | N/A (different surface) | CrewAI source, 2026 |
| AutoGen (event-driven agent runtime) | No fixed enum; event names are free-form topic strings by design | N/A — free-form is the intended model | AutoGen docs, 2026 |
| OpenAI Agents SDK (`@function_tool`, lifecycle callbacks) | Partial — callback names are Python method overrides, so a typo is a missing-override (silently never called), the *same* failure mode this fix closes | Silent no-op, same bug class | OpenAI Agents SDK docs, 2026 |
| Claude Agent SDK (hooks config) | Hook event keys are validated by Claude Code itself at the settings-file level, not by any SDK-side pre-check | Unknown either until you check — the gap this fix closes is specifically for *this harness's own* authoring-time SDK, independent of whether Claude Code itself eventually validates it | Direct repo inspection |

Why several rows read closer to "no fixed enforcement" than "solved": most
of these frameworks' lifecycle surfaces are either free-form by design
(AutoGen) or validated by the *runtime consuming* the config (Claude Code
itself), not by the *authoring SDK* that produces it — which is exactly the
layer `@metaharness/sdk` occupies here. This is a case where MetaHarness's
own architecture (host-agnostic kernel + an opinionated validation SDK on
top) has a natural seam for this fix that several competitors don't cleanly
have, because they don't separate "authoring helper" from "runtime
consumer" the same way.

## MetaHarness Current Capability (post-fix)

`defineHook` now throws `hook event must be one of <10 events>: got "<bad>"`
for any `event` not in the documented Claude Code hook surface, matching
the validation rigor already applied to `tier`, kebab-case names, and
collision detection elsewhere in the same file.

## Hypothesis

Given a harness author who calls `defineHook({ event, handler })` with a
typo'd or unsupported `event` string, when `defineHook` validates `event`
against the documented 10-literal Claude Code hook surface, then the
author should get a clear `Error` at definition time instead of a silently
inert hook reaching `host-claude-code`'s settings.json projection,
subject to: byte-identical behavior for all 10 currently-valid events; 0
regressions in the existing 25-test `sdk.test.ts` suite; 0 in-repo
downstream consumers affected (verified: none exist).

Independent critic (fresh agent, not this session's author): **ACCEPT**.

three independent in-repo sources (`HookDef['event']` type, `host-claude-

hook surface has since grown (e.g. names like `Notification`/`PreCompact`/

install this session), this fix would start rejecting a legitimately-
supported event not yet in ADR-004's list. That risk pre-existed in the
`HookDef` type itself before this diff (the type already hard-restricted
the field at compile time) — this fix only makes the existing compile-time
contract enforceable at runtime too. Flagged as a good candidate for a
future `security-adversarial` or `host-adapters` night: re-verify ADR-004's
hook-event list against a live, current Claude Code install rather than
trusting the frozen 2026 research.
