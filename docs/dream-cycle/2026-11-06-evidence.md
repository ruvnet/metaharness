## OBSERVATION

`packages/flywheel/src/sequential.ts`'s `pairedOutcomesFromItemWins(baseline, candidate)` — the
per-item pairing the anytime-valid sequential promotion gate (`withSequentialEvidence`) and
`verifyReplayBundle`'s gate re-execution (ADR-235/254) both depend on — guarded `Score.itemWins` with
a length-only check (`!bw || !cw || bw.length === 0 || bw.length !== cw.length`), never
`Array.isArray`. `itemWins` is only a TypeScript type; nothing enforces it at runtime for a live
Evaluator's return value or an untrusted `ReplayBundle` parsed from JSON.

```
$ node -e "
const { pairedOutcomesFromItemWins } = require('./packages/flywheel/dist/cjs/sequential.js');
pairedOutcomesFromItemWins(
  {primary:1,noopRate:0,costPerWin:1,regressed:false,itemWins:'ab'},
  {primary:2,noopRate:0,costPerWin:1,regressed:false,itemWins:'cd'},
);"
Uncaught TypeError: bw.map is not a function
```

Confirmed live on `main` (commit `e17802aef80b47c0f6ff990ad8ce962643fa39b2`), reproduced
independently of the research agent that first surfaced it.

## INFERENCE

The crash is reachable, not merely theoretical, through three real call paths: (1) `run.ts`'s live
promotion loop, if an Evaluator's `Score.itemWins` is ever malformed; (2) `replay.ts`'s
`verifyReplayBundle`, called with no try/catch whenever a reviewer supplies `opts.promotionRule` —
documented in that file's own header as a function that must "always return a structured verdict,
never throw" on untrusted input; and (3) the already-shipped `experiments/signal-flywheel/verify.mjs`,
a real "external reviewer, no trust in the producer" script that does
`JSON.parse(readFile('bundle.json'))` → `verifyReplayBundle(...)` with no `validate-bundle.ts` call in
between — so a corrupted/malformed `bundle.json` in the wild would crash that script with a raw stack
trace instead of its designed clean `VERDICT: FAIL` + non-zero exit.

Disclosed, not fixed (independent critic's one caveat): a well-typed `boolean[]` `itemWins` array
containing `null`/`undefined` elements (e.g. `[true, null]`) still passes `Array.isArray` and does not
throw — `.map` works fine on it — but produces a slightly-off informative pair rather than a type
error. This is pre-existing behavior, not introduced or worsened by tonight's fix, and tonight's
documented contract ("never throw") still holds; flagged for a future night, not blocking ACCEPT.

Not a duplicate: grepped `docs/dream-cycle/LEDGER.md` and `docs/adrs/ADR-279-flywheel-sequential-evidence-wiring.md`
for prior `itemWins`-area fixes — the two recorded ones (ADR-279's wiring of `pairedOutcomes` into
`run.ts`/`replay.ts`, and the 2026-09-26 empty-array-lockout fix) are about *missing wiring* and
*empty-array semantics* respectively, neither about runtime type validation of a malformed non-array
value. `grep` for `pairedOutcomesFromItemWins` across `__tests__/` before tonight returned zero direct
hits.

## HYPOTHESIS (frozen before implementation)

matching the paired side, when `pairedOutcomesFromItemWins(baseline, candidate)` is called via either
`runFlywheelGenerations` (`run.ts`) or `verifyReplayBundle` (`replay.ts`, `opts.promotionRule`
supplied), then it should return `undefined` — degrading safely to the base promotion rule, per its
own documented contract — rather than throwing a `TypeError`, subject to: well-typed `boolean[]`
inputs produce byte-identical output to before the fix; `verifyReplayBundle` never throws on untrusted
bundle JSON; zero regressions in the existing flywheel test suite; `experiments/signal-flywheel`'s
committed `bundle.json` still replays byte-identically.
