# flywheel-promotion SOTA Report — 2026-11-06

TL;DR: `pairedOutcomesFromItemWins` (the per-item pairing feeding the flywheel's anytime-valid
sequential promotion gate) guarded `Score.itemWins` by `.length` only, with no `Array.isArray` check —
a non-array value with a matching `.length` (e.g. a string) passed the guard and crashed `.map()`
uncaught, violating `verifyReplayBundle`'s own documented "never throw on untrusted input" contract,
reachable through the already-shipped `experiments/signal-flywheel/verify.mjs` reviewer script. Fixed
with a one-line guard change + 2026-scoped research on anytime-valid promotion gates, evaluator
provenance-binding, and the current industry-wide PR-review-bottleneck literature.

## MetaHarness Current Capability

`@metaharness/flywheel` already implements more of this than most 2026 prototypes: testing-by-betting
e-processes (`sequential.ts`, fixed λ=0.5) composed with the frozen conjunctive gate (`gate.ts`), Ed25519
receipt chains with id/verdict/parents/generation cross-binding (`receipts.ts`, `replay.ts`), and
independent replay verification that re-executes the gate on sealed scores (ADR-235/254). Tonight's bug
sits exactly at the seam between the e-process evidence path (`run.ts` live loop) and replay
(`replay.ts`'s `verifyReplayBundle`) — both call the same `pairedOutcomesFromItemWins`.

**Why the gaps exist:** the full 4-part pattern (candidate-gen + statistical gate + tamper-evident
replayable evidence + human-gate) barely exists as one shipped product anywhere mainstream — criterion
(c), tamper-evident independently-replayable evidence, is nearly absent except in very recent narrow
prior art. 2026 research (RewardHackingAgents, Auditing Harness Tampering) shows the field only just
started treating "the self-improving agent might corrupt its own evaluator" as first-class; most teams
still rely on mutable git/CI history as de facto evidence. Partly cost-avoided: GEPA's own default
accepts any improvement (cheaper/faster) at the price of the Goodhart risk its docs flag.

## Hypothesis

Given a `ReplayBundle` (or a live Evaluator) whose `Score.itemWins` is a non-array value with a length
matching the paired side, when `pairedOutcomesFromItemWins(baseline, candidate)` is called via either
`runFlywheelGenerations` or `verifyReplayBundle` (with a supplied `promotionRule`), then it should return
`undefined` (degrading to the base rule, per its own documented contract) rather than throwing — subject
to: well-typed `boolean[]` inputs produce byte-identical behavior; `verifyReplayBundle` never throws on
untrusted JSON; zero regressions in the existing suite.
