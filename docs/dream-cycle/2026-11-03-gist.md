# Security-Adversarial SOTA Report — 2026-11-03

TL;DR: `harness threat-model`'s "Secrets reachable" field — the one line a
human reviewer reads to decide whether a generated harness exposes
credentials — was a structural false negative for every one of this repo's
20 shipped scaffold templates. A stale `hasReadAllow` gate required an
explicit `Read` rule in `permissions.allow`, a config shape no generator
ever produces and that Claude Code's own deny-first permission precedence
doesn't require. Fixed, tested, live-verified, independently critiqued.

## MetaHarness Current Capability
`packages/create-agent-harness/src/threat-model.ts`'s `buildThreatModel()`
aggregates `scanMcp()` (mcp-scan.ts) findings plus `.harness/mcp-policy.json`
and `.claude/settings.json` into one human-facing report: allowed/denied
tool counts, dangerous-permission count, and four yes/no risk lines
(secrets reachable, network, shell, file-write), each feeding a
clean/medium/high verdict and CI-friendly exit code (0/1/2). Two prior
Dream Cycle nights already hardened the deny-side of this surface:
2026-09-18 (#326/#327) fixed an unanchored `.env` substring match in
`envSecretGuarded`; 2026-10-18 (#413/#414) made the scaffolder itself write
a default-deny `.harness/mcp-policy.json`. Both are real, narrow, already-
shipped fixes — and both left the allow-side aggregation bug this report
closes untouched, since neither fix function touched `secretsReachable`.

## Hypothesis
Given a generated harness scaffold whose `.claude/settings.json` never
lists an explicit `Read` rule in `permissions.allow` (true of all 20
shipped templates — confirmed by direct inspection and by this repo's own
independent critic agent, which re-grepped every template file itself
rather than trusting this claim), when `buildThreatModel()`'s
`secretsReachable` computation drops the `hasReadAllow` requirement and
derives reachability from `envSecretGuarded()` (deny-side) alone, then
`harness threat-model`'s "Secrets reachable" line should correctly read
`yes` for a harness with no `.env`-blocking deny rule — relative to the
unconditional `no` baseline — subject to: no change to `envSecretGuarded`/
`mcp-scan.ts` (already correct, already fixed twice); 0 regressions in the
existing threat-model suite, including the two pre-existing tests that
drive `secretsReachable` via an explicit `Read(*)` allow rule.
