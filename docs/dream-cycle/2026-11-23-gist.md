# Security-Adversarial SOTA Report — 2026-11-23

TL;DR: `harness threat-model`'s one-line verdict was blind to its own
findings. An MCP-enabled harness with **zero** `.harness/mcp-policy.json`
governance, or with a `.claude/settings.json` wildcard (`*`/`mcp__*`) or
unscoped `Bash(*)` allow-rule, printed `Verdict: clean (exit 0)` directly
above a `[HIGH]` finding in the same report. Fixed in `buildThreatModel()`;
766→768 passed (+3, 0 regressions), independently reproduced and critiqued.
2026's MCP-permission-scanner landscape (academic + CSA + practitioner) is
real but fragmented, and none of it that we found specifically addresses a
scanner's own verdict-vs-findings self-consistency — the exact class of bug
fixed tonight.

**Why the "None" pattern elsewhere isn't the whole story:** every 2026 MCP
scanner we found (academic, CSA, practitioner) focuses on *detecting* a
dangerous permission or a poisoned tool. None of the write-ups discuss
*verifying that a scanner's own severity rollup matches its own itemized
findings* — a correctness property of the scanner itself, not of the thing
it scans. That's plausibly because most of these are young, single-purpose
CLIs without a second "human-readable summary" layer sitting on top of a
"structured findings" layer the way `threat-model.ts` sits on top of
`mcp-scan.ts` here — the bug class needs that two-layer shape to exist at
all.

## Hypothesis

Given a scaffolded or hand-authored harness directory that `metaharness
mcp-scan` inspects, when that directory produces a HIGH-severity finding
with no corresponding boolean knob in `buildThreatModel()`'s verdict
grid — specifically `no-policy` (MCP enabled, zero `.harness/mcp-policy.json`
governance), `wildcard-tool-perm` (`*`/`mcp__*`/`mcp__*__*` allow-rule), or
`unrestricted-bash-allow` (unscoped `Bash`/`Bash(*)` allow-rule) — then
`harness threat-model`'s `verdict`/`exitCode`/`dangerousPermissions` should
escalate to `high`/`2`/(+1 per finding), matching `mcp-scan`'s own
`worst: 'high'` reading of the identical directory, instead of reporting
`clean`/`0` as before, subject to: (a) zero regressions elsewhere in the
763-test baseline; (b) no double-counting against findings already
represented by an existing boolean (`no-default-deny`↔policy-default-deny,
`allow-shell`↔shell-access); (c) `scanMcp()` itself is untouched — only
`buildThreatModel()`'s aggregation of its already-computed findings changes.

Confirmed, not rejected.
