# Flywheel Promotion SOTA Report — 2026-10-06

TL;DR: Tonight's flywheel-promotion candidate closes a trust-boundary gap `verifyReplayBundle()`
(`packages/flywheel/src/replay.ts`) has carried, disclosed-but-unfixed, since ADR-274 (2026-09-01):
`verifyReceipt` only proves a promotion receipt's signature matches its *own embedded* public key —
never that the key is one anyone trusts. An attacker with no access to the real producer's signing key
can generate a fresh throwaway keypair, fabricate an entire self-consistent `ReplayBundle` (receipts,
lineage, scores), self-sign it, and every existing check (`receipts`, `allCommitsReceipts`,
`sealedFieldsAuthentic`, `gateReExecutes`) still returns PASS — a self-signed CLAIM, not evidence.
Added an opt-in `trustedPublicKeys` allowlist (mirroring the proven `packages/avo/src/flywheelGate.ts`
pattern, ADR-271) plus a `--trusted-key` CLI flag; omitted, behavior is byte-identical to before. An
independent adversarial critic (fresh context) found one real robustness gap in the first draft — an
unguarded `c.receipt.publicKey` dereference that would *throw*, not fail closed, on a malformed bundle
once the allowlist option was actually used — fixed in the same pass with a non-vacuous regression test.
`packages/flywheel` suite 143→149/149 (+6, 0 regressions); 6/6 new tests fail non-vacuously pre-fix; all
7 real committed `ReplayBundle` files in the repo re-verify unchanged; live CLI proof against the real
committed `experiments/signal-flywheel/bundle.json`. ADR-319 filed. **`evaluated: accepted`.**

Why "None" is the honest answer almost everywhere: promotion gating in every mainstream framework
surveyed reduces to a single eval-score threshold in CI, because none of them ship an architecturally
independent, cryptographically-signed self-improvement claim in the first place — there is no signer to
pin trust to. This is a genuine, still-open gap industry-wide, not a feature competitors quietly solved
and declined to publish.

## Hypothesis

Given a `ReplayBundle` whose promotion receipts are signed by a key not on the reviewing caller's
explicit allowlist, when `verifyReplayBundle` is invoked with `opts.trustedPublicKeys` supplied, then
the bundle must fail replay verification with reason `trustedSigner`, subject to: (a) omitting the
option is byte-identical to today's behavior (no regression for any existing caller); (b) a bundle
signed only by allowlisted keys still passes exactly as before; (c) an empty array is treated as "not
supplied," not "trust nothing"; (d) a malformed/missing receipt fails closed, never throws, once the
option is supplied; (e) 0 regressions in the existing suite.

## Evaluation

`evaluated: accepted`.
- **Baseline** (`git stash` on `replay.ts`+`cli.ts` alone, new tests present): **6/6 new tests fail
  non-vacuously** — `checks.trustedSigner` is `undefined` (the field doesn't exist pre-fix), not
  `false`/`true`.
- **Candidate**: `packages/flywheel` suite **143→149/149** (+6, 0 regressions). `tsc --noEmit` clean.
  Downstream `create-agent-harness` suite **622/624** (2 pre-existing skips), unaffected.
- **Live CLI proof**: `metaharness flywheel replay experiments/signal-flywheel/bundle.json --trusted-key
  <real-signer-key>` → PASS; same command with a bogus key → `FAIL (trustedSigner)`, exit 1; same command
  with no `--trusted-key` → PASS, unchanged.
- **Regression sweep**: all 7 real committed `ReplayBundle`/proof-bundle files in the repo
  (`packages/radio/.radio-flywheel/`, `kimi-k3-harness/.harness/flywheel/`,
  `packages/darwin-mode/bench/swebench/`, `packages/evals-math/bench/proof-bundle-gsm8k*.json` ×3,
  `experiments/signal-flywheel/bundle.json`) re-verify `ACCEPTANCE: PASS`, unchanged, with no
  `--trusted-key` supplied.
- **Blast radius**: `verifyReplayBundle` importers confined to `packages/flywheel/src/{cli,index,
  validate-bundle}.ts` (repo-wide grep) — zero `evals-*`/`autogenous`/`create-agent-harness` direct
  importers.
- **Independent adversarial critic** (fresh subagent, cold-read, did not see the implementation
  rationale): verdict **ACCEPT-WITH-CAVEATS** on the first draft — confirmed the core gap is real and
  the fix closes it correctly (signature validity and signer trust are independently required, no
  forgery bypass found), confirmed `all_commits` coverage, confirmed the empty-array guard, confirmed
  0 downstream breakage via the real test run — but found one real issue: `c.receipt.publicKey` was
  dereferenced with no guard, so a malformed bundle would *throw* instead of failing closed the moment
  `--trusted-key` was actually used. **Fixed in the same pass**: `c.receipt?.publicKey` (optional
  chaining) + `Array.isArray` guard on `opts.trustedPublicKeys`, with a new non-vacuous regression test
  isolating the exact line (a ROOT-verdict commit with no `receipt` field, which the pre-existing
  `sealedFieldsAuthentic` loop skips, to isolate this candidate's own check from an unrelated,
  pre-existing, disclosed-not-fixed crash in that different loop — see Recommended Next Steps).
- **Reward-hack check**: clear. Diff is additive (new optional field + new opt-in CLI flag); no existing
  threshold/gold-data/test weakened; no cost hidden; `git diff --stat` touches only `replay.ts`, `cli.ts`,
  and the one test file.
