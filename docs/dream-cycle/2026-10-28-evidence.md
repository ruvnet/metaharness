## OBSERVATION

- `packages/create-agent-harness/src/sbom-cmd.ts`'s `SpdxPkg` type and `packagesFromLock()`
  never produced a `checksums` field on any SPDX package entry.
- `scripts/sbom.mjs`'s `buildSpdx()` produced a `checksums` field whose `checksumValue`
  was `sha1(integrity-string-or-placeholder)`, not a digest of the real package content.
- Both gaps were disclosed-not-fixed on 2026-10-18 (#413/#414) and 2026-10-23 (#430/#431).

## MEASUREMENT

- Live read of the repo's own `package-lock.json` (307 real npm packages): 255 carry a
  real `integrity` (SRI) field; 52 do not (peer/optional/manifest-derived entries).
- Pre-fix, `scripts/sbom.mjs` against this same lockfile: 100% of packages got a
  `checksums` entry, 0% of them real (confirmed via independent out-of-band re-derivation:
  `sha1(integrity_string) != sha512_decode(integrity_string)` for every sampled package).
- Pre-fix, `sbom-cmd.ts` against the same data: 0% of packages got any `checksums` field.
- Post-fix: 255/307 (83%) carry a real decoded digest; the remaining 52 are disclosed via
  a new `component hashes: X/Y` line rather than silently omitted or fabricated.

## INFERENCE

The SRI→SPDX-checksum conversion (base64-decode the SRI payload, hex-encode it, map the
SRI algorithm token to its SPDX enum name) is the same pattern CycloneDX's own reference
npm tooling (`cyclonedx-javascript-library`'s `parsePackageIntegrity()`) uses — this is
standard practice, not a novel or risky transform.
