# security-adversarial SOTA Report — 2026-09-03

**TL;DR**: MetaHarness ships two "is MCP in use?" scanners over the same
config surface — `mcp-scan.ts` and `threat-model.ts` — and they disagreed.
`threat-model.ts` called `scanMcp()` internally but computed its own,
narrower `mcpInUse` from only `.harness/mcp-policy.json`/`.mcp.json`,
missing `.claude/settings.json`'s `mcpServers` key that `scanMcp()` already
checked. A harness registering MCP only via `.claude/settings.json` got a
`harness threat-model` report claiming "MCP is not in use" — silently
discarding real findings `scanMcp()` had already computed one line above,
in a tool whose job is to be what a PR/compliance reviewer trusts. 2026
research (below) frames this as a "parser differential" / detection-
coverage-gap shape, just not previously named for one tool's own two
commands drifting apart. Fixed by making `scanMcp()`'s `mcpEnabled` the
single source of truth, reused by `threat-model.ts`. An independent
adversarial critic then caught a **second-order regression in the first
version of the fix**: naively swapping in `scan.mcpEnabled` dropped
`.mcp.json` coverage, since `scanMcp()` itself never checked that file —
closed by adding `.mcp.json` as `scanMcp()`'s third detection signal, so
all three surfaces are now checked in exactly one place. This also fixes a
live downstream bug in `@metaharness/agntcy`'s `from-mcp-scan.ts`, which
derives AGNTCY verifiable-credential badges from `ThreatModel.mcpInUse` —
a `settings.json`-only harness was silently under-issued its `mcp.read`
badge.

## MetaHarness Current Capability

`harness mcp-scan` (`mcp-scan.ts`) is the security-scanning source of
truth: reads `.harness/mcp-policy.json`, `.claude/settings.json`
(permissions + `mcpServers`), now also `.mcp.json`; returns structured
findings + `mcpEnabled`. `harness threat-model` (added later, iter 112 —
never referenced in ADR-022 despite ADR-022 documenting `mcp-scan` in
detail) wraps `scanMcp()` for a PR/compliance-ready report, but pre-fix
kept its own, independently-drifting "is MCP in use" check.
`@metaharness/agntcy`'s `from-mcp-scan.ts` (ADR-240) derives
verifiable-credential badges from `ThreatModel.mcpInUse` — a real,
previously-undisclosed consumer of the bug's blast radius. `threat-model.ts`
had **zero dedicated tests** before tonight.

is consolidating as third-party vendor infrastructure. Shipping it in the
harness itself is the differentiator; tonight's finding is that two
commands over one question are only a differentiator if they agree.

## Hypothesis

Given a harness directory registering MCP through exactly one of three
valid surfaces (`.harness/mcp-policy.json`, `.mcp.json`, or
`.claude/settings.json`'s `mcpServers`), when `harness threat-model` runs
against it, then it should report `mcpInUse: true` and surface the real
`scanMcp()` findings for **all three** surfaces independently, subject to:
(a) a directory registering none still reports clean/off; (b) 0
regressions in the 560-test `create-agent-harness` suite; (c) new tests
must fail pre-patch (red/green); (d) fix stays one conceptual change, not
a redesign of `threat-model`'s verdict/exit-code logic.

## Benchmarks / Evaluation

Deterministic code-correctness fix — evaluated by direct reproduction and
unit tests, not a sampled benchmark. `LLM_EVAL=available` tonight
(`OPENROUTER_API_KEY` present) but no model calls were needed.

**Round 1** — `threat-model.ts`: replaced the standalone `mcpInUse`
expression with `scan.mcpEnabled` (reuse `scanMcp()`'s own check).
Red/green: 3/6 new tests fail pre-patch (bug-repro + consistency cases, as
predicted), 6/6 pass post-patch; full suite 560 passed | 2 skipped (0
regressions), `tsc --noEmit` clean.

**Independent adversarial critic** (fresh sub-agent, no authorship
context) reviewed Round 1 cold: **REJECT**. `scanMcp()` never read
`.mcp.json`, so the wholesale swap silently dropped `.mcp.json`-only
registrations — the same bug class reintroduced for a different config
surface. Verified empirically (built a `.mcp.json`-only fixture, confirmed
`mcpInUse: false` post-Round-1); also flagged one new test as tautological
(compared the implementation to itself, could never fail).

**Round 2 (critic-driven fix)** — moved the third detection signal into
`scanMcp()` itself, so `mcpEnabled` now ORs all three surfaces
(`policy || mcpJson || settings.mcpServers`) in the one place downstream
callers rely on. Replaced the tautological test with an explicit
expected-value table (5 cases) plus a dedicated `.mcp.json`-only case, and
2 new isolation tests in `mcp-scan.test.ts`:
```

full suite: 563 passed | 2 skipped (0 regressions)   tsc --noEmit: clean
agntcy suite (downstream ThreatModel.mcpInUse consumer): 82/82 passed
```
Diff: 2 source files (~18 lines) + 2 test files (~65 lines) — well under

**Broader regression check** (root-level integration suites, rebuilt
