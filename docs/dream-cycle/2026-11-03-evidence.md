## OBSERVATION
- `packages/create-agent-harness/src/threat-model.ts`'s `secretsReachable`
  computation was `mcpInUse && !guardsEnv && hasReadAllow`, where
  `hasReadAllow = allow.some(a => /^Read/.test(a))`.
- Direct inspection of all 20 `templates/*/.claude/settings.json.tmpl`
  files: none ever places a `Read` rule inside `permissions.allow`.
  Independently re-confirmed by a separate critic agent via its own grep.
- Claude Code's documented permission precedence: deny checked first, then
  ask, then allow — first match wins (docs.claude.com/.../settings, cross-
  checked against two independent third-party guides).

## INFERENCE
- Because no shipped template ever satisfies `hasReadAllow`, and Read does
  not require an `allow` entry to execute under the documented precedence,
  `secretsReachable` was unconditionally `false` for every real generated
  harness, independent of whether `.env` was actually guarded by `deny`.
  This is a false negative in the one human-facing "Secrets reachable"
  line of `harness threat-model`'s enterprise-review output.
