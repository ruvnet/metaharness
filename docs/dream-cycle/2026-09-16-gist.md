# Flywheel Sequential-Evidence Gate Had a Silent-Lockout Edge Case — 2026

TL;DR: `@metaharness/flywheel`'s anytime-valid sequential-evidence gate
(`withSequentialEvidence`, ADR-234/235-adjacent) is documented to "degrade
to the base rule" when a caller hasn't wired up per-item comparison data —
but its check (`!outcomes`) only catches `undefined`, not an explicit empty
array. `pairedOutcomes: []` — a common JS default-parameter shape — falls
through to `sequentialEvidence([])`, which can never reach significance,
permanently rejecting every candidate regardless of how strong the base
gate's own evidence is. Currently unreachable in production (zero call
sites in this repo), but open PR #288 is about to wire exactly this field
into `runFlywheelGenerations`/`verifyReplayBundle`. Fixed with a 1-line
condition change + 2 new regression tests, 124/124 downstream tests green.
Separately disclosed: the Dream Cycle PR review backlog (7 open, 0 merged
since 09-05) and an unexplained 09-12→09-14 gap, both already flagged by
last night's session and still unresolved — see Recommended Next Steps.

## MetaHarness Current Capability

`packages/flywheel/src/sequential.ts` implements a testing-by-betting
e-process (Ville's-inequality anytime-valid) wrapper around any
`PromotionRule`: `withSequentialEvidence(baseRule)` composes the frozen
`meetsPromotionRule` (or a custom gate) with per-item paired-outcome
evidence, requiring BOTH the base gate's clauses and accumulated e-value
significance (`e >= 1/alpha`, default threshold 20). It exists specifically
to counter the 30-42% false-commit rate published for naive
greedy-accept-on-improvement gates in repeatedly-peeked settings — exactly
the flywheel's own generation-after-generation peeking pattern. Shipped,
unit-tested (16 tests pre-tonight), zero production call sites as of
tonight's session start.

## Hypothesis

Given a `PromotionEvidence` whose `pairedOutcomes` field is present but is
an empty array (as opposed to omitted), when `withSequentialEvidence
(baseRule)` evaluates it, then the returned decision should equal
`baseRule`'s own decision (graceful degradation, per the function's
documented contract) — where before it unconditionally returned
`promote: false` — subject to: (a) a non-empty array with ≥1 discordant
pair keeps existing semantics unchanged; (b) a non-empty, entirely
concordant array (real data, no signal) still correctly rejects for
insufficient evidence — only an EMPTY array degrades; (c) `meetsPromotionRule`
itself is byte-for-byte untouched; (d) zero regressions elsewhere. Frozen
before implementation, not modified after evaluation began.
