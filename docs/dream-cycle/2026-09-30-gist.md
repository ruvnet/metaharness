# Generator-Genome / SDK SOTA Report — 2026-09-30

TL;DR: Tonight's DEEP surface (generator-genome) closed a real, externally-corroborated
gap: `@metaharness/sdk`'s `defineHarness()` claimed (via its own inline comment) to
detect name collisions across "agents/skills/tools", but the code only ever built
`Set`s for `agents` and `skills` — `tools` and `mcpServers` passed through completely
unvalidated. The architecture-review pass found this is not merely latent: several
host adapters (`host-openclaw`, `host-copilot`, `host-codex`, `host-pi-dev`) key
tools/mcpServers into name-indexed structures with silent last-write-wins semantics,
so an SDK-authored `HarnessDef` with a duplicate tool/mcpServer name would silently
corrupt or shadow at the host-adapter layer today. Fixed additively, mirroring the
existing agent/skill pattern exactly. SCAN surfaces (router, turn-credit) each
produced a real, disclosed-not-fixed finding — most notably a demonstrated NaN
propagation bug in the router that silently routes queries to a worse model with
no error.

## MetaHarness Current Capability
`packages/sdk` gives harness authors typed `define*()` builders (`defineAgent`,
`defineSkill`, `defineTool`, `defineMcpServer`, `defineHook`) composed via
`defineHarness()`. `HarnessDef` is structurally identical to `@metaharness/kernel`'s
`HarnessSpec` — no shape conversion is needed for an SDK-authored harness to flow
into any `HostAdapter.generateConfig()`. Only one of ~8 host adapters
(`host-prime-agent`, via ADR-247's `uniqueSkillName`) defends against duplicate
names at its own layer; the rest assumed the SDK boundary already guaranteed
uniqueness — it didn't, for tools/mcpServers.

Net read: this bug class is real and *currently active* across the industry — not
solved-and-unpublished — but no longer uncrowded; three frameworks (OpenAI, Google,
Agno) shipped fixes for it within roughly the last 6 months, and DSPy has the
identical bug live today. The genuinely fresh angle for *this* repo's finding is
narrower: none of the surveyed writeups are about a comment that actively
overstates its own validation coverage (ours claimed "tools", checked none) —
that framing, not "duplicate names are risky" in the abstract, is the novel part.

## Hypothesis
Given a `HarnessDef` passed to `defineHarness()` containing two `ToolDef` or two
`McpServerDef` entries sharing the same `name`, when `defineHarness()` validates
it, then it should throw a `<kind> name collision` error before returning —
subject to: (a) existing agent/skill collision behavior is byte-identical, (b)
harnesses with unique tool/mcpServer names continue to compose successfully, (c)
zero regressions in `packages/sdk`'s existing suite.

## Recommended Next Steps
1. **Router NaN-propagation → silent wrong-model routing** (disclosed, not fixed
   tonight, SCAN=router): `packages/router/src/train.ts` indexes `r.scores[id]`
   without checking every training row has a score for every candidate; a sparse
   row makes `fitKRR` produce a partially-NaN `alpha` vector for that candidate,
   which `predictKRR` then silently returns as `NaN` — demonstrated live: with one
   row missing a candidate's score, `route()` on a query from that candidate's
   winning cluster silently returns a *different, worse* model with `metBar:
   false` and no error/warning anywhere. Contrast: `Router.fromExamples` already
   filters sparse rows correctly (`index.ts:132`) — `trainRouter` never got the
   same guard. Good candidate for a dedicated router-focused night.
2. **Turn-credit NaN-bypass silently nulls signed-receipt fields** (disclosed,
   not fixed tonight, SCAN=turn-credit): `processTrajectory` validates
   `gamma`/`bound`/`mix` but never `input.prior` or `config.pivotalRatio`; a NaN
   `prior` doesn't throw, it silently produces `null` numeric fields in the
   signed receipt (`JSON.stringify(NaN) → null`), so the receipt looks clean but
   the value is quietly gone. This is the **3rd instance** of the NaN-bypass
   pattern already fixed on 2026-09-27 (#360, weight-eft) and 2026-09-28 (#362,
   10 darwin-mode bench scripts, 8 more disclosed) — deliberately NOT selected
   as tonight's primary candidate to avoid a 4th consecutive night on the same
   bug shape (STEP 1.1), but flagged because unlike the bench scripts, this one
   corrupts a *signed evidentiary receipt*, which is a slightly different
   (worse) failure mode than a CLI flag bypass.
3. **`scorePublishReadiness` credits `buildCommands`/`testCommands` from
   manifest/language detection alone**, the same "manifest implies capability"
   shortcut `scoreTestConfidence` (same file) was hardened against on 2026-08-25
   (#229) — never extended to its sibling function. Small, well-scoped, good
   candidate for a near-future generator-genome night.
4. Router's `prices[id] ?? 0` default (missing price → cost 0) makes an
   unpriced candidate always win cost-optimal ties; lower severity than #1, same
   file, worth bundling with a router-focused night.
