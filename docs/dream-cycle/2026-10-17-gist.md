## Hypothesis

Given the `bench/swebench` solve-{advisor,agentic,fusion,mcts,repair}.mjs family, each deriving its
real-money `--max-cost` cap via `const MAX_COST = +argv('--max-cost', Infinity)` then gating on
`if (totalCost >= MAX_COST)`, when `--max-cost` is malformed and `+raw` evaluates to `NaN`, then
(IEEE-754) `NaN >= anything` is `false` and the stop condition silently never fires, burning unbounded
real spend. A shared `parseMaxCost()` guard should throw on any non-finite/negative value instead,
subject to: (a) a valid flag and the absent-flag default (`Infinity`) behave byte-identically, (b)
zero existing test regresses, (c) diff stays under 300 lines, confined to `bench/swebench`. Frozen
before implementation.

## Adversarial Critique

Independent fresh-subagent critic, cold read — **ACCEPT-WITH-CAVEATS**. Reproduced the bug directly
(`+'abc'`/`+'NaN'` → `NaN`; `NaN >= x` → `false`), independently reverted-and-restored the guard to
reproduce the non-vacuous 3/6 red state itself, grepped for downstream importers (none — CLI-only,
invoked from shell runners that never pass `--max-cost Infinity`). Two disclosed, non-blocking caveats:

1. An explicit literal `--max-cost Infinity` now throws (`Number.isFinite(Infinity)` is false) instead
   of being silently accepted as "no cap". Zero real usage found repo-wide; theoretical, not an actual
   regression — left as-is since refusing an odd-looking explicit value is arguably the safer failure
   mode for a real-money cap.
2. Sibling flags in the same files (`--max-steps`, `--temperature`, `--concurrency`) keep the identical
   unguarded idiom; `Math.max(1, NaN) === NaN` confirmed, so `--concurrency` isn't actually protected by
   its own `Math.max` guard. Deliberately out of scope tonight (one conceptual change); carried into
   Scan Finding 1.
