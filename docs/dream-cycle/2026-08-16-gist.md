# flywheel-promotion SOTA Report — 2026-08-16

**TL;DR**: Tamper-evident logs where only the *accepted* subset is independently verifiable — not
the full log — is a known anti-pattern in classical transparency-log design (Certificate
Transparency, Sigstore/Rekor); a January 2026 paper on MCP-manifest transparency logs shows the
identical asymmetry recurring in the agent-tooling space today. Auditing `@metaharness/flywheel`'s
own `verifyReplayBundle()` against that standard tonight found MetaHarness had it too: receipts were
verified on the promoted `chain` but never on `all_commits` (the full diagnostic ledger of promoted
*and* rejected candidates), even though the producer (`run.ts`) signs every commit it mints
regardless of verdict. An independent adversarial critic then found the fix itself was incomplete —
a valid signature proves a payload is internally consistent, not that it's attached to the *right*
commit, so a REJECTED commit's outer `verdict` field could be flipped to `PROMOTED` (receipt
splicing) without invalidating anything — and that gap existed in the pre-existing `chain` check
too, not just the new one. Both closed before shipping, with a disclosed remainder (below).

## MetaHarness Current Capability

`@metaharness/flywheel` runs a bounded, host-agnostic promotion loop (`runFlywheelGenerations`):
propose → evaluate on a holdout → gate with the frozen `meetsPromotionRule` (primary↑, no-op↓,
cost≤, ¬regressed, anchor survives) → sign every commit (PROMOTED *and* REJECTED) into an
append-only lineage → assemble a `ReplayBundle` an external reviewer verifies with, per its own
header comment, "no trust in the producer." ADR-235 (2026-07-06) already hardened this once — fixing
a false-FAIL on honest-null (0-promotion) bundles and adding gate re-execution on sealed scores.
Tonight extends the same "trust the re-run, not the logged verdict" discipline to two places ADR-235
didn't reach.

Synthesis: "sign both accepted and rejected candidates, then let an outsider replay the gate with
zero trust in the producer" has no shipped match in this survey. The gap tonight closed —
*verifying* what was already signed — is thus a genuinely small but real step past what any
surveyed competitor does today, not a catch-up fix.

## Hypothesis

Given `@metaharness/flywheel`'s `verifyReplayBundle`, which verified Ed25519 receipts and re-executed
the gate only across the promoted `chain`, when receipt verification (including an id+verdict
cross-check against the signed payload) is extended to every entry in `all_commits`, and a PROMOTED
commit missing sealed `baselineScore`/`candidateScore` is treated as a `gateReExecutes` failure
instead of a silent skip, then a bundle carrying a tampered, spliced, or unauditable ledger entry
should FAIL replay (`pass: false`) where it previously passed, while every honestly-produced bundle
continues to PASS unchanged, subject to: (a) zero regression in the existing suite, (b) purely
additive `ReplayVerdict.checks`, (c) `meetsPromotionRule` itself untouched, (d) diff materially under
300 lines.

## Adversarial Critique

Independent critic (no authorship context) reviewed the diff — verdict **ACCEPT-WITH-CAVEATS**.
Confirmed: no existing test weakened, `meetsPromotionRule` untouched, no false positives on any
honest bundle `run.ts` can produce (traced the signing code directly). It found a real problem in
the *first-drafted* version: the `allCommitsReceipts` doc comment claimed to catch "forged
failureReasons, understated cost" — false, since `run.ts` signs only `{kind, id, target, verdict,
primaryDelta}`, not the Score fields — and, more seriously, demonstrated that neither the new check
nor the **pre-existing** `chain` receipts check cross-verified a commit's outer `verdict`/`id`
against what the signed payload actually claims, so a REJECTED commit's outer `verdict` could be
flipped to `PROMOTED` (receipt splicing) without invalidating `verifyReceipt`. **Fixed before
shipping**: added `receiptMatchesCommit()`, applied to both `receipts` (chain) and
`allCommitsReceipts`; corrected the doc comments to state precisely what is and isn't attested;
added a dedicated verdict-flip regression test; fixed one pre-existing test fixture that didn't sign
a `verdict` field (masking the exact gap the critic found). The critic's one **still-open**
finding — `gateReExecutes` never re-checks the anchor (anti-Goodhart) clause because `ReplayBundle`
doesn't carry `rootAnchor` at all — is disclosed, not fixed tonight (see Recommended Next Steps): it
predates this diff and closing it needs a larger, non-additive bundle-schema change.

## Recommended Next Steps

1. **Re-verify the anchor clause during `gateReExecutes`.** `ReplayBundle` doesn't carry `rootAnchor`,
   so replay can't re-check `meetsPromotionRule`'s anti-Goodhart clause today — a critic-flagged,
   pre-existing gap this diff doesn't close (needs an additive schema field + a slightly larger,
   more carefully-scoped diff than tonight's).
2. **Sign the Score/failureReasons fields, not just id+verdict+primaryDelta.** Today a bundle editor
   who cannot forge signatures can still alter a rejected candidate's displayed cost or rejection
   reason without failing replay — disclosed, not silently hidden; fixing it changes `run.ts`'s
   signed-payload shape and needs a compatibility plan for existing committed bundles.
3. **Backfill `flywheel replay`'s CLI help/README** with the new `allCommitsReceipts` check and the
   verdict-flip threat model, so a human running it understands what changed — natural next-night
   documentation candidate if not done as a follow-up PR comment first.
