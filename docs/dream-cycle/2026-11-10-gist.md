# Generator-Genome SOTA Report — 2026-11-10

TL;DR: `repo-scorecard.ts`'s `buildRepoScorecard()` (the `metaharness score` / ADR-041
command) credited `profile.testCommands.length > 0` directly in two of its six scorecard
dimensions (`compileConfidence` +25, `taskCoverage` +12). `testCommands` is populated by
`analyze-repo.ts` purely from manifest/language detection — any repo with a `pyproject.toml`
gets `'pytest'` pushed unconditionally, zero real test files required — so a manifest-only
repo scored IDENTICALLY (90/36) to an otherwise-identical repo with real committed tests.
Same "manifest implies tests" bug family already closed in `resolveAgentTopology` (#314,
merged) and pending in `scorePublishReadiness` (#451, open); this was a 5th, undisclosed
instance in a sibling scorer nobody had checked. Fixed by gating both dimensions on
`hasVerifiedTestFiles || testCommands.includes('npm test')`, the same real-evidence-or-
authored-script carve-out already established elsewhere in this package.

## MetaHarness Current Capability

`harness genome`, `harness score`, and `metaharness score` are three separate, deterministic,
no-exec scorecards over a local repo (`genome-scorers.ts`, `score.ts`, `repo-scorecard.ts`).
All three independently infer "can this repo be tested" from `RepoProfile`. Two of three
scorers (`genome-scorers.ts`'s `resolveAgentTopology`/`scoreTestConfidence`, and now
`repo-scorecard.ts`) require real filesystem evidence (`hasVerifiedTestFiles`, a directory
scan) or an authored `npm test` script; the third (`score.ts`'s `scoreTestCoverage`) is fixed
on an open branch (#435) pending merge. `genome-scorers.ts`'s own `scorePublishReadiness` is
the one instance of this bug family still open (#451) after tonight's fix.

## Hypothesis

Given a repo whose only test signal is a manifest/language-inferred `testCommands` entry
(no real test files — e.g. a bare `pyproject.toml`), when `repo-scorecard.ts`'s
`compileConfidence` and `taskCoverage` are gated on `hasVerifiedTestFiles ||
testCommands.includes('npm test')` instead of raw `testCommands.length > 0`, then the
manifest-only repo should score **strictly lower** on both dimensions than an otherwise-
identical repo with real committed test files (pre-fix: identical), subject to: (a) zero
regression across the 18 pre-existing `repo-scorecard.test.ts` assertions; (b) the
authored-`npm test` carve-out keeps full credit for a repo with no dedicated test directory
(regression-guarded by a 2nd new test); (c) the real-test-files repo's score is byte-
identical pre/post-fix; (d) no other scorecard dimension (`harnessFit`, `toolSafety`,
`memoryUsefulness`) is touched. Frozen before implementation; not revised after evaluation.
