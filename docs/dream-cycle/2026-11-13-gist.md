# Security-Adversarial SOTA Report — 2026-11-13

TL;DR: `harness score`'s MCP-safety dimension (`scoreMcpSafety()`) only reads
`.harness/mcp-policy.json`'s booleans — it never consults `mcp-scan.ts`'s own
`scanMcp()` findings, which are the single place this repo already detects
risky *`.claude/settings.json`* grants (wildcard tool permissions, an
unrestricted `Bash`/`Bash(*)` allow-rule, a missing `.env` secret-guard deny
rule). A harness with a perfectly locked-down policy file but a risky
settings.json grant still badges `mcpRisk: Low`/`Medium` and can reach Grade
A/B — reopening, through a sibling surface, the exact "averaging/masking
away an unsafe signal" failure mode the 2026-09-20 grade-cap fix (#336/#337)
was built to prevent.

## MetaHarness Current Capability
`mcp-scan.ts`'s `scanMcp()` is the authoritative detector across 3 valid
registration surfaces (policy file / `.mcp.json` / `.claude/settings.json`
`mcpServers`) and flags settings.json-specific risks (`wildcard-tool-perm`,
`unrestricted-bash-allow`, `risky-bash-allow`, `no-secret-guard`) that no
other file can see. `threat-model.ts` already reuses `scan.worst`/`.findings`
directly (fixed 2026-09-03, #276). `score.ts`'s `scoreMcpSafety()` calls
`scanMcp(dir)` too — but **only** for `.mcpEnabled`, then recomputes
`mcpRisk` from policy-file booleans alone (score.ts:174-227). `oia-manifest.ts`'s
`readHarnessProfile()` has the identical gap for its governance/security
spans (disclosed, not fixed tonight — same root cause, lower production
value since it's not a CI-gating badge).

## Hypothesis
Given a scaffolded harness whose `.harness/mcp-policy.json` reports safe
booleans (`defaultDeny:true`, `allowShell/Network/FileWrite:false`) but
whose `.claude/settings.json` grants a HIGH- or MEDIUM-severity permission
`scanMcp()` already detects (a `mcp__*__*`/`*` wildcard, an unrestricted or
risky `Bash` allow-rule, or no `.env` secret-guard deny rule), when
`scoreMcpSafety()` is changed to escalate its own `mcpRisk` to at least
`scanMcp(dir).worst`'s severity (reusing the `scanMcp()` call it already
makes for `mcpEnabled`, not re-deriving it), then `harness score`'s
`mcpRisk` badge — and the existing mcpRisk-High grade cap (#336/#337) —
correctly fire for a settings.json-only risk, relative to the baseline
where such a harness badges `Low`/`Medium` and can reach Grade A/B, subject
to: (a) a harness with no such settings.json finding is byte-identical in
score/grade/signals; (b) the existing policy-boolean risk computation is
never downgraded, only escalated; (c) zero regressions in
`score-mcp-risk-grade-cap`/`score-mcp-detection`/`genome-scorers*` suites.
Frozen before implementation.
