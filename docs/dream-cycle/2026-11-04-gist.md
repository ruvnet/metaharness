# Host-Adapters SOTA Report — 2026-11-04

TL;DR: `@metaharness/host-prime-agent`'s fail-closed `SANDBOX-REQUIRED.md`
safety disclosure (ADR-247 §2.2 — "never silently drop the deny-list,"
closing the exact ADR-046 bug class) was structurally unreachable from the
two scaffold-time mirrors that actually serve most users: `npx metaharness
--host prime-agent` (CLI, `host-config.ts`) and the web-UI generator
(`scaffold.ts`). Both mirrors always wrote a static one-line "not sandboxed"
sentence and never enumerated the denied capabilities or emitted the
warning file, regardless of policy — a 2026 instance of the same
"disconnected mirror" failure mode that ADR-045 fixed for host-config
coverage back in June. Fixed in both mirrors, tested, live-verified,
independently critiqued.

## MetaHarness Current Capability
MetaHarness scaffolds one declarative `HarnessSpec` into native config for
10 host runtimes (Claude Code, Codex, Copilot, OpenCode, pi.dev, Hermes,
OpenClaw, RVM, GitHub Actions, Prime Agent) through **three** independently
maintained codegen surfaces: the canonical `@metaharness/host-*` adapter
packages, the CLI's dependency-free mirror (`host-config.ts`, ADR-045), and
the web-UI's independent mirror (`scaffold.ts`), the latter two held to a
byte-parity contract (ADR-027). This three-surface design is deliberate
(the CLI stays dependency-free; ADR-045's own text), but it means a
fail-closed security control added to the canonical adapter has no
structural guarantee of propagating to either mirror — and until tonight,
for `host-prime-agent`'s sandbox-required disclosure, it never had.

Every row reads "None" for a real reason, not a blank: none of these
frameworks *are* trying to solve MetaHarness's problem — each one targets
itself, so it only needs to emit config for itself. MetaHarness's problem
(one spec → native config for nine *other* runtimes, via two independently
maintained generator surfaces that must stay byte-parity-aligned) is closer
to a packaging/build-tooling problem than an agent-framework one, which is
why no competitor builds it and why no competitor-side CVE/issue looks like
tonight's bug. The practitioner sync tools above (`agentsync`, "Plexus")
corroborate that the underlying risk — generated-config drift across
multiple AI-host surfaces — is real and currently hand-rolled around
industry-wide; they solve *sync* (reconciling existing configs), while
MetaHarness solves *generation* (emitting correct config from one spec in
the first place), which has no competitor-side precedent to compare against
at all.

## Hypothesis
Given a generated harness whose declared deny-list is non-empty (true of
every default-generated harness — `policyLists()`'s baseline rules always
include `Read(./.env)`, `Read(./.env.*)`, `Bash(rm:*)`, `Bash(git push:*)`),
when scaffolded for `prime-agent` via either `npx metaharness --host
prime-agent` or the web-UI generator, then the emitted output should
include a `SANDBOX-REQUIRED.md` file enumerating the denied capabilities
and a warning banner prepended to `install-prime-agent.md` — mirroring
`@metaharness/host-prime-agent`'s own `sandboxRequiredMd()`/`sandboxBanner()`
— relative to the baseline, which emits neither regardless of policy;
subject to: 0 regressions in existing `host-config.ts`/`scaffold.ts` tests,
CLI↔web-UI byte-parity preserved, and the canonical adapter package itself
left untouched (already correct).
