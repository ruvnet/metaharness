# security-adversarial SOTA Report — 2026-09-18

TL;DR: `mcp-scan.ts`'s and `threat-model.ts`'s "is the real `.env` secrets file
denied?" check used an unanchored `/\.env/` substring regex — CWE-777
("Regular Expression without Anchors") in a live security-verdict path. A
deny rule that only blocks the harmless `.env.example` template made the
scanner report "Secrets reachable: no" / verdict "clean" even with a broad
`Read(*)` grant and the real `.env` fully exposed. Fixed with a single
shared, left-anchored `envSecretGuarded()` helper; an independent critic
caught a residual left-anchoring gap in round 1, closed in round 2 same
night.

## Hypothesis

Given a scaffolded harness whose `.claude/settings.json` `permissions.deny`
list contains an entry that merely contains the substring `.env` without
actually blocking a bare `.env` or `.env.*` file (e.g.
`Read(./.env.example)`, or an unrelated `Read(./secrets.env)`), when
`envSecretGuarded()`'s anchored regex replaces the prior unanchored one,
then `mcp-scan`'s `no-secret-guard` finding and `threat-model`'s
`secretsReachable`/`verdict`/`exitCode` should correctly report the real
`.env` as unguarded, subject to: zero regression on every deny pattern the
repo's own generator (`host-config.ts`) actually emits, and zero test
weakening.

## Adversarial Critique (independent, round 1)

A separate subagent (no visibility into this session's reasoning) reviewed
the diff adversarially. Verdict: **ACCEPT-WITH-CAVEATS**. It independently
re-derived the bug, tested the new regex against realistic deny-list
strings, ran the full test suite and `tsc` itself (not trusting my
numbers), confirmed no reward-hacking (pure test additions, no weakened
assertions, no gold data touched), and confirmed the `.env.local`-only
design choice (conservative: narrower/unverifiable guards don't count) is
defensible. It then found a real residual gap I had not anchored: the
regex checked only what follows `.env`, not what precedes it, so
`Read(./secrets.env)` or `Read(./myapp.env)` — files unrelated to the
harness's real `.env` — still counted as "guarding" it, reproducing a
narrower version of the same false-guard bug. **Round 2 (same night)**:
left-anchored `ENV_GUARD_RE` to require `.env` start at a string/path
boundary (`^`, `/`, or `(`), added the critic's exact repro cases as tests,
re-ran the full suite (575/577, 0 regressions) and `tsc` (clean) against
the round-2 fix. This mirrors this repo's own established precedent (PR
#276's round-2 critic catching a missed `.mcp.json` case) rather than
shipping the round-1 gap disclosed-not-fixed.
