# Darwin-Evolution SOTA Report — 2026-10-07

TL;DR: `tier2-driver.ts`'s own comment claims Tier-2 agent-sandbox "tool
ordering is exercised (its output shapes the log / behaviour)" — it does
not. `toolPolicy` (one of the seven ADR-071 approved mutation surfaces) was
read, logged, and then discarded: it never affected `solved`/`durationMs`.
Any evolution run using `--sandbox agent` scored a toolPolicy-only child
byte-identically to its parent, making ~1/7 of Darwin's uniformly-sampled
mutation surface invisible to selection pressure whenever that sandbox mode
is used. Wired `orderKinds()`'s output into the solve threshold (a
mis-ordered policy costs one extra verification attempt — the lost chance
for a cheap gate to catch the bug before the expensive test run). 0
behavioral change for any compliant (baseline-shaped) `tool_policy.ts`.

## MetaHarness Current Capability
Darwin Mode's `evolve()` picks the mutated surface for each child uniformly
across the seven approved surfaces (`pickSurface`, `hash(...) % 7`),
independent of which sandbox mode scores the run. Three sandbox tiers exist:
'real' (repo test command, surface-independent), 'mock' (Tier-1 deterministic
simulation, ADR-102), 'agent' (Tier-2: executes the variant's real `.ts`
surface code offline, ADR-106). In 'agent' mode, `tier2-driver.ts` imports
and calls `planner`, `contextBuilder`, `retryPolicy` — and `toolPolicy`, but
only to push its output into a log string. `reviewer`, `memoryPolicy`, and
`scorePolicy` are not imported there at all (scorePolicy is deliberately
inert everywhere — `scorer.ts`'s own comment: "a variant may *propose*
weights, but the verdict... is computed here, so a variant can never
re-grade itself", correctly keeping the anti-self-grading control intact).
`mock-sandbox.ts`'s own module doc separately claims "a mutation to
retryPolicy / contextBuilder / toolPolicy actually changes the outcome" —
but `extractSurfaceParams` never reads `tool_policy.ts` either; disclosed,
not fixed tonight (see Recommended Next Steps).

This isn't quite the same shape as "reward hacking" in the adversarial
sense (nothing is gaming the evaluator) — it's the more mundane sibling
OpenAI's Feb 2026 retirement illustrates at the model-eval layer: the
*measurement* layer silently not reaching the thing it claims to measure,
which produces false negatives (a genuinely better toolPolicy mutation
would never show a score delta) rather than false positives. Darwin Mode's
own `cladeOutcomes`/epistasis-linkage machinery would have quietly learned
"toolPolicy mutations never correlate with success" in 'agent' mode — a
wrong conclusion baked in by the sandbox, not the mutation.

## Hypothesis
Given a Tier-2 ('agent' sandbox) evolution run, when a child variant's
`tool_policy.ts` reorders `ORDER` so that `'test'` is not scheduled last,
then `runVariantTaskAgent`'s resulting trace should flip from solved to
unsolved for a task whose `failAttempts` sits at the retry-budget boundary,
relative to an otherwise-identical variant with a compliant (cheap-first)
`tool_policy.ts` — subject to: zero behavioral change for the unmutated
baseline template, zero change to `reviewer`/`memoryPolicy`/`scorePolicy`
surfaces (out of scope tonight), zero regressions in the darwin-mode suite,
and the ADR-071 safety gate still runs first.

## Evaluation
- **Baseline (pre-fix)**: full darwin-mode suite 665/665 (14 pre-existing
  skips). `npx tsc --noEmit` clean.
- **Candidate, round 1**: `packages/darwin-mode/src/tier2-driver.ts` —
  `order` feeds a `misorderPenalty` (1 iff the schedule does not end in
  `'test'`, else 0) into the solve-attempt threshold. 1 new e2e test.
- **Non-vacuous pre/post proof (round 1)**: confirmed by direct `git stash`
  of just `tier2-driver.ts`: pre-fix the new test fails with `expected +0
  not to be +0` (the misordered variant solves when it should not be able
  to); post-fix it passes, with the pre-existing contextBuilder e2e test
  unaffected either way.
- **Independent critic, round 1: ACCEPT-WITH-CAVEATS.** Re-derived the
  attempt arithmetic by hand and by running the suite rather than trusting
  the diff; confirmed the baseline-non-regression and scoring-reach claims
  directly from `templates.ts`/`scorer.ts`. One real gap found: the
  round-1 guard (`order.length > 0 && order[length-1] !== 'test'`) let a
  degenerate `tool_policy.ts` that filters its schedule down to `[]`
  silently match baseline (misorderPenalty=0) instead of being penalized —
  "misordering invisible" was fixed, "degenerately-empty policy invisible"
  was not.
- **Candidate, round 2 (same session)**: simplified the guard to
  `order[order.length - 1] !== 'test'` — `undefined !== 'test'` is true for
  an empty array, so a degenerate schedule is now penalized like a
  misorder instead of silently treated as compliant. 1 more e2e test
  (empty-schedule case).
- **Full suite post-fix (both rounds)**: 667/667 (+2, 0 regressions).
  `tsc --noEmit` clean. 0 downstream importers of
  `tier2-sandbox.ts`/`tier2-driver.ts` outside `darwin-mode` (checked
  directly).
- receipt: `EVALUATED=yes, VERDICT=ACCEPT`. The round-1 critic's own
  caveat was closed same night and re-verified (full suite green,
  `tsc` clean) — not carried forward as an open caveat.
