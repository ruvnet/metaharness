## OBSERVATION

`packages/flywheel/src/gate.ts`'s `meetsPromotionRule` clause 2 required
`candidate.noopRate < baseline.noopRate` (strict) unconditionally, ANDed
with 4 other clauses. `noopRate` is documented in `types.ts` as a
"fraction" (floor 0, lower is better).

## INFERENCE

The strict `<` requirement on a floor-0 rate is a "ceiling lockout":
once a lineage's baseline reaches noopRate=0, the clause becomes
permanently unsatisfiable, silently blocking every future promotion on
that branch regardless of primary/cost/anchor quality. This was not a
synthetic worst case — it is already latent in the repo's own flagship
mechanism-proof artifact (`experiments/signal-flywheel`), which reached
noopRate=0 at generation 2 of 8 and, per its own README, correctly
documents (without diagnosing it as a bug) that "a higher score alone
does not buy a promotion under this gate" — i.e. the lockout was already
observed and narrated as intended behavior, not previously recognized
as a defect.

## DECISION

Fix `gate.ts` clause 2: when `baseline.noopRate <= 0`, require
`candidate.noopRate <= 0` (tie-at-floor satisfies the clause); otherwise
keep the original strict `<` requirement unchanged. Verified this leaves
every clause with `baseline.noopRate > 0` byte-identical (existing tests
for that regime pass unmodified). Independent adversarial critic (fresh
sub-agent, no authorship context) returned **ACCEPT**: confirmed
byte-identical off-floor behavior, confirmed the real-data test's numbers
independently, confirmed clauses 1/3/4/5 remain independent containment
against an adversarial Evaluator gaming noopRate to fake-zero, and
disclosed one minor residual (float-noise near-zero, e.g. `1e-18`, is
not treated as "at floor" — an inherent float-comparison tradeoff, not a
defect this fix introduces; flagged for a future night, not fixed
tonight to keep the diff minimal).

**Disclosure**: this patch changes `gateFingerprint(meetsPromotionRule)`
(the function's `.toString()` source changed) — any external verifier
that pinned the old fingerprint value must re-pin after this change. No
consumer in this repo currently pins a fingerprint value in committed
data (checked: no `gate-fingerprint` literal in any committed
`docs/`/`experiments/`/test fixture) — the sealed `experiments/*`
bundles verify without `--gate-fingerprint` supplied (confirmed above),
so nothing in-repo breaks. This is called out for any downstream
integrator, not because anything in-repo needs updating.
