# Darwin Shield (ADR-155) Safety-Gate Coverage SOTA Report — 2026-11-07

**TL;DR:** Tonight's darwin-evolution deep dive on `@metaharness/darwin`'s "Darwin Shield"
(ADR-155, the defensive-only vuln-discovery harness with a hard output-safety gate)
found a real, live coverage gap in 2026: `RuvSecurityMemory.writeConfirmed()` /
`writeFalsePositive()` persist raw `Finding` records into long-term ruVector memory
without ever calling the module's own `gateFinding()` safety redactor — unlike the
one production call path that reaches them (`runSwarm`), which always gates
findings via `gateOutputs()` before archiving. Two existing call sites
(`compounding.ts`, `ablation.ts`) call these two memory methods directly with raw,
corpus-derived findings, bypassing the gate entirely. Fixed by gating inside both
methods. This is the exact "coverage gap" failure shape documented repeatedly in
2026 output-safety-filter research (below): a gate correctly covers the primary
emission path but not a sibling persistence/retrieval path. Independent critic:
**ACCEPT**, 2 non-blocking caveats (see Evaluation).

## MetaHarness Current Capability

Darwin Shield (`packages/darwin-mode/src/security/`) implements a 4-gate
defense-in-depth design (`policy.ts`): `assertScope`, `redactUnsafeOutput`,
`gateFinding`, `gateOutputs`. The documented pipeline is "profile → rank → context →
hypotheses → static + fuzz → review → SAFETY GATE → patch → score → archive", and
the acceptance-critical invariant is `unsafeOutputs === 0`. Confirmed via independent
architecture review and the adversarial critic: `runSwarm` correctly applies
`gateOutputs()` before anything returns or archives (`agentic.ts`'s
`runAgenticLoop` also gates its own return value via `gateOutputs`, but never calls
`RuvSecurityMemory.writeConfirmed`/`writeFalsePositive` at all — it has no memory
dependency, corrected from an earlier draft of this finding). The module also contains
~3 other exported, documented pipeline functions with no production caller and no
test coverage (`writeAdvisory` in `agents.ts`; `runInvariantHarness`/
`evolveInvariants` in `invariant.ts`) that would reintroduce the same bypass if ever
wired in without their own internal gating — disclosed below, not fixed tonight
(STEP 6's one-conceptual-change scope).

Darwin Shield's rather than mainstream tooling.

## Hypothesis

Given Darwin Shield's `compounding.ts`/`ablation.ts` code paths, which call
`RuvSecurityMemory.writeConfirmed()`/`writeFalsePositive()` directly with findings
built by `findingFromSite()` (never passed through `gateOutputs()`), when
`writeConfirmed()`/`writeFalsePositive()` are hardened to call `gateFinding()`
internally before persisting, then a `Finding` carrying unsafe content (per
`UNSAFE_OUTPUT_PATTERNS`) reaching either method is redacted before it lands in the
`confirmedFindings`/`falsePositives`/`patches` ruVector collections, subject to: (a)
a finding with no unsafe content is stored byte-identical to before; (b) zero
unredacted unsafe-pattern occurrence in storage via these two methods; (c) zero
regression across darwin-mode's full suite.

`npm audit` 0 vulnerabilities.

**Independent critic verdict: ACCEPT.** Checked for weakened tests, altered gold
data, evaluator-exploiting assertions, a double-gating regression on the
already-safe `runSwarm` path (`redactUnsafeOutput` is idempotent — confirmed
empirically), and missed call sites (none — the fix sits at the sink, not at each
caller). Two non-blocking caveats, both corrected before shipping: (1) `gateFinding`
redacts only `evidence`/`patch`/`test`, not `weakness`/`file`/`symbol`/`id` —
pre-existing, sufficient for every current caller, now stated explicitly in the
code comment instead of implying whole-`Finding` sanitization; (2) an earlier draft
misattributed a `writeConfirmed` call to `runAgenticLoop`, which gates its own
return value but never calls `RuvSecurityMemory` — corrected above.
