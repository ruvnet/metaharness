# host-adapters (kernel) SOTA Report — 2026-10-14

TL;DR: `@metaharness/kernel`'s `package.json` `exports` map was missing two subpaths real, documented consumers depend on: `./self-evolution` (the exact import docs/USAGE.md and examples/multi-host/README.md tell users to write) and `./package.json` (used by `create-agent-harness`'s `harness diag` to read the locally-installed kernel's version for its ADR-028 version-skew check — its own docstring calls this "the ONE cross-machine question that almost every support ticket turns out to be"). Both threw `ERR_PACKAGE_PATH_NOT_EXPORTED` for every real npm-installed consumer. For `harness diag`, the consequence was actively wrong output, not just a gap: a correctly-installed harness at the exact manifest-matching kernel version got told `verdict: "unparseable"` and `"Run: npm install @metaharness/kernel@X (kernel not installed locally)"` — reproduced tonight outside this monorepo, where a dev-fallback path happens to mask the bug. Fixed by adding both subpaths.

## MetaHarness Current Capability

`packages/kernel-js/package.json`'s `exports` map listed `.`, `./memory`, `./memory-rvf`, `./dispatch` — but `packages/kernel-js/src/self-evolution.ts` (ADR-014/ADR-006, `SelfEvolvingRouter`) has shipped a built `dist/self-evolution.js` since it was added, and is the exact module `docs/USAGE.md:234` and `examples/multi-host/README.md:59` tell users to import. Neither file nor any in-repo test ever exercises the *documented* import path — `self-evolution.test.ts` imports the source directly via a relative `../src/` path, which bypasses `exports` entirely and could never have caught this. Separately, `create-agent-harness/src/diag.ts`'s `resolveLocalKernelVersion()` (the ADR-028 version-skew check inside `harness diag`) calls `require.resolve('@metaharness/kernel/package.json')` as its PRIMARY resolution path, with a dev-mode-only fallback (`resolve(__dirname, '..', '..', 'kernel-js', 'package.json')`) that only exists inside this monorepo checkout — meaning the primary path has been broken for every real published harness since this subcommand shipped, silently, with no error surfaced (by design — "we never throw... a missing kernel is the WHOLE POINT of this diagnostic" — but `undefined` here doesn't mean "missing," it means "the resolver itself is broken").

## Hypothesis

Given a real (not-monorepo, not-dev-fallback) installation of `@metaharness/kernel` via npm, when `@metaharness/kernel/self-evolution` is imported per the published docs, or when `create-agent-harness`'s `harness diag` resolves `@metaharness/kernel/package.json` to read the installed kernel's version, then both resolutions should succeed exactly as documented/intended, subject to: (a) no other currently-exported subpath's resolution target or shape changes; (b) `harness diag`'s version-skew verdict for a correctly-matched kernel version changes from `'unparseable'` (with a false "not installed locally" actionable) to `'match'` (no actionable); (c) zero regressions in kernel-js's or any of its 14 direct TS consumers' test suites.

## Recommended Next Steps

1. **Wire `publint`/`are-the-types-wrong` into CI** for every package shipping an `exports` map — this exact bug class (a built source file whose `exports` entry was never added) has no automated guard today and could recur for a different subpath.
2. **`diag.ts`'s dev-fallback masks its own primary path from in-repo testing.** `resolveLocalKernelVersion()`'s `catch` branch finds the real `kernel-js/package.json` via a path relative to `diag.ts`'s own `__dirname` — always inside this monorepo during any in-repo test run, so a naive test of the primary path can pass for the wrong reason, as happened during tonight's own investigation until the repro moved outside the repo tree. Consider an injectable workspace-root or test hook.
3. **SDK scan (disclosed, not fixed tonight):** `defineHarness()` never validates `description` despite its README stating it throws (the SDK's own existing test proves this); `defineTool`/`defineHook`/`defineMcpServer` skip the `ensureKebab()` check `defineAgent`/`defineSkill`/`defineHarness` all enforce; `defineHarness()`'s collision check covers agent/skill names only, not tool/mcpServer names. Small, mechanical candidate for a near-future night — independently proposed by two of tonight's five research roles.
4. **Kernel scan (disclosed, not fixed tonight):** `index.ts`'s `loadNative()` has no API-shape check (unlike `loadWasm()`), so a native addon with missing/renamed exports would throw raw instead of falling back. `memory-rvf.ts`'s `ensure(ns)` has the same check-then-await-then-write race as the `SessionLog`/`TrajectoryStore` family (latent — `@ruvector/rvf` isn't installed anywhere in this repo). `TrajectoryStore.rotateIfLarger()`'s TOCTOU race (flagged 2026-10-09) stays deferred — re-evaluated tonight as dead code (zero production consumers anywhere, not even `packages/bench/src/draco/`, its own doc comment's claimed consumer), so three of five independent research roles scored it below tonight's pick once reachability was checked.
5. **Review backlog, restated once, not re-escalated:** 18 open PRs unmerged; the oldest (#360, 2026-09-27) is 17 days old, past the 14-day STALE threshold, with only one merge (#386) since the 2026-09-26 mass-merge.
