# MCP Native-Host Detection Gap — Security SOTA Report — 2026-10-23

TL;DR: `harness mcp-scan`'s `scanMcp()` (and `harness threat-model`'s `mcpInUse`, which delegates to it) only ever looked for MCP registration in `.harness/mcp-policy.json`, `.mcp.json`, or `.claude/settings.json`'s `mcpServers` key. It never independently looked at the 5 OTHER hosts' own native MCP config files (codex, hermes, openclaw, copilot, opencode). Live-reproduced: scaffold `--host codex`, delete `.harness/mcp-policy.json`, and a real, live, ungoverned `[mcp_servers.*]` entry in `.codex/config.toml` got reported as "No MCP surface — nothing to scan" (`mcpEnabled: false`, `worst: info`). Fixed by giving the scanner its own independent detection of all 5 native formats rather than relying transitively on the generator always having stamped a policy sidecar file. An independent critic caught two real bugs in the first draft (wrong openclaw path; a false-positive on any stray file in `optional-mcps/`) — both fixed and re-verified live before this report was finalized.

## MetaHarness Current Capability

`scanMcp()` (packages/create-agent-harness/src/mcp-scan.ts) is the single choke point `threat-model.ts`'s `mcpInUse` and, downstream, `oia-manifest.ts`/`score.ts` all rely on as the authoritative "is MCP in use" answer. A 2026-10-18 dream cycle (#413/#414) fixed the *generator* side — the CLI scaffolder now always stamps `.harness/mcp-policy.json` whenever it detects a native-host MCP registration at scaffold time (index.ts:777-786) — but the *scanner* itself (meant to be runnable standalone against any directory, not just one the generator just produced) never independently checked those same 5 native formats. Any harness predating 2026-10-18, any harness with its policy file deleted or hand-edited, or any directory where MCP was registered by hand outside the generator, hit the gap this candidate closes.

## Hypothesis

Given a harness directory where an MCP server is registered only via a native host format (`.codex/config.toml`, `optional-mcps/*.json`, `.openclaw/openclaw.json`, `.vscode/mcp.json`, `.opencode/opencode.json`) and `.harness/mcp-policy.json` is absent, when `scanMcp()` is extended to independently detect these 5 surfaces, then `mcpEnabled` should be `true` and `worst` should escalate to `high` (`no-policy`), relative to the pre-fix baseline (`mcpEnabled: false`, `worst: info`, "clean"), subject to: (a) zero false positive on a directory with no real MCP registration anywhere, including a stray non-registration file inside `optional-mcps/`; (b) zero regression on hosts that register no MCP at all (e.g. `rvm`); (c) the full existing test suite (627 tests) stays green; (d) `threat-model.ts`'s `mcpInUse` inherits the fix automatically with no separate change needed.

## Adversarial Critique

Independent critic (fresh agent, no prior session context, given the diff + an explicit skeptical checklist, instructed to reproduce rather than trust): **ACCEPT-WITH-CAVEATS → both caveats fixed same night.**

1. **False negative (openclaw path)**: my first draft checked a bare top-level `openclaw.json`; the CLI's real emitter (`host-config.ts:150`, matching `index.ts:780`'s own pre-existing check) writes `.openclaw/openclaw.json`. Live-reproduced by the critic against a real scaffold; the openclaw host silently stayed broken under the identical test every other host passed. **Fixed**: corrected path, added a regression test that pins the WRONG path as a non-match.
2. **False positive (`optional-mcps/` directory)**: my first draft treated *any* file's presence in that directory as a registration (`readdirSync(dir).length > 0`) — a stray `README.md` would trigger a HIGH finding with zero real MCP registered. **Fixed**: now requires at least one `*.json` file that parses to a non-empty object, with new regression tests for both the stray-file and empty-file cases.

Both fixes re-verified: full suite 627→641/643 (+14, 0 regressions), `tsc` clean, all 5 native hosts + `rvm` re-confirmed live end-to-end after the fix.

**Separately disclosed, confirmed independently by the critic, NOT fixed in this PR**: `threat-model.ts`'s own `verdict`/`exitCode` computation (lines ~109-120) does not escalate off `scanMcp()`'s `worst` field at all — it reads a hand-picked boolean grid instead. On the same codex fixture used above, `scanMcp` → `worst: 'high'`, but `buildThreatModel()` → `verdict: 'clean', exitCode: 0`. **This is not a new finding**: issue #399 / PR #400 (2026-10-13, this repo's own prior `security-adversarial` night) already diagnosed and fixed this exact gap — but PR #400 is still open, draft, and now shows `mergeable_state: dirty` (conflicts with current `main`). Recommendation: resolve #400's merge conflict and land it, rather than drafting a third independent fix for the same bug — see Recommended Next Steps.
