## Hypothesis
Given a `TrajectoryStore`-backed JSONL log with N valid records followed by
one corrupted/truncated line (crash mid-`appendFile`, or manual edit), when
`readAll()` is replaced with a line-by-line try/catch that skips and reports
corrupt lines via a new `readAllWithDiagnostics()`, then callers recover the
N valid records instead of losing all of them — subject to: byte-identical
`records` for any file with zero corrupt lines, `corruptLines` empty in that
case too, and zero downstream call-site changes required (none exist yet).

## Evaluation
- **Baseline (pre-fix, reproduced via `git stash`, re-checked after round 2's
  extra test)**: 4/8 tests fail non-vacuously, all 4 being new tests (4
  pre-existing tests pass unchanged) — `readAll()` throws `SyntaxError` on
  the corrupted line, and `readAllWithDiagnostics` doesn't exist yet
  (`TypeError`).
- **Candidate**: `readAll()` now delegates to `readAllWithDiagnostics()`
  (try/catch per line, collects 1-based corrupt-line numbers); `readAll()`'s
  external signature/behavior is unchanged for any clean file.
- **Independent critic, round 1: ACCEPT-WITH-CAVEATS.** Confirmed the fix
  closes the disclosed gap (no uncaught-throw path survives inside the
  parse loop) and re-derived the zero-downstream-importer claim itself
  (`grep -rn "TrajectoryStore" packages --include=*.ts | grep -v kernel-js`
  hits only a stale vendored `dist/` artifact under `packages/bench/
  node_modules/`, not a live source import). Found 3 real gaps: (a)
  `readAll()` silently drops `corruptLines` with no disclosure at the call
  site most callers would actually use; (b) the new tests' corrupted
  fragment always had its own trailing newline — an easier case than a
  genuine torn write, which leaves NO trailing newline and would merge with
  whatever the next `append()` writes; (c) corruption detection is
  JSON-syntax-only, a valid-JSON/wrong-shape line (`{}`, `42`) passes
  through undetected despite the `TrajectoryRecord` type assertion.
- **Candidate (round 2)**: added a JSDoc caveat to `readAll()` disclosing
  (a) and (c) explicitly, and a new test reproducing the harder torn-write
  case (b) — which confirms and documents a real residual limitation
  (the torn tail AND the next, otherwise-good record both get merged into
  one unparseable line and are lost together) rather than silently
  papering over it. Not fixed tonight: recovering a mid-line torn write
  needs a byte-level/incremental JSON boundary scanner, a materially larger
  change than tonight's one-conceptual-change scope; flagged in Recommended
  Next Steps.
- `packages/kernel-js` full suite (7 files): 63 passed + 1 pre-existing skip
  = 64 total (round 1 alone measured 62 passed + 1 skip = 63; round 2's 1
  extra test brings it to 64), 0 regressions across either round;
  `tsc --noEmit` clean both rounds.
- Downstream blast-radius: zero live source importers of `TrajectoryStore`
  outside `kernel-js` (confirmed independently by both this session and the
  critic). `packages/create-agent-harness` full suite (622/624, 2
  pre-existing skips) re-run anyway as the repo's central consumer of
  `@metaharness/kernel` generally: 0 regressions.
- Reward-hack check: no benchmark/gold data/test threshold touched; all 4
  new tests fail non-vacuously pre-fix (`SyntaxError` / `TypeError: … is
  not a function`), including the round-2 "KNOWN LIMITATION" test — it
  is real evidence the API now exists and returns the documented (still
  partial) result, not a rubber-stamp: it does NOT claim the underlying
  torn-write-merge limitation itself was fixed, only that it is now
  reachable and asserted on rather than silently unreachable.

## Recommended Next Steps
1. **Fix `SessionLog.append()`'s index-assignment race** (same file's sibling
   module, `packages/kernel-js/src/session.ts:271-303`): `nextIndex` is read
   synchronously, but the state mutation that reflects a written event
   happens only after `await appendFile(...)` resolves. Two concurrent
   `append()` calls on the same branch (e.g. via `Promise.all`) can both
   read the same index before either write-back lands, producing two
   persisted events with the same `{branch, index}` — a log corruption
   `parseLog()` only detects later, on `open()`/`validate()` (as a
   "duplicate event" error), by which point the log may be unrecoverable.
   Needs a proper serialization primitive (in-flight promise chain per
   branch), not a one-line fix — good candidate for a dedicated
   `kernel`-focused night with its own hypothesis/benchmark.
2. **`@metaharness/sdk`'s `defineHarness()` collision-check gap**
   (`packages/sdk/src/index.ts:126-136`): the function's own comment says
   "Detect name collisions across agents/skills/**tools**", but the code
   only builds `agentNames`/`skillNames` Sets — `tools` (and `mcpServers`)
   are never checked, so two `ToolDef`s with the same `name` pass validation
   silently. This is the exact ADR-046 "silent-drop" bug class the repo has
   repeatedly fixed in host adapters, now found one layer up in the SDK that
   constructs the spec those adapters consume. Small, safe, well-scoped fix
   for a near-future `sdk`- or `generator-genome`-focused night.
3. Security-adversarial's 2026-09-28 night (#361/#362, not tonight's surface)
   disclosed 8 more live instances of a fail-open NaN-bypass pattern in

   process-killing watchdog's `CEILING` check — flagged there as the
   single most severe open finding repo-wide; restated here only for
