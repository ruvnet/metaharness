## MEASUREMENT

**Round 1** (env added uniformly to both the stdio and the http-transport branch, `--env`
placed right after the server name token):
- Baseline (`git stash` on the one changed file): 3/3 new assertions in
  `settings.test.ts` fail non-vacuously — the exact predicted missing-`--env` output.
- Candidate: string-equality tests pass (39/39, 0 regressions). `tsc` clean.
- Independent adversarial critic ran the actual generated lines against the real,
  locally-installed `claude` CLI (`claude --version` → `2.1.319 (Claude Code)`), not just
  the string-equality tests:
  - stdio branch: `claude mcp add 'srv' --env 'API_KEY=secret' -- 'node' 'x.js'` → exit 0,
    `claude mcp get` shows `env: {"API_KEY": "secret"}` — correct.
  - http branch: `claude mcp add --transport http 'remote' --env 'TOKEN=abc'
    'https://example.com/mcp'` → **exit 1, `error: missing required argument
    'commandOrUrl'`**. `--env` is a variadic commander.js option that swallows every
    subsequent bare token until the next recognized flag or a `--` separator; with no `--`
    before the URL, `--env` consumed the URL positional.
  - Separately, even with `--`/correct-ordering variants, the critic found `claude mcp add
    --transport http` **never stores an `env` key at all** for an http-transport server —
    confirmed independently in round 2 below by reading the resulting `~/.claude.json`
    entry directly.
  - **Verdict: REJECT.**

## INFERENCE

The round-1→round-2 cycle is itself evidence of why STEP 10's independent-critic gate exists:
a diff that passes its own hand-written string-equality tests can still be wrong against the
real target system, because the tests were written by the same reasoning that produced the
bug fix (same blind spot). The critic's choice to run the actual CLI, not just assert on
strings, is what caught it. The deeper fact worth carrying forward: `env` is not a
host-adapter oversight for http-transport MCP servers — it is **not supported by the real
`claude mcp add --transport http` command at all**, which makes `host-codex`'s existing,
already-shipped `--env` flag on its own `--url` branch (seen while comparing adapters
tonight) a live open question for a future host-adapters night: does the real `codex` CLI
actually honor `--env` for a `--url`-based server, or does `host-codex` have the same latent
no-op that `host-claude-code` almost reintroduced tonight? Not verified tonight (out of
scope — codex CLI was not installed in this environment to test against); flagged as a
Recommended Next Step, not asserted as a bug.

## HYPOTHESIS (STEP 3.3, frozen before implementation; see gist for the exact text and the
one permitted revision after round-1's falsification)

Given a stdio MCP server spec with `env`, `host-claude-code`'s `mcpAddCommands()` should
project it via `--env KEY=VALUE`, verified end-to-end against the real CLI, not just by
string equality; given a url/http-transport spec with `env`, since the real CLI does not
support per-server env for that transport, the gap should be disclosed, not silently
dropped. Confirmed by evidence above on both halves.

## DECISION

**ACCEPT.** Evidence: evaluated above (round 2). Verdict: ACCEPT (independently confirmed
by two critic rounds, the second with no caveats). Effect: closes a real secrets-delivery
gap for stdio MCP servers targeting Claude Code (every sibling adapter already had this);
corrects a claim this session itself made and had rejected, rather than weakening the test to
make it pass. 0 regressions at every tier measured (package: 40/40; downstream:
703/705+2skip). Reward-hack check: clear — diff is additive only (no existing test altered
or removed across either round; round 1→2 only replaced round 1's 2 broken http-branch
assertions with 2 correct ones), no gold data touched, no cost/threshold manipulation.
Security review: no negative security implication — the pre-fix behavior failed closed (a
missing credential breaks the MCP server's own auth, it does not leak one); the fix restores
intended functionality for the documented, now-verified-working case and avoids a worse
outcome (a broken/ignored flag) for the unsupported case.
