# Security-Adversarial SOTA Report — 2026-11-28

TL;DR: `packages/redblue/src/config/safety.ts`'s `redact()` — the single
chokepoint that scrubs secrets from every stored red/blue-team transcript
and every real outbound HackerOne vulnerability-report draft — used
non-global regexes for 5 of 6 `CREDENTIAL_PATTERNS`. `String.replace()`
with a non-global regex only replaces the *first* match, so a payload
carrying two credential-shaped tokens of the same kind only had the first
one redacted; the second leaked straight through into stored evidence and
`reports/hackerone.ts`'s draft text. Fixed by deriving independent global
copies of those 5 patterns for the redaction path only, leaving the
originals (used by `assertNoLiveCredential()`'s `.test()` calls) untouched
to avoid a *different*, worse regression: a shared global regex's mutable
`lastIndex` would make that credential-refusal guard stateful and able to
silently miss a credential on a later call.

## Hypothesis (frozen before implementation)

Given a payload passed to `redact()` containing **N > 1** occurrences of
the same `CREDENTIAL_PATTERNS` token type, when the fix is applied, then
all N occurrences should be replaced with `[REDACTED:<label>]` — not just
the first — subject to: `assertNoLiveCredential()`'s existing per-call
behavior (including across repeated calls) must stay byte-identical,
nothing else in `SENSITIVE_PATTERNS`/`CREDENTIAL_PATTERNS` changes shape,
and zero regressions in `packages/redblue` or its one downstream consumer
(`create-agent-harness`'s `redblue` CLI dispatch).

**Independent critic (fresh subagent, adversarial, not self-review):**
verdict **ACCEPT-WITH-CAVEATS**. Confirmed the fix empirically (its own
`git stash` repro, its own standalone node snippet proving a global
regex's `lastIndex` resets around `String.replace`, a full repo-wide grep
confirming `assertNoLiveCredential()`'s non-global patterns are untouched)
and corrected an assumption this session almost shipped: `private_key` is
*not* a residual gap — the `.map()` globalizes all 6 `CREDENTIAL_PATTERNS`
entries, including it. The critic found one **real, pre-existing (not
introduced)** gap: two same-type credentials glued with no separator
between them (e.g. `...1Bearer bbbb...2`) only partially redact, because
the first match's greedy character class consumes into the second token's
own prefix. Verified independently by this session too (`git stash`
confirms identical behavior on plain `main`) and pinned with a new,
clearly-labeled "KNOWN LIMITATION" test so a future fix changes it on
purpose, not by surprise. Disclosed, not fixed tonight — closing it needs
a different mechanism (boundary-aware matching or run-length capping), a
second conceptual change kept out of this diff.
