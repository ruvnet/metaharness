# ADR-273: Darwin Mode — the `llm-agent` sandbox (real LLM evaluation substrate)

**Status**: Accepted (implemented)
**Date**: 2026-09-01
**Project**: `ruvnet/agent-harness-generator`
**Related**: ADR-070 (evolve loop), ADR-071 (mutation surfaces + safety gate), ADR-072 (scoring/promotion), ADR-099 (`real` sandbox degeneracy), ADR-102 (`mock` sandbox), ADR-106 (`agent` / Tier-2 sandbox)

> None of the three existing evaluation substrates — `real` (repo test command), `mock` (deterministic scripted simulation), `agent` (Tier-2, executes a variant's real TypeScript surface CODE offline) — can measure whether one phrasing of a *prose* prompt-genome surface actually changes real agent behaviour. All three are, by design, independent of the surface's literal text content for a prompt-only genome. This ADR adds a fourth mode that genuinely invokes a real LLM per task, so a prose-genome consumer can finally get real evolutionary signal.

## Context

A downstream consumer (`ruvnet/wifi-densepose`, the `harness/ruview` contributor harness) maintains a prompt genome (`ruview-contributor-harness`) whose seven surfaces are natural-language policy sentences — e.g. `reviewer: "Reject secret exposure, unsupported accuracy claims, bypass flags, unbounded subprocesses, missing tests, or mutations outside the requested workspace."` — meant to steer a real LLM-driven contributor agent's behaviour on real repository tasks.

Running `metaharness-darwin evolve` against that repo with each existing sandbox mode produced degenerate, non-differentiating results:

- **`--sandbox real`** (default): every variant scores identically (`0.435`, `pass=0.00`) because the repo's own test command has no dependency on the mutated surfaces at all (this is the documented, expected ADR-099 degeneracy).
- **`--sandbox mock`**: every variant *also* scored identically (`0.765`, `pass=0.60`) for this genome, despite ADR-102's claim that mock mode makes the trace "a pure function of the variant's surface parameters." Reading `mock-sandbox.ts`'s `extractSurfaceParams` shows why: it extracts behaviour-shaping numbers via regex against *structured code patterns* — `maxAttempts\s*[:=]\s*(\d+)`, `.slice(0, N)`, `threshold\s*[:=]\s*(0?\.\d+)` — patterns a genome whose surfaces are prose sentences (not TypeScript config literals) never contains. Every extraction silently falls back to its default, so the simulated agent loop runs identically regardless of surface content. This is not a bug in `mock-sandbox.ts` — it is working exactly as designed for a genome whose surfaces are executable-code-shaped; it is simply the wrong substrate for a prose-shaped genome.
- **`--sandbox agent`** (Tier 2, ADR-106): also identical to `real` (`0.435`, `pass=0.00`). `tier2-sandbox.ts` spawns a child process to *import and execute* a variant's surface files as literal TypeScript modules (`buggyAfter`'s fixture depends on `context_builder.ts` implementing a real `.slice(0, N)` ranking function). A prose-only genome has no such executable module behind its surfaces, so there is nothing for Tier 2 to run differently — again, correct behaviour for the wrong genome shape, not a defect.

A further, separate finding while investigating this (out of scope for this ADR, noted for the record): the downstream consumer's `flywheel/genome.json` prose is *never read* by `metaharness-darwin evolve` at all — `repo_profiler.ts`/`generator.ts`/`templates.ts` synthesize their own generic baseline `.ts` surface files from a repo scan (confirmed: zero references to `genome.json` anywhere in `packages/darwin-mode/src/*.ts`). Whatever a real evolutionary signal this ADR enables will only be genuinely useful to that consumer once (or if) a follow-up bridges Darwin's synthesized baseline to their actual policy prose — a separate, future ADR.

## Decision

Add a fourth, fully independent sandbox mode, `'llm-agent'`, as a new module (`llm-agent-sandbox.ts`) that does not modify `sandbox.ts`, `mock-sandbox.ts`, or `tier2-sandbox.ts`, and touches `evolve.ts`/`types.ts`/`cli.ts` only at their existing sandbox-mode dispatch points (three-way branches become four-way; no existing branch's behaviour changes):

- **Genuinely calls a real LLM.** Spawns the `claude` CLI (`execFile`, no shell, argv-split — same no-injection discipline as `tier2-sandbox.ts`) in non-interactive mode (`-p`), with `--restricted` (removes Bash/PowerShell/REPL and other command-execution tools — a single read-only judgement call has no legitimate use for them), `--permission-mode plan` (defense in depth on top of `--restricted`), and `--output-format json` for deterministic parsing. Environment is scrubbed to `PATH`/`HOME`/`USERPROFILE` plus two identifying variables — the same posture `tier2-sandbox.ts` already uses for its own child process.
- **Task design avoids the model's own safety training as a confound.** A task that asked the model to evaluate a *security* judgement (e.g. "is this embedded secret OK to leave in place?") would let the model's baseline safety alignment override contradictory appended guidance regardless of whether the sandbox mechanism works — a false negative that would look like "still no signal" when the mechanism is actually fine. `DEFAULT_LLM_AGENT_TASKS` instead asks a single, cheap, *process/style* judgement question (does a small pure function need a test before merge) with a declared `desiredAnswer` — a domain a real reviewer-surface's appended guidance can plausibly and reliably steer without any safety-training tension.
- **Grading is deterministic**, not LLM-self-reported: the first word of the real JSON response's `result` field is compared against the task's declared `desiredAnswer`. A match is `exitCode: 0` ("solved" — the same convention `scorer.ts`'s `taskSuccess = passed/total` already reads from every other sandbox), a mismatch is `exitCode: 1`.
- **The ADR-071 safety gate runs first, explicitly**, inside `runVariantTaskLlmAgent` itself — `inspectVariant(variant.dir)` — rather than being assumed to have already run upstream. (Aside, noted for the record: `tier2-sandbox.ts`'s own module doc claims "The gate (`inspectVariant`) has already cleared the variant before any execution", but `inspectVariant` is in fact never called anywhere on the Tier-2 code path today — confirmed by search. Out of scope to fix here since it is pre-existing and unrelated to this ADR's own new code, which does call it.) A disqualified variant is sealed with the reserved `exitCode: 99` and never reaches a real LLM call — no real spend on an unsafe variant.
- **Real spend is capped by the CLI, not the library.** `--sandbox llm-agent` estimates `(generations * children + 1) * taskCount` real invocations and refuses to proceed past a default cap of 15 unless the caller raises it explicitly (`--llm-agent-cap <n>`) or confirms (`--llm-agent-confirm-large-spend`). This mirrors none of the other three modes (all $0), because this is the first sandbox mode with a real per-invocation dollar cost.
- **Wiring**: `types.ts`'s `sandboxMode` union gains `'llm-agent'`; `EvolutionConfig` gains `llmAgentTasks?`; `evolve.ts`'s `evaluateVariant` dispatch gains the fourth branch; `cli.ts`'s `--sandbox` flag validation and its "no signal at default" stderr note both mention the new mode. The unrelated ADR-076 opt-in graded-promotion path (`config.benchSuite`) is untouched — it already special-cases only `mock` mode with a fallback for everything else, and extending it to `llm-agent` is a separate, not-yet-requested feature.

## Consequences

- The existing three sandbox modes and their tests are byte-unmodified; only their shared dispatch points gained a fourth branch.
- `llm-agent` is the first Darwin Mode sandbox with real, non-zero marginal cost per run — every other mode ($0) can be run freely; this one cannot, and the CLI now says so before it happens rather than after.
- `llm-agent`'s single default task (`llm-review-needs-test`, surface `reviewer`) is deliberately narrow — one cheap, well-understood judgement, not a general benchmark. Broader task coverage (other surfaces: `planner`, `toolPolicy`, `contextBuilder`; harder or multi-turn judgements) is a natural follow-on once the mechanism itself is validated, not required for this ADR.
- This ADR does **not** address the separate finding that `metaharness-darwin evolve` never reads a downstream consumer's `genome.json` prose at all (see Context). A prompt-genome consumer gets real signal from `llm-agent` only for whatever surface content actually lives in a variant's `.ts` files at evaluation time — bridging an external prose genome into that baseline is out of scope here.
