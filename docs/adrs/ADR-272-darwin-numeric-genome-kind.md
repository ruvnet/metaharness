# ADR-272: Darwin Mode — numeric genome kind (a second, parallel evolution domain)

**Status**: Accepted (implemented)
**Date**: 2026-09-01
**Project**: `ruvnet/agent-harness-generator`
**Related**: ADR-070 (evolve loop), ADR-071 (mutation surfaces + safety gate), ADR-072 (scoring/promotion), ADR-073 (archive tree), ADR-089 (crossover), ADR-100 (Pareto selection)

> Everything Darwin Mode has evolved so far is one genome kind: seven text files, mutated by rewriting code/prose, scored by running the repo's own test suite. That is the right shape for evolving a harness's prompts. It is the wrong shape for evolving a *numeric* configuration — e.g. an ML training run's learning rate, batch size, and epoch count — where "mutation" means perturbing a bounded number, not rewriting a file, and "fitness" means an external metric (a loss, an accuracy number) that has nothing to do with `npm test`. This ADR adds that second genome kind as new, parallel modules, without touching the existing one.

## Context

A downstream consumer (`ruvnet/wifi-densepose`, the `harness/ruview` contributor harness) wanted to use Darwin Mode's evolutionary search to tune `ruview-forecast-train`'s hyperparameters (learning rate, epochs, batch size, weight decay) against a weighted-quantile-loss (WQL) metric computed by training a real Burn/Rust model. They built a standalone reimplementation of the loop first, then asked for it upstream instead.

It does not fit through any existing extension point:

- `EvolutionConfig.generator?: CodeGenerator` (ADR-071) is genuinely pluggable — but `createChildVariant` (mutator.ts) still hardcodes *which file* to regenerate via `pickSurface()`, drawn from the closed seven-value `MutationSurface` union. A `CodeGenerator` can change *what code* fills a surface file; it cannot make the variant not be "a directory of seven approved files".
- `EvolutionConfig.benchSuite` (ADR-076) evaluates a child against a parent over a benchmark of *coding tasks* (`BenchmarkTask`, with `publicTestCommand`/`hiddenTestCommand`) run through the SWE-bench-style sandbox. There is no way to substitute an arbitrary external metric for "does the test suite pass".
- `RepoProfile.testCommand` (repo_profiler.ts) is "the command the sandbox runs to score a variant" — profiled from the *target repo's own* test/build tooling, not a caller-supplied fitness function.

Widening `MutationSurface` to an eighth, numeric-genome "surface" was considered and rejected: that union is ADR-071's safety allowlist — the seven files an LLM-backed mutator is permitted to touch, specifically bounded to keep prompt-injection/capability-escalation risk contained. A numeric hyperparameter vector is not a code-safety domain; folding it into that allowlist would blur the boundary the allowlist exists to hold, for no benefit (a numeric genome is never LLM-mutated free text in the first place).

## Decision

Add a second, fully independent genome kind, as new modules that do not modify `evolve.ts`, `mutator.ts`, `types.ts`, `archive.ts`, `scorer.ts`, `sandbox.ts`, `cli.ts`'s `evolve` verb, or any existing test:

- **`numeric-types.ts`** — `NumericParamSpec {min, max, scale: 'linear'|'log', type: 'float'|'int', default?}`, `NumericGenomeSpec` (name → spec), `NumericGenome` (name → value), `NumericVariant`, `NumericScoreCard` (`{primary, regressed, noopRate, costPerWin, raw?}` — the same evidence shape `ruviewPromotionRule`-style gates already expect), `NumericArchiveRecord`, `NumericEvaluator` (the fitness-function interface), `NumericEvolutionConfig`/`Result`.
- **`numeric-mutator.ts`** — deterministic, seeded (mulberry32 + Box–Muller, no `Math.random`, mirroring `mutator.ts`'s `hash()` reproducibility contract). Perturbation is Gaussian noise in **unit-genome-space**: a `log`-scale parameter (e.g. a learning rate) is perturbed multiplicatively, a `linear` one additively; always clamped to `[min, max]`; `int`-typed parameters are rounded. Every mutation changes at least one parameter (forced, so the archive never fills with byte-identical duplicates). `crossoverGenome` recombines two parent genomes by independent per-parameter coin flip, forced to a proper non-empty subset from B — the numeric analogue of ADR-089.
- **`numeric-archive.ts`** — a small `NumericArchive` class mirroring `archive.ts`'s API and semantics (tree, retention of non-promoted variants, deterministic insertion-order tie-breaks, tolerant `load`) but typed for `NumericVariant`/`NumericScoreCard`. Kept separate rather than generifying `Archive` in place, so the existing archive and its tests are untouched.
- **`numeric-evaluator.ts`** — `ShellEvaluator`, the default `NumericEvaluator`: spawns a caller-supplied command (never a shell, argv already split — same "never a shell" discipline as `copyVariantDir`/the sandbox runner), writes `{variantId, genome}` as JSON on stdin, parses a `NumericScoreCard`-shaped JSON object from stdout. An evaluator crash, timeout, non-zero exit, or non-JSON output demotes the candidate (`regressed: true, primary: -Infinity`) instead of throwing — one bad candidate cannot abort the run.
- **`numeric-evolve.ts`** — `evolveNumeric()`, the generation loop: baseline (bounds midpoint or explicit `default` per parameter) → evaluate → per generation, mutate/crossover from current parents → evaluate with bounded concurrency (reuses `mapLimit` from `evolve.ts` directly — genuinely generic, untouched) → parents strictly improving over their own parent's `primary` are promoted; on a stall, fall back to the Pareto front over `(primary ↑, distance-from-baseline ↑)` (reuses `paretoFront` from `pareto.ts` directly — also generic) so a stalled search still explores instead of freezing. Persists `archive.json`/`reports/winner.json` under a `.metaharness-numeric` work tree, mirroring `evolve.ts`'s persistence contract.
- **CLI**: `metaharness-darwin evolve-numeric <repo> --genome <spec.json> --evaluator "<cmd> [args...]" [--generations N] [--children N] [--concurrency N] [--seed N] [--sigma F] [--crossover] [--evaluator-timeout-ms N]`.
- **Exports**: `index.ts` re-exports all five new modules alongside the existing ones (namespacing was unnecessary — no symbol collisions with the prompt-kind exports).

## Consequences

- The existing prompt-kind evolution (evolve/mutator/archive/scorer/sandbox/cli's `evolve` verb) is **byte-unmodified**. `packages/darwin-mode`'s full suite: 586 passed / 3 skipped-by-platform (pre-existing Windows symlink-permission `EPERM` failures in `__tests__/security/inspect-bypass.test.ts` and a downstream cleanup failure in `__tests__/perf/mapLimit.test.ts` — both require filesystem symlink privileges Windows denies by default outside Developer Mode; unrelated to this change, not present on the package's Linux/macOS CI).
- A numeric-genome consumer never needs Darwin Mode to understand its evaluation domain — the `NumericEvaluator` boundary is opaque by design (`raw` carries whatever the caller wants to report; the engine only ever reads `primary`/`regressed`/`noopRate`/`costPerWin`). This is deliberately narrower than the prompt kind's built-in sandbox: numeric evolution's whole value is "plug in your own fitness function", not "we also judge your fitness function".
- No LLM-backed numeric mutator exists yet (unlike `openrouter-mutator.ts`/`ruvllm-mutator.ts` for prompts) — Gaussian perturbation is a standard, well-understood default for bounded numeric search and needs no model in the loop. An LLM-informed numeric proposer (e.g. suggesting promising regions from training curves) is a natural future ADR, not required for this one.
- `selection` (quality-diversity / behavioral-diversity / niche-steering / clade / MAP-Elites), `benchSuite`/SGM risk budgets, curriculum, and epistatic crossover are all prompt-kind-specific and **not** ported to the numeric kind in this ADR — those depend on `MutationSurface`-shaped behavioural descriptors or coding-task benchmark suites that have no numeric-genome analogue yet. The numeric kind ships with: mutation, opt-in crossover, and Pareto-front stall recovery. A richer numeric selection strategy is a follow-on ADR if a consumer needs it.

## Validation

`packages/darwin-mode` — 17 new tests (603 total from 586): `defaultGenome` (bounds-midpoint including the `log`-scale geometric mean, explicit `default` override), `mutateGenome` (never leaves `[min,max]` across 75 seed/generation combinations, keeps `int` types integral, is byte-deterministic for a fixed `(seed,generation,index,sigma)`, differs across seeds, never a silent full no-op), `crossoverGenome` (proper non-empty subset from B), `evolveNumeric` (converges toward a known synthetic optimum over 6 generations, is reproducible across two same-seed runs including the winner's exact genome, round-trips `archive.json`, demotes an evaluator's `regressed:true` without crashing the run), and `ShellEvaluator` (round-trips a genome through a real spawned Node subprocess with no shell, demotes on non-zero exit / non-JSON stdout / timeout, tolerates log noise printed before the JSON payload).

End-to-end CLI proof: `metaharness-darwin evolve-numeric` run against a synthetic two-parameter target (`learning_rate → 0.01` log-scale, `epochs → 150` linear) via the real built `dist/cli.js` and a throwaway Node evaluator subprocess — 3 generations × 4 children genuinely converged to `learning_rate=0.007369, epochs=149` (primary improved +1.997 over baseline), proving the full CLI → `evolveNumeric` → mutation/crossover → `ShellEvaluator` subprocess → archive → Pareto-stall-recovery → winner-report path end to end through the actual published binary entry point, not just unit-level.

Wiring against the real motivating consumer (`ruview-forecast-train`'s hyperparameters, scored by real Burn/Rust training + WQL over SSH) is tracked in the `ruvnet/wifi-densepose` repo's `harness/ruview/flywheel/ruforecast/` — that repo's `run.mjs --confirm` path now invokes this ADR's `evolve-numeric` CLI instead of a standalone fallback search.
